# Notifications and Alerts

Three connected surfaces plus background machinery:

- **Alerts page** `/alerts` (no rail row or phone tab; reached from the header bell with its unread badge, and Ctrl K): the record of every alert this device fired or received, grouped by type, device-wide across Characters. Glossary: Alert, Notification Feed.
- **Settings > Notifications** `/settings/notifications` (Settings rail group "Alerts"): what may fire, per Character, per event, per channel; master switch, channel gates, permission prompt/enable, thresholds.
- **Browser permission explainer** (one-time banner) `NotificationPermissionPrompt`.
- **Machinery**: Foreground Poller (5 min, open app), Scheduled Push (Projection uploaded to Firebase, delivered by FCM to the service worker), server-pushed events (community, price alerts, ship lost; ADR 0027; nearby, ADR 0028; new mail, ADR 0029), app-icon badge, Web Push registration, feed sync.

User goal: be told about the in-game things that matter (queues finishing, jobs, mail, structure attacks, price crossings), on a pop-up and/or in an in-app list, for every Character, without a server holding EVE tokens (ADR `docs/adr/0010-scheduled-push-without-server-side-tokens.md`, ADR 0009 push replaces periodic background sync).

Code: `src/routes/Alerts.tsx`; `src/features/notifications/*` (see below); `src/engine/{notificationDiffs,projection,occurrenceKey,severity}.ts` (pure); `src/sw.ts:135,165` (service worker); `src/sync/{deviceRegistration,webPushSupport}.ts`; `src/app/{AlertCharacterSwitch,routeScopes}.ts(x)`; Settings host `src/routes/Settings.tsx:1092`.

## Purpose and user goal

"Tell me when something in game needs me, even when the app is closed." This doc owns being told: which Notification Events fire, for which Character, through which channel (device pop-up or the in-app Alerts list), and which can reach a closed app via Scheduled Push (ADR 0010; ADR 0009). Its sibling `alerts.md` owns the record of what already fired. Every Character is polled, not only the active one (`src/features/notifications/foregroundPoller.ts:268`, "One poll across every character"; `src/routes/Alerts.tsx:11`).

- **Top jobs (ranked):** 1. "Will I be told before my queue, job, extractor or courier runs out, for every Character?" (per-event, per-Character, per-channel toggles and thresholds). 2. "Turn on notifications on this device" (permission prompt, Enable, iOS install-to-home-screen notice). 3. "Why didn't this alert me?" (rows needing a Permission or corp role show why, with Grant, #1525; push-badged events, #2952).
- **Device and cadence:** settings are made on the desktop, the app's primary device (owner, 2026-10-11). The phone is a delivery target for push: iOS needs the installed app, Android has the Play Store app, and the Install Prompt is phone-only (`20261002-165619`). Settings are set once and revisited rarely (inferred).
- **Above the fold (Settings › Notifications):** permission state with Enable, the master switch and the two channel gates, search, then the active Character's section (open by default).
- **Not for:** reading, dismissing or muting what already fired (`/alerts`, `alerts.md`); instant combat alerts with the app closed (pushed: events whose time is known ahead, ADR 0010; EVE notifications under an Alerts Grant, ADR 0020; the five server-pushed events, ADR 0027; and nearby Incursions and skyhooks under a location-capable Alerts Grant, ADR 0028); a push digest (#2871, dropped: closed as not planned).
- **Sources:** owner, 2026-10-11 (desktop primary, phone for one-off lookups); ADR 0009, ADR 0010; decisions `20260901-181135`, `20260925-112832`, `20260907-114310`; #1525, #2952, #2844, #2871.
- **Unconfirmed:** that pilots mainly want the phone buzz rather than the in-app list; set-once cadence.

### Mobbin brief

- **Fit:** high. A notification preferences matrix, a permission priming banner and per-account sections are common patterns.
- **Analog apps:** Slack, GitHub, Discord, Robinhood.
- **Screen queries:**
  - `web: notification settings with events as rows and delivery channels as checkbox columns, grouped by account in collapsible sections`
  - `ios: permission priming banner explaining why to allow notifications with allow and dismiss buttons`

## Alerts page (`/alerts`)

- Route gate: `UNGATED` (`routeScopes.ts:89`): it reads Dexie only; a Character with no grants simply has an empty feed. Not shown until preferences have hydrated (`!prefsHydrated -> null`).
- Header: "Notification settings" link (to `/settings/notifications`), "Dismiss all" icon (only when there are live alerts), nothing else. No Data Age badge (local data). No refresh (live Dexie query `readFeed`, ordered `firedAt` desc).
- Banner when master or the feed channel is off: "The in-app alert list is switched off in Settings... What is already here is still listed" (`alerts.feedOff`).
- Grouping: one group per `alertGroupKey` - `eveType:<TYPE>` for EVE notifications (each type is its own group) else `event:<eventId>`. Dismissed entries excluded. Group: count, newest fire, severity, Character ids, entries newest first (`alertGroups.ts`).
- Severity (`alertSeverity`): EVE types - critical for StructureUnderAttack, LostShields, LostArmor, Destroyed, OrbitalAttacked, OrbitalReinforced, CorpKicked; warning for fuel/reagent/low-power/abandonment/jobs paused or cancelled/services offline, bills (CorpAllBill, BillOutOfMoney, CorpOfficeExpiration, InfrastructureHubBill), WarDeclared, AllWarDeclared, CorpBecameWarEligible; clear for StructureWentHighPower; watch for every Moonmining type (extraction started/ready/cancelled, drill fired, automatic fracture) and CorpAppNew; unknown types default `watch`. Events: warning = characterNotTraining, structureFuelLow, corpWalletThreshold, planetaryExtractorExpiring, skillQueueEnding, courierDeliveryDue, contractFailed, marketOrderUndercut, shipLost, mercenaryDenAnarchy; clear = marketOrderFilled, walletBalanceChanged, priceAlertTriggered, contractCompleted; the rest watch. `mercenaryDenReinforced` is the one critical personal event (severity is per event, so its lead-time warning shows in the Danger banner as well as the exit).
- Sort: severity (`compareSeverity`) then newest fire first.
- Row: caret expand (button `aria-expanded`), severity icon + count, label (+ "MUTED" tag), mute toggle (IconButton `pressed`, tooltip), dismiss-type X. Expanded: each fire has Character pill (only if the device has > 1 Character; body also drops the repeated Character name via `dedupeCharacterName`), relative age with tooltip of full timestamp (honours Local/EVE time), optional "approximate time" info for provisional sell-fill rows (`isProvisionalFill`: fill time is the poll time until the wallet confirms, `fillTimeSettle.ts`), body as a link, dismiss X.
- Fire link target = `notificationUrlForSubject(eventId, subjectId ?? typeId, characterId)`: base route (`NOTIFICATION_ROUTES`: skills -> `/skills/trained`, queue ending -> `/skills`, SP extraction -> `/characters`, jobs -> `/industry`, clone -> `/clones`, PI -> `/planetary-industry`, mail -> `/mail`, calendar -> `/calendar`, contracts -> `/contracts/history`, wallet -> `/wallet/journal`, fills -> `/market/history`, undercut -> `/market/orders`, EVE notification -> `/alerts`, corp fuel -> `/corp`, corp jobs -> `/industry`, members -> `/corp/members`, corp wallet -> `/corp/wallet`, price alert -> `/market/browser`, stock target -> `/market/stock`, incursion nearby -> `/travel/route`; fallback `/alerts`) plus `highlight=<id>` for fills, undercut, wallet, contracts, courier, jobs, corp job, member joined; `type=<id>` for price alerts; `division=<id>` for corp wallet; `market=<id>` for stock targets; `stops=<staging system>` for incursion nearby; always `character=<id>`. `AlertCharacterSwitch` makes that Character active, strips the param, shows a 5 s "Switched to <name>" status; an unknown or already-active id just loses the param.
- Filters (`FilterBar`, funnel sheet on phone; URL, ADR 0015): search `query` (matches group label or any entry title/body, case-insensitive), `characterId` (Select, "All characters"), severity chips for critical/warning/watch (no chip for `clear`; empty set = no filter; chips show counts of live groups), `showMuted` ("Muted types" chip with count). `activeAlertsFilterCount` counts query + character + each severity + showMuted. "Reset filters" button appears when filters hide everything. Narrowing to a Character filters the entries before grouping.
- Muted: a group is muted only if muted for every Character it fired for (`isEntryMutedInFeed`). Muted groups are hidden unless the chip is on and are excluded from counts, "Dismiss all", the nav badge and the app badge. Mute writes the feed-channel flag per Character/type (`toggleEventChannelPref` / `toggleEveTypeChannelPref` on `feed`), so it is the same switch as the Settings Alerts column and is synced.
- Dismiss writes `dismissedAt` and schedules sync per Character (`dismissFeedEntriesAndSync`); dismissed rows are kept (invisible) and still suppress a duplicate toast. With Dismiss on View on (Settings), the View button on the Alerts popover and on the Overview danger banner dismisses the alert too, then navigates.
- Focus management: after dismiss/mute the focus moves to next row, else previous, else the panel heading (WCAG 2.4.3).
- Empty: "No alerts yet / Events you have enabled appear here while the app is open"; no-match variant with Reset. Footnote: "This device keeps the last 300 alerts, and syncs 30 days of them between your devices."
- Retention constants: `NOTIFICATION_FEED_LIMIT = 300` (older trimmed on write except rows just written); sync window `FEED_SYNC_WINDOW_MAX_ROWS = 100` and `FEED_SYNC_WINDOW_MS = 30 d` (`feed.ts`).

## Feed storage and merge rules

- Dexie `notificationFeed` row keyed by Occurrence Key (`id`): `characterId`, `eventId`, `eveType?`, title, body, `firedAt`, `dismissedAt?`, `notifiedHereAt?`, `subjectId`/`typeId`, fill fields.
- `mergeFeedRecord`: earliest `firedAt` wins, latest `dismissedAt` wins (a dismissal sticks whichever order two writers land), other defined fields from incoming.
- Toast suppression (`rowSuppressesToast`): skipped only if this device already notified (`notifiedHereAt`, local, never synced), or dismissed anywhere, or the row is older than `TOAST_STALE_AFTER_MS` = 24 h (decision `20260925-112832-device-notification-dedup-is-per-device`).
- Feed sync: rows synced via `notificationFeed` collection (`sync/syncedCollections.ts:668`, `feedSync.syncFeed`), per Character; `feed.ts` itself does not call sync (service worker imports it) - page callers use `feedSync.ts` (decision `20260912-125743-alert-dismissals-push-on-dismiss-a-visible-tab`). A Service-Worker-written row syncs on the next page-context sync.
- Removing a Character deletes its rows (`deleteFeedForCharacter`).

## Badges

- `refreshAppBadge()` = 0 if master off or feed channel off, else count of `visibleFeedEntries` (undismissed and not muted); sets/clears via the Badging API (`navigator.setAppBadge`/`clearAppBadge`, errors swallowed, no-op where unsupported). Called on poller mount, every feed write/dismissal, on preference change (Alerts and Settings).
- `useUnreadAlertCount()` is the same rule as a live hook for the rail badge and Overview column (device-wide).
- Note: nothing marks an alert "read"; it is dismissed or not. "Unread" = visible.

## Settings > Notifications

- Section `notifications` in Settings rail group "Alerts" (`features/settings/sections.ts:29`); also reached by `Alerts` header link, command palette "Open notification feed" is the Alerts page (not settings).
- States by live `Notification.permission` (read on focus/visibility, never from the stored outcome): `denied` -> blocked notice (Play Store app: "Notifications are off for this app" + "Open notification settings" Android intent button; otherwise generic notice) and the browser channel and its per-row Device checkboxes are disabled, but the rest remains usable; `default` -> hint + "Turn on device notifications" primary button (the only code that triggers the browser prompt; also records the ask so the explainer is not shown again); iOS Safari not installed (`webPushSupport() === 'requires-install'`) -> "install to home screen" notice instead of the button; `granted`/no API -> unchanged.
- Master switch "Enable notifications" (`masterEnabled`, default true) disables the fieldset below it. Channel gates: "Device pop-ups" (`browserEnabled`, default true, forced off while blocked) and "Overview notifications" (`feedEnabled`, default true). Gates are independent, not a fallback chain. Master/browser/feed gates are device-local (`setDeviceNotificationPrefs`). "Dismiss on View" (`dismissOnView`, default false, device-local, enabled even with the master switch off) sits in the same row, outside the channel fieldset: when on, the Alerts popover's View button and the Overview danger banner's View button also dismiss the alert (`AlertsPanel.tsx`, `DangerBanner.tsx`). The Alerts popover's footer link to this page reads "Manage Notification Settings". Wallet Balance Changed's per-Character threshold list is headed "Minimum ISK change alert" (`headingKey` on its `thresholds`).
- Search box "Search events or characters" (URL `search`; active at >= 3 chars, `NOTIFICATION_SEARCH_MIN_QUERY_LENGTH`): an event label narrows the rows; a Character name keeps every row and narrows opened rows to that Character; events win when both match (`filterNotificationEvents`).
- One event-first list (`NotificationEventList.tsx`; decision `20261014-173602`): events under named groups (`eventGroups.ts`: Skills, Industry and PI, Market and contracts, Mail and calendar, Space and community), then "Corp notifications", then EVE notifications last. Each row (`AggregateRow.tsx`) has a label, an optional closed-app badge (`pushBadgeKind`: "scheduled push", tooltip "up to 72 hours ahead", for events with `projection.everyOccurrence === true`; "server" for the server-pushed events, tooltip without the 72-hour promise), a "All N alike" / "K differ" chip (`channelSummary.ts`), and two tri-state `SelectionCheckbox`es (Device, Alerts) that broadcast to the Characters the event applies to (`broadcast*` in `preferences.ts`).
- Opening a row lists every Character as a chip with its own Device and Alerts checkboxes (`CharacterChipGrid.tsx`): inline from `md`, a `Modal placement="sheet-full"` on a phone.
- An event applies to a Character when its token holds the event's scope and (corp events) the Character holds the corp capability; unresolved capabilities read as held (`eventApplicability.ts`). Characters it does not apply to stay listed, dimmed, with a tooltip: a re-authorize hint for a scope, "a Director must grant the role" for a corp role. A row says once how many Characters have not granted the Permission, linking to Settings > Permissions. Corp events share one group header with the "best-effort: fires only while the app is open" note.
- Row hints: `extractorExpiringHint` (72 h projection horizon, open the app at least that often), `marketOrderUndercutStationOnlyHint` (own NPC station only, app open).
- Threshold controls, listed per Character under the opened row's chips (`EventThresholdsList.tsx`; only Characters the event applies to and has on): select choices or ISK inputs (parsed with `parseIskAmount`, committed on blur/Enter), persisted per Character, synced, rebuild the Projection within 1 s (coalesced `PROJECTION_REBUILD_DELAY_MS = 1000`).
- EVE notifications row expands to Families (Structures, War, Corp Governance, Bills, Moon Mining, PI, plus an Other group for seen types) with a tri-state per family and per type across Characters (`EveNotificationRow.tsx`); each type row opens inline to its Characters.
- Defaults (absence means default, `eventSelection.ts`): ordinary events both channels on except `feedOnly` events (marketOrderFilled, contractCompleted, contractFailed, walletBalanceChanged) where Device defaults off. EVE types default Alerts-on / Device-off (`EVE_TYPE_DEFAULT`) except StructureUnderAttack, LostShields, LostArmor, Destroyed, OrbitalAttacked, OrbitalReinforced, CorpKicked which are Device-on too. Legacy bare boolean means both channels.

## Foreground Poller

- `ForegroundNotificationPoller` (mounted in `Layout`, renders null): first poll 10 s after mount (`FIRST_POLL_DELAY_MS`), then every `POLL_INTERVAL_MS = 5 min`, only while this tab is the Tab Leader (Web Lock; per-origin election; the leader keeps polling while hidden, issue #5120) and not running elsewhere (`runUnlessRunningElsewhere('neocom:poll')`); catch-up on `visibilitychange` and on taking leadership. IndexedDB teardown errors (iOS backgrounding) are swallowed as a missed tick. Also restores the app badge on mount.
- `runForegroundPoll`: skipped entirely if master is off. Per Character, per domain (19 in `POLL_DOMAINS`: skill queue, SP extraction, industry jobs, clone jump, colonies, mail, calendar, contracts, wallet, market orders, undercut, EVE notifications, structure fuel, corp jobs, corp roster, corp wallet, price alerts, stock targets, incursions): enabled events = in scope AND either channel on; if none, the domain is not fetched. Domain loads run in the background lane. Each domain stores a baseline snapshot (Dexie via `pollerState`), diffs against it, then saves it. First poll after a baseline is absent usually fires nothing (inferred from `if (!prev) return []` guards seen in `diffCharacterNotTraining` and its comments; exceptions: SP extraction, and structure fuel/price alert treat a missing counterpart as not-previously-inside).
- Delivery loop: allow-list gate for EVE types (`isEveTypeAllowed`); browser channel only if master + browser gate + permission granted + event/type pref; `alreadyDelivered` checked by Occurrence Key before this poll writes its own feed row; fires with identical rendered copy are grouped into one toast with a count suffix; browser delivered keys are marked (`notifiedHereAt`). Feed channel: one row per fire, never grouped; `recordToFeed`. Retractions remove disproven extractor rows. Then `rebuildProjection`.
- Browser display (`display.ts`) prefers the service worker registration's `showNotification` (the `Notification` constructor throws on Android Chrome and does not exist on iOS). Tag `characterId:eventId`, `renotify: true`, click data url from `notificationUrlForSubject`.
- Click handling (`notificationClick.ts`, `sw.ts:135`): focus an existing same-origin window and navigate it (unless already there), else open a window; errors swallowed.

## Scheduled Push (closed app)

- ADR 0010: the client projects timestamped future events (72 h `PROJECTION_HORIZON_MS`) and uploads rendered rows; a scheduled Cloud Function fires due rows through FCM. The backend never holds an EVE token.
- `rebuildProjection`: for each Character (concurrency-limited), if master && browser gate && permission granted, for each projecting domain's saved baseline run its `projection()` and keep rows whose event has scope and browser channel on; otherwise upload empty rows (clears the device's rows). Then `uploadProjectionRows` (skips unless `webPushSupport() === 'supported'` and permission granted).
- Triggers: after every poll; after a preference change that alters `projectionInputs` (master, browser gate, per-Character browser-off-default events and EVE types, the four push thresholds), coalesced by 1 s `createCoalescedRebuild`; after Enable.
- `registerDeviceForWebPush`: gets an FCM token (`VITE_FIREBASE_VAPID_KEY`), then calls the Firebase callable `registerDevice` with `deviceId`, `fcmToken`, and per Character a freshly refreshed short-lived ESI **access token** plus the Projection rows (rendered title/body). Refresh tokens never leave Dexie. Skipped by fingerprint when nothing changed within `REREGISTER_AFTER_MS` = 1 h (poller sets `skipIfUnchanged`; the Enable tap does not). Per-Character partial success; fingerprint remembered (localStorage `neocom.lastPushRegistration`) only when all landed and no overlapping upload. Replaces only this device's rows (issue #2240). Empty roster -> no token minted/deleted.
- `unregisterProjectionRegistration` / `unregisterDeviceForWebPush` delete the FCM token when the last Character leaves.
- Service worker `push` handler (`pushHandler.ts`): parses `data` (`characterId`, `eventId`, `occurrenceKey`, `title`, `body`, optional `eveType`, `fireAt`); unparseable payload still shows a fallback notification (WebKit revokes a subscription if a push shows nothing); records a feed row (id = occurrence key, `firedAt = min(fireAt, now)`, `notifiedHereAt = now`); shows notification and writes the feed in parallel (`allSettled`).

## Server-pushed events (closed app)

ADR 0027, decision `20261025-073433-server-pushed-events-community-triggers-polled-price-alerts`, issue #5121. Five events the backend can push with no EVE token: `SERVER_PUSHED_EVENT_IDS` in `serverEvents.ts`.

- **Registration.** `rebuildProjection` also builds, per Character, `serverEvents` (the five that are in scope and on for the Device channel; empty lists when master, the browser gate or permission is off) and `serverInputs` (`readServerInputs`: Quickbar price targets with the Trade Hub station, the ship-lost minimum). `registerDeviceForWebPush` sends both beside `eveTypes`; both are in the fingerprint. The server stores them on the device's registration doc (`serverEventsByCharacter`, `serverInputsByCharacter`, plus `polledServerEvents` for its query); an upload without them keeps the stored ones. The ship-lost minimum is in `projectionInputs`, so changing it re-registers within 1 s; a Quickbar target or Trade Hub change reaches the server with the next poll's rebuild (up to 5 min, app open). The Enable tap sends the same lists, so it never wipes them.
- **Rollout.** The deployed `registerDevice` parser ignores keys it doesn't know, so the web client works against an older function; nothing is pushed for these until `firebase deploy --only functions` ships `pushCommunityAlert`, `pushCommunityPledge` and the updated `dispatchProjections` and `alertsCall`.
- **Community** (`functions/src/communityPush.ts`, `serverEventStore.ts`): Firestore triggers on create of a waiting-list doc, a Member doc (not the founder; not one marked `admittedFrom: 'request'`) and a Pledge doc (the requester's own open, non-standing Request with `notify.app`; never their own Pledge). Pushed at once to the admin's or requester's devices that enabled the event.
- **Price alerts and ship lost** (`functions/src/serverEventPoll.ts`): on the 15-minute `dispatchProjections` tick, beside the projection dispatch. One Fuzzwork read per hub station, one zKillboard `losses/characterID` read per Character (1 s apart, 300 a run, rotated; 420/429 stops for the run). Diffs per device against readings on the registration doc (`serverEventBaselines`), mirroring `diffPriceAlertTriggered` and `diffShipLost` (root parity tests). A failed source keeps the last reading; a transient send failure keeps it so the next tick retries.
- **Delivery.** Quiet Time applies; `shipLost` passes when "Let attacks through" is on. Dead FCM tokens delete the registration, as the other two senders do.
- **Rendering.** The push carries the raw fire (`fire`, JSON) and a plain English floor. The service worker parses it (`serverEventPayload.ts`; it must name the push's own event and Character), renders it with the poller's copy (`serverEventCopy.ts`), names a lost hull and system through public `/universe/names`, and writes the feed row under `occurrenceKey(fire)`. If this device already showed a pop-up for that key (`notifiedHereAt`), the push replaces it silently (same tag, `silent`); the tag is per Character and event, so it can replace a newer pop-up of the same event. A Pledge edited, or joined by others, before the open app polls can still file a second row (the poller keys by the `updatedAt` it reads and groups per Community).

## Alerts when closed (server-polled push)

- ADR 0020: an opt-in, per-Character **Alerts Grant** (a second SSO authorization whose refresh token goes to the server, never to the device) lets `functions/src/pollEveNotifications.ts` read `/notifications/` every 15 minutes and push the EVE types each device enabled for the browser channel (`eveTypes` on `registerDevice`).
- ADR 0028 (issue #5122): the grant may also carry `esi-location.read_location.v1`. For such a grant the same run reads the Character's solar system, then `pollNearby.ts` pushes `incursionNearby` and `skyhookRaidableNearby` per device: entries, diffs (`incursionAlert.ts`, `skyhookAlert.ts`) and jump counts (`jumpRoute.ts` over `data/stargateGraph.ts`) are byte-pinned mirrors of the app's own, under the device's uploaded `routeRules` and per-Character N (`incursionNearbyJumps` / `skyhookRaidableNearbyJumps` in `serverInputs`), gated on the per-Character `serverEvents` list (the two ids are in `SERVER_PUSHED_EVENT_IDS`). Gates only: no Thera/Turnur holes or Ansiblex bridges, and the game location rather than a hand-picked Current System (decision `20261025-074204-server-counts-nearby-jumps-over-stargates-from-the`). One copy per occurrence per device, not re-pushed while the list still names it; Quiet Time skips without queueing (decision `20261025-074204-nearby-alerts-ride-the-alerts-grant-and-its`). Per-device state rides on the registration doc (`nearbyState`).
- The client asks EVE for the location scope only after a `registerDevice` answer carried `nearbyGrants` (an older deployed function, which would refuse it, omits the field): `alertsGrant.ts` `readAlertsNearby` / `useAlertsNearby`. A grant from before shows "On, without nearby alerts" with an "Add nearby" re-authorize action; nearby rows show the closed-app badge once some Character's grant carries the location (`NearbyPushBadge`).
- A nearby push carries its raw fire like the other server-pushed events (below); the worker words it with `pollDomains/copy/nearbyWording.ts`, the poller's own copy, and names the systems, planet and constellation through `/universe/names`.

- ADR 0029 (issue #5143): the grant may also carry `esi-mail.read_mail.v1`, added only by an explicit per-Character **Add mail** (never part of Turn on). For such a grant, and only while some device lists `newMail` in its `serverEvents` for the Character, the same run reads `GET /characters/{id}/mail/` (headers only; ETag/304; same etiquette) with the same refreshed token (`esiMail.ts`, `pollMail` in `pollEveNotifications.ts`). `mailPush.ts` mirrors `diffNewMail` and the Occurrence Key (root parity test): the first read seeds a high-water `mail_id` silently (`mailHighWaterId` on the grant doc; nothing replays on enable), then every id above it not sent by the Character fires. No device wanting it clears the mark, so re-enabling seeds afresh. At most 5 newest mails of a burst are pushed per device (the rest reach the Alerts list when the app opens); Quiet Time skips without queueing; a transient send failure keeps the mark and ETag and logs `deviceId|Occurrence Key` in `mailPushed`, so a retry skips devices already served. A 403 drops the mail scope from the grant (state cleared) without revoking it.
- **Mail content.** The push carries the raw fire (`fromId`, `subject`); the worker resolves the sender through public `/universe/names` and words the pop-up ("{{character}} has new mail from {{sender}}: {{subject}}", `newMailText` in `serverEventCopy.ts`; an unnamed sender or empty subject is left out). The feed row is filed with the poller's plain line ("{{character}} has new mail.") because the Notification Feed syncs to Firestore: no sender, subject or other mail content is ever stored server-side. Server state is the mark, ETag and pushed log only. This is a deliberate departure: the open app's own pop-up and feed row for `newMail` name neither sender nor subject.
- Rollout and UI: `registerDevice` answers `mailGrants` beside `nearbyGrants` (an older function omits both, so the client never asks EVE for the mail scope: `useAlertsMail`). "Add mail" re-authorizes with every extra the Character already has (a re-authorization replaces the token with exactly what is requested); each row states what its grant reads; the `newMail` row carries the closed-app badge once some Character's grant has mail (`MailPushBadge`). Turn off deletes the whole token; there is no mail-only removal.

## Permission explainer

`NotificationPermissionPrompt` shows a fixed banner (role=alert) once per device when: preferences hydrated, not previously `seen`, at least one Character, `Notification.permission` is `default` (or iOS not installed), the player has left the first screen of their first-ever session (`firstScreen.ts`, issue #1788: route change, session flag in Dexie `notifications.hasCompletedASession`), and it wins the onboarding banner slot (`useOnboardingBannerSlot('notifications')`). Buttons: Dismiss (stores `seen: true`), and Enable (hidden when iOS install required), which calls `enableWebPush()`: requests permission; on grant registers the device (lazy-imported Firebase chunk so startup never statically reaches Firebase, `bootImportGraph.test.ts`); stores outcome via `promptStateAfterAsk`. Dexie key `notifications.permissionPrompt`.

## Synced vs local preferences (`syncedPreferences.ts`)

- Local Dexie `notificationPreferences`: master, browser gate, feed gate, per-Character event maps, per-type EVE maps, thresholds.
- Synced (setting `sync.notificationFeedPrefs`, one whole-value last-write-wins blob across all Characters, allow-listed in `syncedSettings.ts:261`): only the **feed** half of every per-Character event/type toggle (explicit values only, defaults not shipped so future default changes apply) plus **all seven thresholds**. Master, both gates and the browser half stay device-local because the OS permission is per device. Merge keeps local browser flag. Accepted trade-off: two devices editing different Characters concurrently can clobber each other.
- Writes through `updateNotificationPrefs`: persists locally, pushes the synced blob unless the change was browser-channel only, schedules sync, and schedules a Projection rebuild if the projection inputs changed. `hydrateNotificationPreferences` merges the synced blob into local on load.

## Interview Q&A

1. **Why is there both a poller and a push backend?** CCP has no webhooks; a polling backend would need refresh tokens (reverses ADR 0001, and rotating tokens cannot be shared). So the open app polls every 5 min and also projects known future timestamps for 72 h to a scheduled function (ADR 0010, `projection.ts:155`).
2. **Which events can wake a closed app?** The `PROJECTABLE_EVENT_IDS` (Scheduled Push; those with `everyOccurrence` carry the badge, `eveNotification` projects only structure reinforcement exits), every allow-listed EVE notification type for a Character with an Alerts Grant (ADR 0020), the five server-pushed events (ADR 0027, "server" badge), and nearby Incursions and skyhooks for a Character whose Alerts Grant carries the location (ADR 0028). Everything else needs the app open (`eventRowSupport.ts` `pushBadgeKind`).
3. **How do the poller and push avoid double notifying?** Both compute the same Occurrence Key; the poller checks the feed row (`notifiedHereAt`, dismissal, 24 h age) per fire before writing its own row (`foregroundPoller.ts` delivery loop; decision `20260925-112832`). A feed row synced from another device does not suppress this device's toast.
4. **Why does a mute in Alerts affect Settings?** Mute is the feed-channel flag for that type per Character; the page and the Settings "Alerts" column are one setting, synced (`setFeedMutedForCharacters`).
5. **What is synced and why not the rest?** Feed toggles and thresholds only; the browser half and master are tied to this device's permission (`syncedPreferences.ts` header).
6. **What does the backend receive?** FCM token, device id, per-Character short-lived access token and rendered projection rows; never a refresh token (`deviceRegistration.ts:205-250`, CLAUDE.md rule).
7. **How is Scheduled Push kept honest?** Wording hedges for 8 events that a normal in-game action falsifies; projection rows are replaced wholesale each rebuild; unprojected domains and disabled events upload nothing; EVE types are filtered by allow-list (`projection.ts:102-140`, decision `20260907-114310`).
8. **Why default Device off for some events?** `feedOnly` events (order fills, contract completed/failed, wallet) are durable-record value, not interruption; courier forfeits are irreversible so a popup adds little (`events.ts` trait comment, issue #1091). EVE types default feed-on/device-off except loss/attack/kick (`eventSelection.ts`).
9. **What happens when permission is denied?** Browser channel disabled everywhere; feed channel and Alerts page keep working; poller keeps filing feed rows (`NotificationsPanel.tsx` browserBlocked comment). Play Store app points to Android settings.
10. **How are 300+ alerts bounded?** Trim to newest 300 on write excluding the just-written ids; sync window 100 rows/30 days (`feed.ts`).
11. **What does the alert link do for an alt?** `?character=<id>` -> `AlertCharacterSwitch` switches the active Character, strips the param, shows a status line for 5 s (`AlertCharacterSwitch.tsx`).
12. **Why does the poller skip a domain?** If no event it could fire is both in scope and enabled on some channel, it is not fetched at all (saves ESI budget), and a truncated or failed load keeps the last good baseline (issue #1248).
13. **Tab-leader semantics?** Only the leader tab polls. The poller's leader keeps its lock while hidden, and a tab being shown steals it, so a visible tab wins over a hidden one; a hidden tab leads only when nobody else does. How long a hidden page keeps running is up to the browser (Android Chrome throttles and then freezes it within minutes); push covers a closed app (`lib/tabLeader.ts`, glossary Tab Leader).

## Observed gaps

- Wording drift: the channel is called "Overview notifications" in Settings (`feedChannelLabel`, hint "A dismissible list on the Overview page") and column "Alerts", while the list now lives on `/alerts` (Overview shows a summary column).
- Settings hint says "These choices stay on this device" (`settings.notifications.hint`) although feed toggles and thresholds sync.
- No quiet hours / do-not-disturb, no per-event sound, no snooze (inferred from absence in `src/features/notifications`, not from a statement in code); "Dismiss" is the only state, no "mark read".
- Mute and dismiss are per type or per fire; no "dismiss older than"; muted types still accumulate rows (up to 300).
- Alerts severity table is hard-coded (verified `alertGroups.ts`) (`alertGroups.ts`); an unknown EVE type is `watch`; `critical` exists only for EVE structure/orbital/kick types and `mercenaryDenReinforced`.
- `spExtractionReady` is opt-in via a separate setting that is not on this panel (`sync.spExtractionMonitoringEnabled`).
- newCalendarEvent/marketOrderFilled/undercut/wallet/contract events cannot arrive with the app closed.
- A hidden leader polls only as long as the browser runs the page: minutes on Android, not hours (issue #5120). Browsers without Web Locks make every tab a leader, so every open tab, hidden or not, polls.
- iOS needs install-to-home-screen before any push; the explainer hides Enable there.
- Corp events are best-effort by design and need roles; missing role cannot be fixed from the app (hint text `corpCapabilityHint` verified; "best-effort" behaviour is from copy, inferred for actual poll reliability).
- Scheduled push registration depends on Firebase config (`VITE_FIREBASE_VAPID_KEY`); failures only log to console (`webPush.ts`, `projectionUpload.ts`), with no UI.
- (Verified `pushHandler.ts:handlePush`) Faulty/blank-title push payloads fall back to a generic notification with no feed row.
- Alerts page has no keyboard shortcut beyond global `A` (verified in `SHORTCUTS`), and no pagination: all rows (<= 300) render grouped (inferred from `Alerts.tsx` having no paging code).
