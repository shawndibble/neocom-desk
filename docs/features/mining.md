# Mining

Route `/mining`. Two tabs. Overview = personal mining output (ISK, ISK/day, m3, raw vs refined), all ore/ice/gas, last 90 days kept on device. Tax = Moon Mining Tax ledger: moon-ore sessions you owe rent on, to whom, how much, paid or not. Internal names stay `MoonMiningTax` / `miningTax` (decision `20260905-215631`); user-facing label "Mining" (nav key `nav.miningTax`).

User goals: Overview = "what did I mine, what is it worth, ISK/day". Tax = "never miss an alt's obligation, bill each landlord the right amount at the right price, know what is paid".

## Purpose and user goal

"What did I mine, and what do I owe each landlord?" Overview is the default tab (`20260924-202220`); Tax exists because a renter mines several corporations' moons, owes each a different percent, and had no way to see what is owed to whom or whether it is paid (#523, `20260905-170644`).

- **Top jobs (ranked):** 1. "What did my Characters mine, and what is it worth per day?" (Overview). 2. "What do I owe each Payee, and what still needs assigning or review?" (Tax). 3. "This payment arrived or went out: which entries does it settle?" (Settle up, link payment).
- **Device and cadence:** desktop primary, with the EVE client open beside it (owner, 2026-10-11): Tax bookkeeping is a desk session (multi-select, Split, Combine, link dialogs), and the payment copy buttons (amount, "to" name, reason) and "How this was priced" Copy as text go into the client. Phone parity: #2148 adds a phone sort to the Tax table. Overview cadence: after a mining session; Tax: when billing or paying a landlord.
- **Above the fold:** Overview: ISK, ISK/day and m³ tiles, then the chart. Tax: Owed balances per Payee and the attention strip (needs review, unassigned), then the ledger.
- **Not for:** field progress during an op (Survey tab, `mining-survey.md`); per-moon observer data in the personal tabs (needs the moon owner's Accountant role, `20260905-170644`); a corporation that wants it runs the Corp Tax Book (below, `/corp/moons`).
- **Sources:** owner, 2026-10-11 (desktop primary, phone for one-off lookups); `20260905-170644`, `20260924-202220`, `20260906-132251`, `20260909-204328`, `20260922-204846`; #523, #2148, #3121.
- **Unconfirmed:** cadence for both tabs; that Overview, not Tax, is the more visited tab.

### Mobbin brief

- **Fit:** high for Tax (balances, ledger, settle up), medium for Overview (earnings dashboard); ore pricing and refining are EVE-specific.
- **Analog apps:** Splitwise, Copilot Money, QuickBooks, Robinhood.
- **Screen queries:**
  - `web: balances owed to several people as cards with a settle-up button, above a ledger table of dated entries with paid and unpaid status`
  - `web: earnings dashboard with total, per-day rate and volume tiles above a bar chart by day and a table of entries`
  - `web: table with row checkboxes and a sticky bulk-action toolbar for assigning selected rows to a person`

- **Mobbin won't help with:** ore refining value, price-source tags, splitting one ESI ledger entry by quantity.

## 3. Overview tab

Purpose: output stats. All tracked Characters (not just active). Files: `OverviewTab.tsx`, `yieldSnapshot.ts`, `ledger.ts:141 loadAllCharacterYields`.

Load (`loadMiningYieldSnapshot(showRefining, compressed)`, `yieldSnapshot.ts:158`):

1. Per Character ledger (fan-out at `ESI_FANOUT_CONCURRENCY`), merged into device history, grouped by (date, system) over harvested set = ore + ice + gas clouds + manual moon tags + manual ignores (`groupMiningYield`).
2. Pricing type per ore = Compressed counterpart when Ore Form = Compressed and one exists (`oreFormTypeId`, `src/engine/miningTax/oreForm.ts:7`). Gas prices as itself.
3. If Show refining: load reprocessing recipes (`loadReprocessing`), Character modifiers (skills, implants). If off: skip recipes, material prices, skills/implants.
4. Server hub-station Open Prices (R2, `open-prices/<typeId>.json`, one read per priced type): each day's closing Jita 4-4 best buy and best sell. A type with no object prices as nothing.
5. Live Jita book from Fuzzwork for every priced type, for today/yesterday before the day is published and for the "now" bases. Nothing is saved on the device (decision 20261019-131707).
6. Every row valued on all four bases up front (`byBasis`), so switching basis never refetches.
7. Volumes: SDE, else live ESI `getUniverseType`, cached `STALE_AFTER.static`; a confirmed `null` volume is also cached.

Overview always prices at Jita (`DEFAULT_TRADE_HUB`); Tax prices at the Payee's hub.

### Formulas (exact)

- Range window: today counts as day 1; `7d` = today + 6 prior days; start = today - (days-1); dates are bare UTC strings, never routed through local time (`yieldRange.ts:30`). No "All" range: history caps at 90 so it would equal 90d.
- ISK per mined day = sum of raw value of in-range rows / count of DISTINCT dates with any mining; null when no dates (`yieldRate.ts:13`). It uses raw (sell-the-ore) value, not refined (`OverviewTab.tsx:294`). Days with no mining are NOT in the divisor. Why: ESI has no intra-day timestamp so no hourly rate is measurable; originally calendar hours (`20260909-204328`), later per-day (`20261006-085420`).
- Days mined tile: `daysWithData / rangeDays`; "history starts" hint when the oldest saved day is later than range start (`yieldRange.ts:64`).
- Raw value per line = unit price x quantity; price must be > 0 else the line is 0 and the row flips `pricedAll=false` (`yieldValuation.ts:101`).
- Refine value per line: `batches = floor(units / portionSize)`; each material `floor(materialQty x batches x efficiency)` (floored per material, as the game does; no invented fractions); leftover units `units - batches x portionSize` are shown, not rounded away (`reprocessing.ts:108`). Missing recipe while refining is on => `pricedAll=false`. Unpriced material => value is a floor, `pricedAll=false`.
- Efficiency (`reprocessing.ts:68`): ore/ice/moon ore = `0.5 x (1 + 0.03 Reprocessing) x (1 + 0.02 Reprocessing Efficiency) x (1 + 0.02 specialisation) x (1 + implant%/100)`; scrap = `0.5 x (1 + 0.02 Scrapmetal)` only. the 0.5 is the pilot's Facility Yield (`refiningSetup.ts`; default `BASE_STATION_REPROCESSING_RATE = 0.5`), never clamped to 1; the Reprocessing Tax comes off each refined value as an ISK fee (`netOfReprocessingTax`). RX-801/802/804 = +1/+2/+4% (best fitted, `characterModifiers.ts:60`). Example, all skills V, specialisation V, no implant: 0.5 x 1.15 x 1.10 x 1.10 = 0.69575. Per-line efficiency uses the type's own specialisation; the "basis hint" states a baseline without specialisation (`baselineRefiningEfficiency`).
- Buyback: every ISK figure (entry and line totals, material unit prices) x `rate/100`; quantities, `pricedAll`, efficiency, batches are not scaled (`buybackRate.ts:25`). Valid: finite, `0 <= rate <= 100`.
- Price resolution per type per day (`priceBasis.ts:69`): "now" bases = live price of the chosen side only (none => unpriced). Mined-day bases: the day's Open Price (chosen side, at the station) -> live, but live only if date >= yesterday (an older day with no price = type did not trade, stays unpriced). A price must be > 0.
- No price-source tags: every day prices from one source, so the table, chart and CSV say only Full / Partial pricing (`pricedAll`). The row detail's "How this is priced" names the chosen basis and buyback rate (`basisPriceHint`).
- Per-type chart: top 8 by value; the rest fold into "Other N types" only when there are more than 9 types (`MiningYieldCharts.tsx:54`, `topTypes.ts`: `sorted.length <= limit + 1` => no fold). Daily chart axis includes days with no mining.
- Ledger history merge (`ledgerHistory.ts:27`): a fresh row replaces a stored row with the same (date|system|type) (today's quantity grows through the day); rows only stored are kept; duplicates inside one fetch are summed first; prune counts back from the NEWEST held day, not the wall clock (`LEDGER_HISTORY_DAYS = 90`, cutoff = newest - 89). A cached copy older than the last merge is ignored so it cannot roll today back (`ledger.ts:50`).

Each table has CSV/clipboard export.
- CSV (`yieldCsv.ts`, surface `mining-overview`): every column the table can offer, not just visible ones.

## 4. Tax tab

Purpose: Moon Mining Tax. All tracked Characters by default. Files: `TaxTab.tsx`, `snapshot.ts`, `ledgerActions.ts`, `assignments.ts`.

### Entities (GLOSSARY.md)

- Mining Ledger Entry: (Character, EVE date, system) with moon-ore lines summed per type; derived each refresh, never stored (`groupLedger.ts`). Moon ore = SDE moon set + manual "tag as moon ore"; ordinary ore/ice/ignored are excluded (that exclusion is the whole moon filter).
- Assignment: stored record claiming (part of) an entry for a Payee at a tax %: `oreLines` snapshot, `estimatedValue`, `taxOwed` (both snapshotted), `status`, optional `groupId` (combined), `collectsGrowth`, `payment`, `reviewDiff` (`src/db/index.ts:659-700`).
- Payee: per-Character free-text landlord with default tax %, Trade Hub (priced at that hub, default Jita; `20260907-100006`), legacy `systemId`, learned in-game entity id (`rememberPayeeEntity`), optional `entityKind` (character|corporation|alliance) set from the Name search (`PayeeNameField`, `payeeEntitySearch.ts`) or an exact-name lookup on save (`20261014-130951`); unmatched names stay unverified labels; Settle up shows Open in EVE (from the payer) under "To".
- Statuses (`rowStatus.ts`): unassigned, outstanding, paid, needs-review, dismissed. Open = unassigned + needs-review + outstanding (`ledgerSections.ts:3`); History = paid + dismissed.

### Load pipeline (`snapshot.ts:66`, order matters)

1. Hydrate Ore Form. 2. `loadAllCharacterLedgers` (also computes unclassified types = ESI types neither moon, ore/ice, nor ignored). 3. `recordLedgerArrivals`. 4. `coalesceAssignments` (repair Combined Entry invariants before reconcile). 5. `reconcileAssignments`. 6. `repriceForOreForm`. 7. Load Payees and Assignments (after reconcile so flips show). 8. Build rows with `computeOwnership` + `findDuplicateAssignmentIds`.
   Data Age badge = oldest `fetchedAt`; `fromCache` true only if every read was cache-only (offline).

### Pricing for Tax (`pricing.ts`, `priceBasis.ts:125`)

- Value = sum of quantity x unit price; tax owed = value x taxPct/100, computed ONCE at assign time and stored (`valuation.ts:28`). Later price moves or Payee default edits never change it. Example: 1,000 units x 5,000 ISK x 10% = 500,000 ISK.
- Unit price tiers, buy side only: the hub station's Open Price for the mined date -> today's live buy (unconditional on date: deliberate difference from Overview) -> today's live SELL as last resort (flagged `live-sell`, softer "priced at today's sell" notice) -> none (0, "could not be priced" banner). A quoted 0 counts as unpriced.
- Priced at the entry's mined date and at the Payee's hub (`hubForPayee`; absent/unknown hub = Jita). Why: `20260926-112731` (a bill created a month later must not use today's price), `20260906-081307` (compressed ore at Jita buy), `20260926-142542` (bid-less ore at sell).
- Ore Form: Compressed (default) values and names the Compressed type when one exists, else raw; gas untouched (`20261006-185915`). Flipping re-prices Unassigned and Outstanding only (`oreFormReprice.ts:19`); Paid, Dismissed, needs-review stay frozen (frozen ISK is truth). A record with an unpriced line is skipped and retried next load, never zeroed.
- Per-ore value editing (setting "Edit ore values individually"): `oreLineValues` replaces `quantity x unitPrice` for the named lines; unnamed lines still price from the book (`valuation.ts:28`, `20260927-105434`).

### Ownership, growth, review (core engine)

- `computeOwnership` (`ownership.ts:60`): per ore type residual = entry qty - sum of covering Assignments' qty. Growth collector (`growthCollector`) = the sole Assignment, or the one flagged `collectsGrowth` when 2+; a collector owns all residual (nothing becomes "unassigned", no other Assignment grows). With 2+ and no flag (legacy split): a type claimed by exactly one Assignment grows into it; a type claimed by none or 2+ stays an Unassigned residual. A PAID Assignment never grows (ADR 0024, D23): residual that would go to it stays Unassigned, so late ore after payment is its own assignable row for the same day and system (split sides and combined members alike). Snapshots never shrink.
- Late ore on a paid day: assigning it (`createAssignment`, or a new member in `joinAssignments`) moves `collectsGrowth` to the new Assignment when the entry's collector is paid (only the flag changes on the paid record), so the rest of the day folds into that one unpaid row (`20261018-143631`).
- `diffAssignedOreLines` (`needsReview.ts:15`): reports only types whose quantity strictly GREW (a new type counts as growth from 0); equal or lower never flags (false positives on real ISK are the worse failure).
- `reconcileAssignments` (`reconcile.ts:40`): per Character, diff each Assignment against its owned fresh lines. Entry absent from the fresh read (aged out, or lapsed grant) -> left alone. Growth on an OUTSTANDING Assignment (single, or member of a combined entry) is absorbed straight in (re-priced at mined date and Payee hub, `planNeedsReviewResolution`, `assignments.ts:675`); if re-pricing throws it falls back to flagging. Growth on Dismissed flips to `needs-review` with `reviewDiff` {typeId, before, after}. Paid never flips: ownership never grows it, so its status, ore and tax stay as paid and the extra ore is Unassigned (ADR 0024). A paid Assignment an earlier version already flipped keeps its review. Skips the write (and `scheduleSync`) when the diff is unchanged. Why: `20261004-135551` "unpaid growth has no history to protect".
- Accept new total (`planNeedsReviewResolution`): re-snapshots ore to owned fresh lines, re-prices, clears `reviewDiff`, `paidAt`, `oreLineValues`, and reverts to `outstanding` EVEN IF it had been paid (never under-states; a payee who already covered part is one "mark paid" from square).
- Duplicates (`ownership.ts:137`, decision `20260923-112236`): flagged only when identical Payee, tax % and ore lines AND the covering set together claims more of some type than the entry holds. Dismissals never count. All members returned. Shown in the Attention strip.
- `assertUnclaimed` (`assignments.ts:59`): inside the write transaction, re-reads Dexie; refuses (`AlreadyAssignedError`) when requested + already claimed (dismissals included) of a type exceeds the entry quantity; with no entry lines, any second claim refuses. Covers two tabs/devices racing.
- Split (`split.ts:17`): `planSplit` throws if a move exceeds held qty (no silent clamp); zero moves dropped; kept lines at zero dropped. `splitAssignment` throws "Nothing to move" or "Cannot move every unit - unassign instead". Each side priced at its own Payee's hub. Split is not offered on combined members.
- Coalesce (`coalesce.ts:135`): fuses only `outstanding` Assignments with no payment on the same entry with the same terms (payee:taxPct); refuses when members span >1 existing groupId; identical members that over-claim = duplicate (keep one, values NOT summed), else quantities and values summed. `planGroupEjections` (`coalesce.ts:213`): a Combined Entry whose members disagree on terms ejects the disagreeing ones (all when fewer than 2 agree). Safety net only; writes already keep the invariant.

### Combined Entries

- One obligation, one Payee, one rate, spanning EVE days (sessions crossing 00:00 UTC). Rules in `selection.ts:77 combineEligibility`: need >= 2 rows; same Character; same system; at most one distinct `groupId` (one group + ungrouped rows = add to that group); same Payee and rate across every member (`agreedTerms`). Blockers `too-few | mixed-character | mixed-system | multiple-groups | mixed-terms`, each with its own reason text.
- Combined row: "N days" toggle, summed values, date range; status = worst member status. Settle up expands to actually-outstanding members only (`settleUpMembers`) so an already-paid member is not billed twice.
- Take out (one day) / Uncombine all clear only `groupId`; figures and payment stay (`uncombineAssignments`).

### Continue a session across midnight UTC (`sessionContinuation.ts:39`)

Offered when a wholly unassigned entry has the same Character + system on the EVE day immediately before, and that day has exactly one non-dismissed Assignment that is `outstanding` with a Payee (paid = closed session; split day = no single Payee). Continue: assigns next-day ore to the previous Payee and rate, combined with previous (or added to its group); next day priced at the Payee's hub. Undo (toast) re-reads both records inside the transaction and keeps changes since; if previous was already combined, undo leaves it combined (`ledgerActions.ts:189`). Auto mode (device `miningTaxAutoContinue`) continues each new offer once; dismissals stored per next-entry key (`miningTaxDismissedContinuations`); card also offers "choose other" (opens detail) and "keep separate".

### Settle up (`SettleUpDialog.tsx`, `settleAllocation.ts`)

- Two steps: no wallet-journal link step because ESI's journal lags too far for a just-sent payment (`20260911-210622`). A recorded-but-unlinked payment is auto-matched later (`paymentLinks.ts`, no dialog).
- Paying from (`settlePayer.ts`, `20261021-202639`): entries spanning Characters get a "Paying from" picker with subtotals; only the payer's entries start ticked, others under "Also pay for other characters". Default: a row's own Character with only that entry ticked (rest under "Also pay N other entries"); a balance card or selection uses its one Character, else the active one if it has entries, else the most owed. Open in EVE sits on its own row and sends from the payer.
- Items ticked per Payee (multi-Payee supported); copy buttons (amount, "to" name, reason text from systems and dates); paid-on date; method; contract id; "Pick from wallet" (made payments); primary "Record payment", secondary "Just mark paid".
- "I sent a different amount" (`allocateOldestFirst`, `settleAllocation.ts:27`): sort ticked entries by date ascending; accept each while `coveredTotal + taxOwed <= amount + 0.5 x (n+1)` (cumulative half-ISK slack per accepted entry: transfers are whole ISK, stored tax is not); STOP at the first that does not fit (never skips to a cheaper newer one); leftover = `max(0, amount - coveredTotal)`; non-finite or <= 0 amount covers nothing. Example: owed 100M (day 1) and 50M (day 2), sent 120M => day 1 covered, leftover 20M, day 2 stays owed. An Assignment is paid or owed, never half.
- Ore still arriving (`oreArrival.ts`, `20261004-213852`): `ARRIVAL_WINDOW_MS` = 1 hour (ESI's longest ledger lag). An entry's day is in-window while `dayStart + 24h + 1h > now` (`isInArrivalWindow`). `recordLedgerFetch` stamps `grewAt` when a fetched total exceeds the stored total (first sight counts as growth only if this Character was checked since that day began; non-increasing `fetchedAt` is ignored). `arrivalNotice`: `arriving` while `now - grewAt < GROWTH_WAIT_MS` = 50 min (1 h longest lag minus 10 min shortest: ore just seen was mined at least 10 min before; yellow "wait ~N min", never more than 50; only ticked entries count), `quiet` (small print "ESI can lag up to 1 h"), `none` (day ended > 1h ago). Never blocks. Dialog re-pulls the ledger on open and every 10 min (`RECHECK_INTERVAL_MS`) while an entry could still grow; "Checking ESI..." / "Couldn't check ESI" states.
- `settle` marks paid and stores `payment` info in one Dexie transaction.

### Made payments and links (`madePayments.ts`, `paymentMatches.ts`, `paymentLinks.ts`)

- Sources: wallet journal outgoing amounts (amount < 0, absolute value) with ref_type in `player_donation, contract_price, contract_price_payment_corp, contract_deposit` (contract refs = method contract, else donation); completed item-exchange contracts issued by the Character with price 0 and assignee != 0 (payment in kind; amount null, never priced from cargo, pilot confirms). Each Character's reads fail independently (`.catch(() => null)`); results newest first; counterparty names via `resolveNames`. Scopes: wallet journal + contracts, ungated.
- Matching: `amountsMatch(a,b)`: `|a-b| <= max(1, 0.005 x b)` (0.5% or 1 ISK); `LINK_WINDOW_DAYS = 14`, asymmetric (payment after mining; an entry dated well after the payment is no match). Suggested Payee: `suggestPayeeForSystem` pre-selects the Payee of the most recent non-dismissed Assignment in that system (date, then `updatedAt`), ranks others by use count then name; legacy `systemId` only breaks ties with no history (`suggestPayee.ts:40`).
- Link transaction attaches a reference to an already-paid row; never changes status or amount; exact-ISK match preselected "Suggested". Link wallet payment = reverse flow from the Wallet side.

### Corp Tax Book in the Tax tab (#4065, D12, D24, D28, D30)

Only when a tracked Character's corp has an active Corp Tax Book (a `get` of `corps/{corp}`; a corp the Character left stays readable, remembered in the `corpTaxBookCorps` setting). No book, or any failed read: the tab is exactly as above. `useCorpBookView` reads the member's own lines (`uid`/`uids` rules) as each Character in turn, prices them at the book's hub and Ore Form with the tab's own loaders, and `overlayCorpBooks` (`src/engine/corpTaxBook/personal.ts`, pure) decides each day:

- **Pending corp record**: the day is not Billable (day end + grace, then an officer sync) or has no rate. A relabel of the unassigned row; the member's own allocation applies and nothing is owed to the corp.
- **Billed**: Billable. The book decides quantity, price and rate for exactly what it observed; an issued Statement's lines are that decision, frozen. The row is owed to the virtual "<Corp> (Corp Tax Book)" Payee (display-only, never in Dexie, never offered to Assign) and takes its ore from the member's unassigned ore.
- **Paid**: the Statement's settlement (`allocatePayments`); a part payment lands on the oldest days. A `player_donation` in the member's wallet journal to the corp that the book does not hold yet (matched by sender, amount and time) also pays the oldest Billed days, as does credit the book holds for no Statement yet (so a day stays Paid once the book credits the donation that paid it): the member's side is done, and a corp that disagrees bills them again.
- **Conflict**: ore the member gave another Payee that the book also observed. Visible, not owed; resolves to the corp 14 days after the day closed.
- **Unattributed**: free ore no book claims on a closed day; owed to no one. Several books in one system on one day split the entry by observed quantity.
- **Dismissed by corp**: shown with the officer's reason; owes nothing.

Row detail adds the locked terms, the rate and its effective date, and "Disputed: you 10%, book 15%" with "Compare with the book" (a modal, D28). Under the balance card, `CorpBookSyncNote` prints "Safe to pay — 12 Jul is closed (Corp synced 2h ago)" or "Safe to pay once Corp syncs (last synced 2d ago)". "Settle up" for the corp Payee is `CorpPayDialog` (what to send and where; the corp's book credits the donation itself). A donation the book could not match shows in the attention strip with **Claim**, which calls `claimCorpTaxBookPaymentCallable` (uid-authorised, audited as `claimPayment`, credits the Miner the Character is grouped into).

The book's observed rows may carry optional `solarSystemId` and `moonId`, set by the syncing officer's client: the personal ledger knows only the system, so without it a row is lined up by character and day (several systems that day: the one sharing most ore) and per-moon rates cannot be resolved by a member.

## Corp Tax Book (#4055, ADR 0023, ADR 0024)

The corporation's side of the same tax. A **Corp Tax Book** records, for one corporation, what every character mined at its refineries, what each **Miner** owes, and who has paid, from the refinery's own ledger instead of anyone's personal one. Officers run it at `/corp/moons`; corp members see it as a row type in the Tax tab (subsection above); anyone mailed a **Statement** reads it on a no-login verify page. The numbers are one engine: the book prices ore like the Tax tab (buy side of the Compressed counterpart at the mined date, at the book's hub), so a member and their corp reach the same tax. Code: engine `src/engine/corpTaxBook/` (pure), officer sync `src/features/corp/taxBook/`, page `src/features/corp/moons/`, mail queue and verify page `src/features/corpTaxBook/`, member overlay `src/features/miningTax/corpBook/`. Storage and callables: `docs/ARCHITECTURE.md`. Decisions D1-D31: `docs/context/decisions/20261018-1344*.md`.

### Officers: `/corp/moons`

Route `/corp/moons`, tab "Moons" in the Corp sub-nav (`docs/features/corp.md`). The entry shows to every Character whose roles can view the book (D8: CEO, Director, Accountant, Junior_Accountant; `canViewCorpTaxBook`), whether or not the mining scope is granted or a book exists (`20261018-172958`). Edit actions follow the server's `canEdit` (CEO, Director, Accountant). Page states, in order:

- **Roles too low**: "Moons need the Accountant role".
- **Scope missing**: "Allow mining ledger access" asks for `esi-industry.read_corporation_mining.v1`. The scope is additive, so an old grant keeps working elsewhere.

A newly turned-on book is hidden from members' own Mining Tax pages for 72 hours (`membersSeeFrom`) so officers can set it up first.
- **Book on**: five tabs (Overview, Extractions, Miners, Statements, Moon owners); **Needs you** sits on Overview. A sync-age badge beside the page title says how fresh the book is (hover for who synced it); the health strip below the tabs shows warnings only. Settings (gear) and Activity open from the page header. Tab and drill-downs are URL routes: `/corp/moons/overview`, `/corp/moons/extractions`, `/corp/moons/extractions/<id>`, `/corp/moons/miners`, `/corp/moons/miners/<id>`, `/corp/moons/statements`, `/corp/moons/statements/<periodStart>` (an issued period's page), `/corp/moons/moon-owners`. `?statement=<id>` opens one Statement's panel on a period page or a Miner's page (a bad id shows "Statement not found" and is dropped; closing the panel replaces the history entry).

Every scalar column sorts, and a paged section sorts the whole list before paging. Multi-value cells (ore lists, a payment's Credited to) are not sortable.

**Turning on and access.** Opening the page verifies the officer: the client sends its short-lived EVE access token (never the refresh token) and the server reads the Character's corporation and roles from ESI, then keeps an access record that lapses after 24 hours. Accountant, Director and CEO can use the page and edit. A write that waives or removes money (dismiss, reverse a dismissal, write-off, rebill, mark not tax) re-checks the role live with the token again; an expired record is renewed on the next visit.

**Sync on visit, gaps, health.** Visiting the page syncs the book from this officer's client (`syncCorpTaxBook`), unless anybody synced in the last 15 minutes (ESI caches these endpoints for an hour); **Sync now** forces it. A sync reads the refinery observer ledger (Athanor and Tatara only; a Metenox has no ledger), the corp's Extractions, the moon notifications and the journal donations of the chosen wallet divisions, uploads them, then settles the Statements the engine reports paid. Ledger rows are upserted by miner, ore, day and refinery and are monotonic: quantity never goes down and an older ESI cache is ignored. The sync age shows as a badge beside the page title ("3d ago", hover: "Synced by <officer>", or "Synced by Scheduled sync (<holder>)" when the 6-hourly Automatic sync made it). The health strip (`BookHealthStrip`) prints only what needs attention:

- A stale warning, "Synced by <officer> 4d ago — the book is going stale", after about 3 days (a fresh sync says nothing here); "Never synced" before the first sync; the failure or skip reason ("Log in again", "The mining scope is not granted", ...); coverage gaps, unrated moons, a stopped Automatic sync.
- Billable through is not here: it is a chip on the Overview tab ("Billable through 12 Jul"; hover: day end + 30 min grace by default, then a sync).
- **Gap: 3-5 Jul, <refinery> — unrecoverable** when no sync reached a day before ESI dropped it. The horizon assumes the ledger keeps 30 days (the corp's claimed 90 is unconfirmed) and moves back if ESI returns an older row (`20261018-162604`). The day of the last sync counts as lost too, since a day's quantity keeps growing. Gaps are carried into every later sync. Donation history gaps are not reported.
- "N days have no rate yet" until a corp default rate exists; those days are not billed.

**Extractions tab.** One chip (estimated value in chunks still minable), state filter chips (Fractured, Ready, Extracting, Expired, Cancelled when the book has one; default Fractured, Ready and Extracting, Expired off; a count is every Extraction in that state; a phone gets a checkbox list), a timeline (Extracting, Ready, Fractured and minable, Expired; a row opens the moon's page; hover a bar for the extraction window) and a table of refinery, state, when, ore, estimated value and mined vs left. The chips filter the timeline and the table together (the timeline also stops at 20 days back). Lifecycle: Extracting until `chunk_arrival_time`, Ready, Fractured (laser fired, or `natural_decay_time` auto-fracture), Expired at fracture plus 48 hours (per-structure override up to 4 days, in Settings). Ore and ISK come from the ExtractionStarted notification; without it the row says "Ore unknown — link a survey". The drill-down (`MoonDetail`) shows this extraction's timestamps, ore source, who mined the chunk (units, value, tax), the moon's past extractions, and **Dismiss tax for this extraction**.

**Overview tab (#5247, the default).** The book's totals, **Needs you** (declarations, overdue, unmatched donations, leavers; each card keeps its primary action as a button and the second as a text link; a card's title links to its Miner's page) and the moons worth a look: **Fractured** (mineable, field going), **Ready** (mineable now), then **Pops in the next 7 days** (Extracting moons whose chunk arrives within a week). Every Extraction stays on the Extractions tab. Pure grouping: `src/engine/corpTaxBook/bookSections.ts`.

**Miners tab.** One row per Miner: standing (Member, Guest, Left corp), owed, overdue (days), Next Statement, credit, last paid. Overdue first. Search, and Members / Non-members filters (members by default is the point of D2: guests are billed too); a Miner who owes nothing and holds no credit is folded into a count. A Miner's page (`MinerDetail`) is one scroll, no inner tabs, each section titled with its count and paging its newest ten rows with **Load older**: **Today's mining** (days that are not Billable yet; its info icon says when today ends, day end plus the book's grace), **Next Statement** (Billable days not on a Statement yet; select days to **Dismiss selected**), **Earlier days** (on a Statement, Paid, Dismissed, Written off), **Payments** (donations and hand-recorded, each with **Mark not tax**, and the correction lines given, as a kind of row in the same ledger; its ⋮ holds the corrections below), **Moons** (a row opens to that Miner's ore lines there) and **Activity** (mail, dismissals with **Reverse**, and the audit log, behind filter chips All, Mail, Dismissed, Audit). The header carries owed, paid, credit, Next Statement, Today's mining, Written off and the **N characters** link opening the characters popover. The Payments foot keeps the sum line "Statements - written off - payments and dismissals = owed". Written off shows two things apart: what payments within tolerance left over, and lines "Recorded after payment", which are never billed (a paid Statement's days are closed for good, D22). A moon's page lists who mined it, each row opening to that Miner's ore lines (ore, amount, estimated value, tax, total) and one **Open miner** link.

**Automatic sync (#4068, ADR 0025).** Settings has an **Automatic sync** section. A CEO, Director or Accountant turns it on for their own Character: a second EVE login for a narrow set of scopes (the mining ledger, the corporation wallet, notifications, the Character's corporation roles and structure locations), whose refresh token goes to our server and never to this device. One holder per corporation, so a new opt-in replaces the old one. Four times a day (00:35, 06:35, 12:35, 18:35 UTC) the server (`syncCorpTaxBooks`) runs the same pipeline as a visit: it re-checks the holder's roles with their own token, syncs the observer ledger, Extractions, moon notifications and donations, detects gaps, re-matches Unmatched donations and settles the Statements the donations now cover. It **never issues a Statement or sends mail** and does not group an officer's own Characters (that needs their device). Each run writes the same last-sync line ("Synced 2h ago by Scheduled sync (<holder>)") and audit entries marked "scheduled sync". The holder can turn it off, and so can the CEO for anyone; turning it off deletes the stored token. If the holder loses the role, leaves the corporation, or the authorization is revoked or expires, the schedule stops, the token is deleted and the health strip says "Automatic sync stopped: <why>" until someone turns it on again. A run that only hit a transient failure (EVE unavailable, error budget) is skipped and the schedule stays on. Server code: `functions/src/corpSyncGrant.ts` (grant custody and the run loop), `corpTaxBookScheduledSync.ts` (one book's pipeline), `corpTaxBookSyncEsi.ts` (the ESI reads); the pure half is mirrored in `corpTaxBookSyncEngine.ts`. Client: `AutomaticSyncSection`, `features/corp/taxBook/syncGrant.ts`.

**Grouping and corrections (#4194, #4200).** The Miner's page has a **N characters** link opening a popover (who is main, who is waiting for a guest's confirmation, Make main, Unlink) and **Group with**, one audited `regroupMiner` edit that keeps the target's id so its Statements stay with it (plan: `src/engine/corpTaxBook/grouping.ts`). A sync also groups the syncing officer's own app-account Characters that are in the corp (D26); EVE exposes no account identity, so other members' alts are grouped by hand, and an Unlink is remembered in the book so no officer's sync regroups it. Grouping a guest's characters waits for the guest's confirmation (`confirmCorpTaxBookGroupingCallable`; there is no screen for the guest to confirm yet). The Payments section's ⋮ holds **Change a day's rate** (a per-day rate override (only for a day not yet on a Statement)), **Add a correction line** (on the next Statement) and **Rebill from date** (never reaches a paid Statement; for corp members it needs a Director). Dismissing several days is one act and the approval limit is checked on the total.

**Survey, leavers, moon names (#4194, #4205).** When no ExtractionStarted notification gave the ore, a moon's page offers **Link a Survey** (by Share Link id, validated by opening it): the first counted scan's composition and a chunk rate give an estimate labelled "Linked Survey (estimate)", and the link survives later syncs. "Left corp" is decided from the public `POST /characters/affiliation`, so non-Directors get it too; a character ESI did not answer for counts as still a member, so a failed lookup never shows a false leaver. **Measured chunk rate (#4070).** Each refinery's real rate is learned, not stored: for every stored Extraction with ExtractionStarted ore, notified m³ (10 m³ a unit) over the hours from start to chunk arrival; the refinery's rate is the median of its last 5 such cycles (`learnChunkRates`, `src/engine/corpTaxBook/extraction.ts`). A survey estimate uses the refinery's measured rate, else the book's manual rate, else 30,000 m³/h; the moon page does not name the rate it used. Settings lists the measured rate and cycle count per refinery. Refineries show the real moon name (`GET /universe/moons/{id}`, cached), falling back to "Moon <id>".

**Needs you.** A queue of what only an officer can resolve: a declared payment (Confirm paid / Reject declaration), an overdue Miner (Send reminder, Dismiss), an **Unmatched** donation (Assign to a Miner, Not tax), and a Miner who left the corp owing (Write off). Overdue is Statement-issue plus the book's days (14 by default), with no interest; a declaration pauses it for at most 14 days, then it resumes on its own (D29), and a rejection gives a fresh 14.

**Dialogs.** Every money action opens a dialog that says it is logged under your name and that your role is checked again. Dismiss (a day, selected days, a Miner, an extraction) takes a reason shown to the Miner and is reversible; above the approval limit it needs a Director. **Record payment** is for ISK the journal cannot show (a contract, another division, a handover); it is credited oldest debt first, an overpayment held as credit. **Mark not tax** takes all or part of a donation (a buyback) and the debt reopens by that amount. **Write off** is logged and does not reopen. **Assign a donation** credits an Unmatched donation to the chosen Miner.

**Statements tab and the run.** The tab lists periods (monthly by default, or every N days) with columns Period, Status, Miners, Billed, Paid, Outstanding, Mailed n/N (Statements mailed at least once, of those issued), Due (the earliest unpaid, unpaused Statement's date, "N days late" in red once past; "Paused · until" when every unpaid one is held by a declaration) and Issued, and the totals written off. An issued row opens `/corp/moons/statements/<periodStart>`: Billed, Paid, Outstanding and one row per Miner's Statement (Due, Mail). A row opens the Statement panel (`?statement=<id>`: Remaining, Credited, Forgiven, Written off within tolerance, Issued, Covers, Due, Mail, the verify page's lines and payments; **Copy verify link** is officer-only and reads the token only on click; **Open Miner page** is absent on the Miner's own page). The row ⋮ holds **Record payment** (credited toward that Statement first) and **Send reminder** for that Statement (capped at one after **Stop reminders**). Figures are whole ISK on screen: a sub-1-ISK credit, remainder or left-over reads as nothing (display only, the stored amounts keep their fractions; `src/engine/corpTaxBook/wholeIsk.ts`). The period run (`StatementRun`) is three steps: **Check** (every day in the period is Billable and priced; Balances due; Miners below the minimum Statement roll into the next period; credit applied; earlier Statements issued but never mailed go with this run; an Unmatched donation is not on anyone's Statement until assigned), **Preview mail** (the real mail for any Miner), **Send** (a notice says about 5 mails a minute, so N mails take about M minutes). Send issues each Statement, which is create-only and never changes, then queues its mail. Corrections and late ore on unpaid days go on the _next_ Statement as labelled lines (forward-only); the balance is Statements - payments - dismissals - write-offs. A payment within max(0.5%, 100k ISK) of a Statement settles it and the remainder is written off and logged. Default minimum Statement 5M.

**Mail queue.** Every Statement goes as one mail per Miner to its main, from the sending officer's character (`esi-mail.send_mail.v1`). The mail is short: per line the date, refinery, value and tax; the total, amount due and due date, the pay code and the verify link (`20261018-161107`, which supersedes D16's full breakdown; the verify page has the detail). Past 10,000 characters it is summarised by day per refinery, then per refinery; total, code and link are never cut. The queue is stored in Dexie (`corpMailQueue`) and one tab works through it under the `neocom:mailQueue` Web Lock at one mail per 12-15 s. It keeps going in a background tab; with every tab closed it waits and resumes on the next open. A 520 MailStopSpamming holds the whole queue for `remainingTime` plus a second; any other failure marks that mail Failed with a reason, **Retry**, and **Open in EVE** (the in-game compose window). The top-bar **Statements** chip shows "N of M sent" on every page and opens the queue. Every mail is logged in the book's audit trail. Reminders are manual, one click per Statement; a Miner who chose **Stop reminders** can be sent only one per Statement.

**Settings** (gear, header). Tax rates: corp default, Guest default, per moon, per Miner; each with an effective-from date and never retroactive; the most specific wins (record, Miner, moon, feeder, Guest, corp). Pricing: trade hub (Jita) and Ore Form (Compressed), both printed on every Statement; no refined value. Billing: start date, grace after day end (6 h), overdue days (14), minimum Statement, cadence, wallet divisions donations are read from (division 1). Extractions: the manual chunk rate (m³/h; the fallback, default 30,000), each refinery's measured rate and the cycles behind it, and field life after fracture. Approvals: the dismissal limit above which a Director must approve (a Director sets it). Editing needs Accountant or above.

**Activity.** An immutable audit feed of everything done in the book (turned on, synced, rate added, payment recorded, dismissed, mailed, ...) with who and when; each Miner's page filters it to that Miner. Nothing is deleted; reversals are new entries.

### Members: the Tax tab

Already covered above ("Corp Tax Book in the Tax tab"): the tab shows a corp member's days as Pending corp record, Billed, Paid, Conflict, Unattributed or Dismissed by corp, only when the member's corp has a book (D24); no book or any read failure leaves the tab exactly as before. Added here:

- **Safe to pay** reads "Safe to pay once <Corp> syncs (last synced 2d ago)" until a sync after the grace period, then "Safe to pay — 12 Jul is closed". A Billed day never changes after it is on a Statement.
- **Unmatched donation.** A donation from a character the book does not know, with no pay code, credits no one. It shows in the attention strip with **Claim**, which runs `claimCorpTaxBookPaymentCallable`: it checks that the donation came from the signed-in Character, credits the Miner that Character is grouped into, and is audited as `claimPayment`. Someone else's donation answers exactly like a missing one. A donation carrying a Statement's pay code is credited to that Miner from any character without revealing any grouping.
- **Paid stays paid** (ADR 0024, D23). A Paid entry in the personal tab never flips to needs-review when ore grows; late ore becomes a new Unassigned entry for that day. In the book, a paid Statement's days are closed: late ore is logged "Recorded after payment" and written off, and "Rebill from date" can never reach it.
- **Leavers.** A member who leaves keeps read access to their own lines; the book remembers the corp for them (`corpTaxBookCorps` setting), and the corp Payee stays with a note. The officers see "Left corp, owes X" and may write it off.

### Guests: the verify page

Every Statement mail carries a link to `/corp-tax-book/verify/:token`. No login and no account: the token is unguessable and maps to one Statement. The page (`VerifyPage`) shows the corporation and period, what was mined (day, ore, unit price, rate, tax; correction and late-ore lines labelled), **Payments credited** to _this_ Statement only (a donation that paid two Statements shows its own part on each), balance due, how to pay (donate to the corporation from any of your characters; the code pins a donation to this Statement), and the **Terms** with dates (rate and effective date, price basis, due date, minimum Statement). Waived and written-off amounts are printed.

- **Stop reminders.** A toggle: the regular Statement still comes, officers may send at most one reminder per Statement.
- **Closed account.** If the Miner's account is closed the page says so and that no more mail will come. An officer closes a guest's account from the Miner's page (**Close account**, guests only; `closeAccount` edit, `src/engine/corpTaxBook/closeAccount.ts`): one transaction issues the optional final Statement and sets `closedAt`. Credit is refunded by default (the officer sends the ISK in game and records it as a payment; the app cannot move ISK); it is forfeited only with a recorded consent note or an \"asked on\" date 90 or more days back, checked on the server and with a live role re-check. Ore on days that are not Billable at the close is never billed. A closed Miner gets no more Statements (`planStatementRun` skips them, `issueStatement` and `setMiner` refuse them); the final Statement is mailed from the Statements tab like any other (`20261018-182323-*.md`).
- A bad or revoked link shows "This link is not valid"; a network failure shows a retry message. Analytics and Sentry log the route pattern, never the token.

## Reconciling with the corp's numbers

An assigned row's detail has a "How this was priced" card (per-ore unit price, price tier, hub, ore form, tax %) with **Copy as text** to paste to the landlord (#2832); unit prices are re-read for the mined date, the total is the frozen bill. The personal tab reads only the Character's own ledger; corp observer data (moon id, timestamps) needs the Accountant role, which a renter lacks. When the landlord corp runs a Corp Tax Book, its numbers appear here directly (see above) and "Compare with the book" shows the difference; otherwise there is no corp-figure import. Likely causes of a mismatch and the fix for each:

| Cause                          | Check                                                                                                                  | Fix                                                                                                                                                                      |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Different price                | Corp may use a different price or hub. App: buy side, mined-date snapshot, Payee's hub (default Jita), Compressed form | Payee hub in Manage Payees (new Assignments only); Ore Form setting; "Edit ore values individually" per-ore values; or edit Estimated Value / Tax Owed in Assign or Edit |
| Different tax %                | Payee default vs corp rate                                                                                             | Edit entry tax %; Payee default only affects new Assignments (tax owed is frozen)                                                                                        |
| Ore arrived late               | ESI lags up to 1 h; arrival notice; late ore on a Paid day shows as a new Unassigned row                               | Assign the new row (Outstanding absorbs growth by itself; Dismissed flags Needs review: Accept new total)                                                                |
| Session crossed midnight UTC   | Two entries, corp bills one                                                                                            | Combine, or Continue card                                                                                                                                                |
| Two landlords, same system/day | One entry, two bills                                                                                                   | Split by quantity                                                                                                                                                        |
| Wrong ore class                | Attention strip "unclassified ore"                                                                                     | Tag as moon ore / Ignore                                                                                                                                                 |
| Old bill missing               | Entry older than 30 days left ESI window                                                                               | None in app; Assignment stays in Dexie but is not shown or counted                                                                                                       |
| Paid but amount differs        | Sent a different amount                                                                                                | Settle up "I sent a different amount" (oldest first, whole entries)                                                                                                      |

Paid stays paid when edited ("correcting isn't un-paying"). Frozen figures: later price moves never restate a bill.

## 7. Interview Q&A

1. **Why can the app not attribute ore to a specific moon or time?** ESI's personal ledger is pre-aggregated to (Character, UTC date, system, type); the observer endpoint that has moon ids needs the Accountant role of the moon-owning corp, which a renter never has. Granularity ceiling is the entry; same-system same-day sessions for two landlords are separated by quantity (Split). `docs/context/decisions/20260905-170644-moon-mining-tax-ledger.md`; `src/engine/miningTax/types.ts:21`.
2. **How is the tax computed and why is it frozen?** `taxOwed = estimatedValue x taxPct/100`, `estimatedValue = sum(qty x unit price)` at the mined date, Payee hub, buy side; stored on the Assignment. Invoice semantics: later price moves or default-rate edits must not restate a bill. `src/engine/miningTax/valuation.ts:28`, `assignments.ts:675`.
3. **What price does Tax use when nothing was captured for a day, or the ore has no bids?** Saved -> live buy (any date) -> live sell flagged `live-sell` -> 0 flagged unpriced. Live is unconditional (unlike Overview) so old never-captured days keep billing as before; sell fallback beats billing 0 for thin compressed moon ore. `priceBasis.ts:125`, `20260926-142542`.
4. **How does Overview pick a price?** Per type per day: the day's closing Jita 4-4 Open Price on the chosen side -> live (only today/yesterday). "Now" bases use live only. No source tags. `priceBasis.ts`, `20261019-131707`.
5. **Why does Overview keep 90 days when ESI gives 30, and what is lost?** The device merges each fetch into `db.miningLedgerHistory`; prune counts from the newest held day so a pause does not erase history; days before the first fetch after shipping are gone, so the Days-mined tile says "history starts". Tax does not use it. `ledgerHistory.ts:27`, `ledger.ts:44`, `20260922-204846`.
6. **What happens when more ore shows up on an already-assigned day?** Outstanding: silently absorbed and re-priced (also combined members). Paid: stays paid; the extra ore is a new Unassigned row for that day and system (ADR 0024), and once assigned it collects the rest of the day. Dismissed: flips `needs-review` with a before/after diff; accepting reverts to outstanding. Only strict growth counts. `reconcile.ts:88`, `needsReview.ts:15`, `assignments.ts:675`.
7. **Who gets new ore when one day has two Payees?** The growth collector: sole Assignment, else the one flagged `collectsGrowth`; unflagged legacy splits grow only into the sole claimant of a type, otherwise the ore sits Unassigned. A paid collector or claimant never grows: that ore sits Unassigned. `ownership.ts`.
8. **How does Settle up handle a partial or odd payment?** Oldest-first, whole entries only, stop at the first that does not fit, 0.5 ISK cumulative slack per entry for whole-ISK transfers, leftover reported. `settleAllocation.ts:27`.
9. **Why does Settle up never block on late ore?** ESI lags up to 1h and has no timestamps; the only signal is a total that grew between two fetches (stored with `grewAt`). 1h window, ticked entries only, recheck every 10 min. `oreArrival.ts:20,71`, `20261004-213852`.
10. **How are multi-record actions kept consistent across tabs/devices?** One Dexie transaction per action that re-reads inside it (`assertUnclaimed`, `undoContinue`, `deletePayee`), sync after commit, `AlreadyAssignedError` -> refresh. `ledgerActions.ts:100`, `assignments.ts:59`.
11. **How is refined value computed and where can it mislead?** Whole portions only, per-material floor, specialisation per line, implant only for ore-like types, an unpriced material makes it a floor (`Partial`); a type with no recipe also flips Partial when refining is on. Overview ISK/day uses RAW value only. `yieldValuation.ts:101`, `reprocessing.ts:68,108`, `OverviewTab.tsx:294`.
12. **Why ISK/day, not ISK/hour?** No intra-day timestamp to measure hours; per-day divides by distinct mined days (zero-mining days excluded). `yieldRate.ts:13`, `20260909-204328`, `20261006-085420`.
13. **What does flipping Ore Form do to existing bills?** Re-prices Unassigned and Outstanding; Paid/Dismissed/needs-review stay frozen; a record that cannot be priced is retried next load, never zeroed. The setting syncs. `oreFormReprice.ts:19`, `20261006-185915`.
14. **What does deleting a Payee do?** Optionally moves owed days plus whole combined entries to another Payee in one transaction; standalone paid days stay as history. `ledgerActions.ts:274-310`, `20261004-141751`.
15. **Why can an old owed bill disappear from the Tax tab?** Rows come only from the 30-day ESI ledger; balances are summed over rows, so an Assignment whose entry aged out stops showing and counting though it remains in Dexie. `snapshot.ts:122`, `balances.ts:36`, `ledger.ts:80`.

## 8. Observed gaps

- Tax rows come only from ESI's 30-day ledger (`snapshot.ts:122`); an owed Assignment older than 30 days vanishes from the table and from Owed balances (computed from rows, `balances.ts:36`) though it remains in Dexie. Overview's 90-day history is not used by Tax (`20260922-204846`: "The Tax tab is unchanged"). Verified contradiction: the comment at `reconcile.ts:76` ("aged out of ESI's 90-day retention") and the `MiningLedgerRow` doc in `src/esi/endpoints.ts:1478` ("90-day retention on ESI's side") say 90 days, but the ledger loader comment `ledger.ts:38-43` and `ledgerHistory.ts:3` say ESI returns only 30 days (the 90 is the device history cap). The behavior in code follows 30 (Tax uses the raw ledger); the two 90-day comments are stale/misleading.
- `/mining` gate lists only `getCharacterMining`; wallet journal/contracts reads for payment suggestions are ungated and fail silently with no in-page prompt (`madePayments.ts` header).
- Overview prefs are device-local (not synced, not in URL); only Character filter and sort are shareable.
- Tax CSV is a fixed 7-column set, no ore or payment-link data; Overview CSV exports every column.
- Ore column in the Tax table is hidden below 87.5rem; ore is visible only in detail there.
- No per-moon identity (ESI limit); same-system same-day separate moons rely on manual Split.
- Overview always prices at Jita and Tax at Payee hubs, so Overview ISK and Tax estimated value can differ for the same ore.
- ISK/day divisor excludes zero-mining days: a sporadic miner reads higher than a calendar-day rate.
- Accept new total on a Paid Assignment reverts it to outstanding and drops `paidAt`/`oreLineValues` (intentional but destroys the paid record).
- "Partial" on Overview is a tag only; no filter for unpriced rows.
