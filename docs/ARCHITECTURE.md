# Neocom Desk — Architecture Map

For agents locating or adding code. Terms match `GLOSSARY.md` — read that first
for glossary (Character, Skill Plan, Build Plan, Remap Marker, etc.). Past
scope decisions (including everything the "GLOSSARY.md round N" comments below
cite) live one per file in `docs/context/decisions/`; `grep` that directory.

## 1. System overview

Neocom Desk is a static SPA (React 19 + TS + Vite) hosted on GitHub Pages —
no app server. Two kinds of data:

- **API-derived** (skills, wallet, assets, mail, ...): pulled live from CCP's
  ESI, cached per-device in Dexie (IndexedDB), never synced.
- **Editable** (Skill Plans, Build Plans, `sync.`-prefixed settings):
  created in-app, synced cross-device via Firebase (Firestore + one Cloud
  Function, `mintFirebaseToken`). Firebase exists _only_ for this sync path —
  it is not a general backend and never sees EVE tokens beyond one
  short-lived access token per sign-in (ADR 0001). The public contract
  snapshots (ADR 0013) are not in Firestore: a GitHub Actions job
  (`.github/workflows/public-data-contract-offers.yml`, `functions/src/publicDataContractOffers.ts`,
  every 30 min, fired on time by the Cloudflare Worker `workers/public-data-dispatch`) that holds no EVE
  token and calls no ESI endpoint publishes them to Cloudflare R2 as static objects, R2 being their
  only store (ADR 0019, issue #4270). Its state (archive fingerprint, type hashes, writer state) is
  R2 objects under `contract-offers-state/`. One is every for-sale contract line of
  every item type, as an `index.json` (per type the offer count, cheapest ask
  and the objects holding its rows, plus every region) and per-type objects;
  the Items board and BPC Sourcing read only the types they need. The other,
  off the same archive fetch, is public courier contracts as a route and a fee
  (issue #909), one object.
  A second, separate job (GitHub Actions `.github/workflows/public-data-workbench-fits.yml`, `functions/src/publicDataWorkbenchFits.ts`, issues #2484, #5071) copies EVE
  Workbench's public fits into R2, one object per hull
  (`workbench-fits/<shipTypeId>.json`, issue #4271), because Workbench's API
  can't filter by hull; the client fetches a hull's object by id with no
  Firebase session, since the fitter works logged out
  (`features/fittings/workbenchFits.ts`). The sync's checkpoint is the R2 object
  `workbench-fits-state/state.json`, not Firestore.

- GitHub starts `schedule:` runs hours late, so the 15 min lawless job is also fired by a Cloudflare Cron Trigger Worker calling `workflow_dispatch` (`workers/public-data-dispatch`, README there; issues #5113, #5215). The workflow's own `schedule:` stays as the fallback.
- A daily GitHub Actions job (`.github/workflows/public-data-market-open-prices.yml`, `functions/src/publicDataMarketOpenPrices.ts`) folds EVE Ref's last market-order
  snapshot of the previous UTC day into the R2 object `open-prices/<typeId>.json`:
  per type, every Trade Hub _station_'s highest buy and lowest sell for the day
  (`{ typeId, dates, stations: { <stationId>: { buy, sell } } }`), up
  to 400 days, public static file with no Firebase involved (`functions/src/marketOpenPrices.ts` holds the logic,
  `marketOrdersArchive.ts` the streaming fetch). The mining pricing reads the
  same objects, one per type it prices (`features/market/hubSnapshot.ts`); they
  replaced the retired `captureMiningPriceSnapshot` job, its Firestore
  `marketHistory` and the `mining-prices/` month objects.
  Its last-run record (the shrink guard) is the R2 object `open-prices-state/last-run.json`, not Firestore.
- The `public-data-hauling-books` job (`.github/workflows/public-data-hauling-books.yml`, `functions/src/publicDataHaulingBooks.ts`, every 30 min, fired on time by the `workers/public-data-dispatch` Worker) streams EVE Ref's latest market-order snapshot and writes each Trade Hub station's best 30 buy and sell price levels per type to `hauling-books/<stationId>.json` in R2 (`haulingBooks.ts`). The hauling scan builds its order-book pass from them (`features/market/haulingBooks.ts`), so every survivor gets books with no ESI request per item. Its last-run record is the R2 object `hauling-books-state/last-run.json`. Touches no Firestore.
- The daily `public-data-lp-store` job (`functions/src/publicDataLpStore.ts`) folds EVE Ref's 30 daily market-history files (`marketHistoryVolume.ts`) into two sibling R2 objects per Trade Hub region: `lp-store-volume/<regionId>.json` (units per day, the LP Store's Sells/day) and `hauling-demand/<regionId>.json` (per type: volume, days with trades, order-count sum, recent sale price, newest day; the Hauling scan's demand pass, issue #5344). Data is about 1 to 1.5 days old.

Auth is browser-only OAuth2 PKCE against `login.eveonline.com`; refresh
tokens never leave the device. Market prices come from Fuzzwork aggregates,
ESI as fallback (ADR 0002). The item/skill/blueprint catalog (SDE) is
snapshotted at build time into `public/data/*.json` by `scripts/build-sde.mjs`
— no SDE calls at runtime. Core-feature files are precached for offline-first use (`blueprints`, `shipTree` and the small `market/` lookups). The large single-feature files (`src/sde/lazySdeFiles.ts`, the one list `vite.config.ts` ignores and `src/sde/warmLazySde.ts` fetches) are not: they are fetched on first use or by an idle, connection-gated background warm (also the dogma engine assets), cached by the service worker's `sde-data` route. Per-type description, dogma attributes and effects, volume and packaged volume (Item Detail, required skills, hardpoints, implant bonuses, Hauling's volume fallback; read through `src/features/skills/typeDetail.ts`) are lazy the same way, split into 64 range-bucket shards, `public/data/typeInfo/<floor(typeId / 2000)>.json` (`src/sde/typeInfoShard.ts`; neighbouring ids share text, so gzip packs them together), so opening one item reads one small file; a type no shard carries falls back to the cached ESI read.

External dependencies: `esi.evetech.net`, `login.eveonline.com`,
`market.fuzzwork.co.uk`, `data.everef.net` (public BPC contract search, ADR
0013), Firebase (Firestore + Functions), and `mutamarket.com` (abyssal module
estimates, only via the `mutamarketEstimate` function). Nothing else.

## 3. Data flows

**SSO login (PKCE)**
`app/loginFlow.beginEveLogin` → `auth/session.startLogin` stashes one
**Pending Login** per round trip in `sessionStorage` — `neocom.sso.pkce.<state>`
holding `{ verifier, scopes, createdAt }`, so two racing presses cannot clobber
each other's verifier (#649) — redirects to `login.eveonline.com` →
`routes/Callback.tsx` → `auth/session.completeLogin` validates state,
exchanges code, decodes the JWT (`auth/jwt`), writes `CharacterRecord` +
`TokenRecord` (refresh token) to Dexie. Later ESI calls go through
`auth/session.getValidAccessToken` (single-flight refresh, buffer 60s before
expiry) → `esi/client.configureEsi`'s injected `getToken`. A callback that
cannot complete does not dead-end: `app/loginFlow.retryLastLoginOnce` restarts
the sign-in asking for what a live Pending Login (else `neocom.sso.intent`)
asked for, so a corp grant is not retried as a plain re-auth, under a budget in
`neocom.sso.autoRetries` that stops it looping between the app and SSO. Only
then does a panel appear, worded per failure, with a button that restarts the
sign-in. A `?error=` from SSO (a cancelled sign-in) is terminal.

**ESI read-through cache**
Pattern: try live `esiFetch` → on success, write `db.esiCache` (keyed
`[characterId, key]`, or `GLOBAL_CACHE_CHARACTER_ID` for character-independent
lookups like universe types/names). One deliberate exception:
`character/structures.ts` mirrors a resolved structure name under that same
sentinel once any Character in the roster resolves it (issue #669) — not
because a structure name is public, but because every Character tried
belongs to the one roster sharing it. That is also the one sentinel row with
a purge trigger: `cachePurge.purgeSharedStructureCache`, fired by
`removeCharacter.ts` only once the roster reaches zero Characters, never on
any single Character's own scope revoke or owner change (see
`docs/context/decisions/20260909-165444-...md`). On failure, fall back to
cache; `null` only when neither exists. Auth failures (401/403/refresh failure) surface as
`needsReauth: true` instead of silently going stale. Implemented once, in
`esi/cache.ts` (`loadWithCache`/`loadWithCacheStatus`, `isAuthFailure` from
`esi/client.ts`) — every `features/*` data module (`skills/data.ts`,
`character/{wallet,mail,calendar,contracts,orders}.ts`,
`assets/assets.ts`,
`industry/data.ts`, `industry/jobs.ts`) is a thin wrapper over it.
Freshness is decided from `db.esiCacheMeta` — each row minus its value, kept
in step by a DBCore middleware (`db/esiCacheMeta.ts`) in the same transaction
as every `esiCache` write/delete — so a stale check never deserializes a
multi-MB value; the boot prefetch skips a task whose row is fresh
(`isCacheFresh`). A loader built with `conditionalFetch` sends the stored
ETag, and a 304 bumps only the meta row.
`character/stations.ts` is the exception that reads the SDE snapshot first and
only wraps `loadWithCache` for what the snapshot misses — see **NPC stations
come from the SDE snapshot** below.
Cache **reads** are additionally gated by `cachePurge.isCachePurgePending`:
if a scope-revoke purge could not complete for a Character, its cached rows
are treated as absent so a stale grant can never serve the previous owner's
data — offline then shows an empty view rather than someone else's wallet.
Auth failures also call `stores/authFailure.reportEsiAuthFailure`, so the
shell surfaces one notice instead of each view rendering its own banner.

**Freshness window.** Every cache key has one: `readFreshRow` serves the Dexie
row without a live call while `max(the row's own Expires header, fetchedAt +
staleAfterMs)` is still in the future. `staleAfterMs` defaults to
`STALE_AFTER.default` (10 minutes — the app-wide promise that page-to-page
navigation inside it never touches the network) and is set to
`STALE_AFTER.static` (24h) by the loaders reading data that does not change:
universe types/systems, the stations the SDE snapshot does not cover, routes,
PI planet and schematic names,
structures, a delivered mail's body, an issued contract's item lines. ESI's
header only ever _extends_ the window, never shortens it below the floor.
`invalidateFreshness()` (called by `useRouteSnapshot.refresh`) suspends the
window for `REFRESH_BYPASS_MS`, so a manual refresh reaches ESI without
sending every other route back to the network too.

**Grace period (`loadPastWindow`).** `esiFetch` had no timeout at all (it now
has only the 30s "this connection is dead" bound issue #655 added), so past the
window a slow or hanging connection used to leave the page on a spinner over
rows already on disk. The live call is now raced against `STALE_GRACE_MS`
(250ms). If it answers first — which it does on any healthy connection — its
result is returned verbatim, so the single-phase contract every caller had,
`needsReauth` and `skipCacheOnAuthFailure` included, is completely unchanged;
this is why racing beats substituting a stored row unconditionally, which
broke 30 tests across 22 files by making every past-window read two-phase.

When the grace expires, `readStaleRow` supplies the stored row
(`fromCache: false` — no bad news yet) and `recordLateOutcome` follows the
call, then fires `onCacheRevalidated`. `useRouteSnapshot` subscribes and
re-runs its loader stamping the _unchanged_ epoch, so the rendered snapshot
stays `current` and `loading` never flips — the view updates in place instead
of blinking back to a spinner. A signal arriving mid-load is held and flushed
when that load settles, so it never cancels a load the user is waiting on and
a burst across a page's several keys collapses into one re-run. A late failure
lands in `revalidationFailures` (keyed like `inFlightLoads`), which
`heldAfterFailure` reads to give the re-read its `fromCache: true` /
`needsReauth` / `cached: null` — and to stop it starting another slow call, so
the signal cannot loop. No substitution happens for a manual refresh (it must
report what actually happened) or for a key whose window is longer than
`STALE_AFTER.default` — a lapsed 24h row is a station name, and re-rendering
for a constant is all cost. A `STALE_AFTER.static` key instead takes
`loadLapsedConstant`: the stored row at once, refreshed behind the caller
with **no** signal, so the fresh row is simply there for the next read —
unless it opted into `skipCacheOnAuthFailure`, which keeps the blocking live
call. A key
whose long window encodes a _publish cadence_ rather than immutability opts
into the grace race with `allowStaleServe`, which is how the Contract Search
snapshots render last cycle's rows while this cycle's arrive (#963).

**Retained route snapshots.** All of the above kept the _rows_ local; it did
not keep them _rendered_. `useRouteSnapshot` holds its result in `useState`,
which React Router discards when it unmounts a route, so every tab visit
restarted at `data === null` with `loading` true. `lib/routeSnapshotCache.ts`
is the in-memory, session-only store that closes that gap: pass
`{ cacheKey: '<view>' }` and the hook writes each successful snapshot under
`` `${cacheKey}:${characterId}` `` and reads it back _during render_, so the
first frame after a navigation already has rows. Views spin on
`loading && !data`, never `loading` alone — `loading` stays honest for the
Refresh button. The key is an explicit string because several call sites pass
an inline loader whose identity changes every render. `esi/cachePurge.ts`
publishes `onCachePurged` (a character id, or `null` for the cache-wide
fallback tier), which this store subscribes to, so a consent purge takes the
in-memory copies with it — `purgeCorpScopedCache` included, since a retained
snapshot is a whole rendered board and cannot be forgotten by `corp:` prefix.
`features/corp/useCorpSnapshot.ts` opts in the same way via
`{ name, characterId }`, folding its own key (character + corporation +
division) into the retained name.

**Partial snapshots.** A loader with a slow tail (Assets: prices, names,
Firestore copy values) calls `signal.publish(partial)` after its fast read.
The hook renders it only when nothing is on screen (no finished, retained or
carried-over data), keeps `loading` true until the loader returns, and never
retains it — so `data` can be non-null while `loading` is true, and views
still spin on `loading && !data`. A partial's gaps must read as "not loaded
yet", never as a value a filter can act on (Assets' `pricesReady`).
`market/prices.ts`'s `getAdjustedPrices(now, { allowStale })` is the matching
cache-side escape: it serves a lapsed persisted copy at once and, when the
refresh lands, fires `emitCacheRevalidated` so mounted views re-read.

Session-only is the load-bearing limit, not an implementation detail: the
**first** visit to a route after an app load still composes its snapshot from
scratch, and that is the one window a spinner is still on screen. `prefetch.ts`
does not close it — that warms `esiCache`, so the composition reads local rows
instead of the network, but it warms endpoints, not composed view snapshots.
**Intent warming** (`app/routeWarm.ts`) narrows that window rather than closing
it: `Layout`'s rail links compose their route's snapshot on pointer-enter and
on focus, so the click lands on a warm cache. Same thin-orchestrator shape as
`prefetch.ts` — it calls the view's own loader, so no second composition path
can drift — and it inherits the same scope rule, declaring the endpoints each
loader reaches and filtering them against the stored grant through
`prefetch.ts`'s `grantCovers`, since asking for an ungranted endpoint answers
403 and paints the shell-wide re-auth notice for a pointer sweep. Note that
this is deliberately **not** the route's `locked` flag: an `UNGATED` route can
still compose scope-gated reads — `/calendar` pulls six — so a lock-based gate
would read as unlocked for everyone and warm blindly. "Is this route gated" and
"may this Character be asked for this" are different questions, and only the
second one is safe to act on.
`ROUTE_WARMERS` is deliberately incomplete: a route qualifies only once its
loader lives outside its own component file, because exporting one from a
`.tsx` route trips `react-refresh/only-export-components`, which CI fails on.
Today that is `/calendar` alone; moving the other loaders into `features/` —
where `docs/ARCHITECTURE.md` puts loading anyway — is what adds the rest.

Fully closing the window would mean running route loaders at boot (a burst of
exactly the kind `prefetch.ts` is written to avoid) or persisting snapshots
across reloads — which `routeSnapshotCache.ts`'s own header already argues
against on the grounds that `esiCache` is the durable copy and a second
persisted one would need its own purge and freshness rules, and which would
additionally have to survive a stored snapshot's shape drifting across
deploys. What a view may show in the meantime is `docs/DESIGN.md` §6a.

**Name lookups are cache-first.** `features/character/names.ts`
(`resolveNames`) and `typeNames.ts` (`resolveViaEsi`) both used to POST
`/universe/names` first and read `esiCache` only as an offline fallback, so
every render of a view holding a name blocked on a live round-trip. Both now
read the cache first and ask only for ids they have no name for. `resolveNames`
returns a lapsed name (`STALE_AFTER.static`) at once and refreshes it behind
the caller; a type name has no window at all, being as immutable as the SDE
snapshot it backstops.

**NPC stations come from the SDE snapshot** (issue #655).
`public/data/market/stations.json` is the complete `staStations` table — id,
name, system and (since #655) `stationTypeID` for every NPC station in the
game. `sde/npcStations.ts` indexes it by id once per session and
`character/stations.ts` reads it before ESI, so `loadStationName`,
`loadStationSystemId` and `loadStationSummary` cost no request for any id ESI
has already labelled a station (`location_type` on Assets/Clones rows, a
detected owned-stock placement, a Build Location search hit). That is what
makes the `Promise.all(stationIds.map(...))` fan-outs at those call sites
harmless: they are map lookups, not requests, so they need no concurrency cap.
`GET /universe/stations/{id}` stays as the fallback for an id the snapshot
predates and for a snapshot that could not be read.

Because the table is complete, membership in it also _discriminates_: an id
the snapshot has loaded and does not hold is a player structure.
`character/contractLocationName.ts` uses that in place of the
station-probe-then-structure order it used to run, deleting a guaranteed 404
per open for any contract at a structure — a 404 counts against ESI's
100-errors-per-minute budget like any other non-2xx. `lookupNpcStation`
answers with three values, not two, so "loaded and absent" (a structure) is
never confused with "snapshot unreadable" (conclude nothing, fall back).
The file stays outside the install precache (`src/sde/lazySdeFiles.ts`), so a first
offline visit still has no snapshot and station names come from `esiCache`
exactly as before.

**Boot prefetch.** `app/prefetch.ts` warms every granted surface into
`esiCache` on app start and on each character switch, wired from the same
`App.tsx` effect shape as `triggerSync`. It is a thin orchestrator over the
existing `features/*` loaders — never its own fetch code — so it inherits
their cache keys and auth policies, and the freshness window makes it
idempotent. Two constraints shape it: tasks are filtered against the stored
grant (`prefetchTasksFor`, reading `ESI_REGISTRY` — an ungated warm-up would
403 its way to a spurious boot-time re-auth banner), and the run is capped at
`ESI_FANOUT_CONCURRENCY`. Progress drives `stores/prefetch.ts` and one dot in
the rail beside the sync dot. A consequence worth knowing: `/settings`' ESI
activity log shows far fewer rows than before, because a freshness hit never
reaches `esiFetch`.

**Detail prefetch.** After a mail-header or calendar load that really reached
ESI (`fromCache` false), `features/character/detailPrefetch.ts` fetches the
detail rows the reader would otherwise need a connection for: the 20 newest
mail bodies (unread first) and up to 20 calendar events in the next 14 days,
through the views' own cached loaders (`prefetchMailBodies`,
`prefetchCalendarEventDetails`). Two triggers only: the boot warm-up (the
active Character's tasks, then `prefetchRosterDetails` for every other
Character holding the scope) and the Foreground Poller's mail and calendar
domains. Bounded, two requests at a time in the background lane, skipped
unless `lazyAssetWarmGate` reads the connection as unrestricted, and an id
that failed once is not asked for again that session. Rows already cached are
never refetched.

**Share Link copies.** `features/share/shareStore.ts` keeps a loaded share's
payload in `esiCache` under the sentinel Character (`share:<id>`) until its
`expiresAt`, and serves it, labelled with `CachedNotice`, only when Firestore
cannot be reached. A live read wins and refreshes it; a Survey is never kept.
`esiCache`'s daily prune drops what is left a day past the share's life.

`loadWithCacheStatus` takes `detectAuthFailure`/`skipCacheOnAuthFailure`
options for `industry/jobs.ts`'s narrower definition (only a 403, and no
cache fallback — a character that never granted the scope has never cached
a jobs response). `features/character/{names,typeNames}.ts` and
`features/market/groupNames.ts` do their own batch/partial-resolution
instead of a single-key read-through, so they only share the raw
`readCached`/`writeCached` primitives and the `GLOBAL_CACHE_CHARACTER_ID`
sentinel, not `loadWithCache` itself.

**Skill plan edit → sync**
UI mutates `db.skillPlans`/`db.buildPlans`/`setSyncedSetting` directly, then
calls `scheduleSync(characterId, { collections: ['plans'] })` (2s debounce)
or `triggerSync` for immediate. `collections` names the synced collections
the edit wrote: a pass within `PARTIAL_PASS_WINDOW_MS` of a full one pulls
and pushes only those, and coalesced requests union them (issue #4896,
`sync/syncScheduler.ts`). Omit it when unsure — that is a full pass, as are
boot, Character switch, reconnect, the background sweep and `triggerSync`.
Deletes MUST go through `markPlanDeleted`/`markBuildPlanDeleted`
/`deleteSyncedSetting` (each records a tombstone) — a plain Dexie delete
resurrects from the remote copy. `setSyncedSetting` also enforces the
`SYNCED_SETTING_KEYS` allow-list (`src/sync/syncedSettings.ts`); adding a
synced setting is a deliberate two-file edit (list + its pinned test). A
preference with a _control_ rather than a call site goes through
`lib/useSyncedSetting.ts`'s `createSyncedSetting` instead — same store shape as
`createLocalSetting`, but it seeds from the pre-sync device-local key, fans
`scheduleSync` out to every Character, and re-reads on each successful sync
(pulls land in Dexie behind the store's back). Settings' Defaults panels are
its five callers.
`triggerSync` → `syncAuth.ensureSignedIn` (mints a Firebase custom token from
the current EVE access token, uid `char:{characterId}`, claim `ownerHash`) →
per collection: fetch remote docs filtered `where(ownerHash==current)` →
`merge.mergeRecords`/`merge.mergeSettings` (last-write-wins by `updatedAt`;
remote tombstones kept 30 days, local settings tombstones until the key is
rewritten) → push/pull/delete accordingly. Syncs are globally serialized and coalesced per character; each
character signs in on its own persisted Firebase session (`sync/syncAuth.ts`). If a
character's `ownerHash` changed since the last sync (sold/transferred), local
plans for it are wiped first (`handleOwnerHashChange`).

**Industry build plan compute**
`useIndustryWorkspace` loads blueprint catalog + owned blueprints +
character skills, plus `features/industry/buildPlanPricingInputs` — the one
module that hydrates the assumed-ME / include-blueprint-cost settings (and
owns the "don't price until hydrated" gate, `isPricingReady`) and loads
corp blueprints, per-Trade-Hub standings and BPC Sourcing rows;
`pricingSourcesForHub` narrows them to one plan's hub. A new pricing input
goes there and in `resolveBuildPlan`, nowhere else. Every view that prices a
plan — `BuildPlanDetail` for the open plan, `useComparedBuildResults` for
Build Plan Compare / the index / every Group Rollup — takes those inputs,
fetches its market snapshot (plus a second, reaction-activity one for a
configured Reaction Location) and calls `features/industry/resolveBuildPlan`
(Build Opportunities reads only `assumedMe` from the module and prices on its
own). That one pure call does all the wiring:
per-plan corp-blueprint merge (`includeCorpAssets`), Reaction Location, price
basis, make-or-buy context, a fresh Blueprint Acquisition tier pool, the
top-level acquisition (resolved ME/TE), and then `computeBuildPlan`, which
clamps runs/ME/TE, resolves the `FacilityPreset` and calls pure
`engine/industry/buildVsBuy` → `BuildResult` (materials, job fee breakdown,
build-vs-buy verdict). Never throws — computation errors surface as
`{ result: null, error }`.

**SDE build-time pipeline**
`scripts/build-sde.mjs` downloads Fuzzwork SDE CSVs (`invTypes`, `invGroups`,
`dgmTypeAttributes`, `industryActivity*`, `mapRegions`, `mapSolarSystems`,
`staStations`, ...) into a gitignored repo-local cache, emits slim
`public/data/{skills,blueprints,types,reprocessing,pi,...}.json` plus the
`public/data/market/*.json` catalogue (market groups/types,
solar systems, NPC stations, market regions, attributes, variations; the small
lookups are precached, `types`/`stations`/`variations` are lazily fetched). Runtime
never fetches CSVs — `src/sde/loadSde.ts` and `src/sde/loadMarketSde.ts`
fetch+memoize the built JSON once per session.
It reads Fuzzwork's build-numbered dump and CCP's JSONL export of the same
game build (it fails if they differ) and records that build in
`scripts/sde-build.json`. `.github/workflows/sde-refresh.yml` reruns it
nightly when both sources move to a newer build and opens an auto-merging PR.

## 4. Invariants & gotchas

- Refresh tokens live in Dexie **only** — never Firebase, never logs (ADR 0001).
- ESI attributes (`getCharacterAttributes`) already include implant bonuses;
  subtract `features/skills/dogma.extractAttributeBonuses` output to get base
  attributes for the engine.
- Required-skill dogma attribute pairing (verified against everef.net + a live
  ESI response, **the commonly-assumed pairing is backwards**):
  requiredSkill5 (1289) pairs with **1287** (not 1288); requiredSkill6 (1290)
  pairs with **1288** (not 1287). See `features/skills/dogma.ts` header.
- Firestore rules split `get`/`update` (hash-strict — `ownerHash` must match
  the token claim) from `list`/`delete` (uid-only). A hash-strict `list`
  would fail every query the moment one stale-owner doc exists, so
  `planSync.ts`'s normal sync path always scopes `list` queries with
  `where('ownerHash', '==', current)` to compensate. Removing a Character
  deletes nothing remote: the `purgeStaleAccounts` Cloud Function (admin SDK,
  not bound by these rules) clears an account after 90 days without a sync.
- Communities (issue #3596, ADR 0018) are the third kind of Firebase data,
  next to per-character sync data and public caches: membership-gated shared
  data (`communities/{id}`, its `members/{uid}`, and each Member's chunked
  `library/{n}` of Shared Blueprints). Rules let Members read; a Member writes
  only their own chunks and pushed-at stamp. Create/join/leave/remove/revoke/
  regenerate/delete are callables (`functions/src/communities*.ts`) because
  the 100-Member and 10-Communities caps and delete-on-leave can't be rules.
  `purgeStaleAccounts` also removes a stale Character from its Communities (a
  stale admin takes the Community with it). `characters/{uid}/communities/{id}`
  is the Character's membership index. Shared Fittings (issue #3605) are a flat
  `communities/{id}/fittings/{uid~saved-<id>|uid~game-<esiId>}` — flat so a
  Community's list is one query however many Members there are; the doc id's
  uid half is what the rules bind a write to. Each holds the Fitting Share Code
  (not a URL), name, hull and updated-at, never notes. `saveFitting` and
  `deleteFitting` (`features/fittings/myFittings.ts`) re-push or remove a saved
  Fitting's copies best-effort; leave/removal/purge sweep them in
  `deleteMemberShares` (`functions/src/communitiesStore.ts`).
  Requests (issue #3807, ADR 0021) are `communities/{id}/itemRequests/{id}`
  (lines, location, terms, owner, `expiresAt`, `closed`), read by any Member
  and written only by callables, which hold the 10-open-Requests-per-Member cap in a
  transaction (the 50-lines cap is enforced when the input is parsed). `…/pledges/{uid}` (issue #3808) is one Member's
  Pledges on that Request, written directly by its owner under `firestore.rules`
  (not on one's own Request, only while it is open, line indexes the Request has,
  positive integer quantities up to 10^12; the Pledger's client asserts
  `delivered`, `contractIds`, an optional typed `manual` amount (issue
  #3809) and the stored contract figure `auto` and its `through` finish time, so
  they are shape-bounded: at most 10 positive integer contract ids a line, kept as
  capped evidence; `auto` and `through` are non-negative whole numbers). Rules cannot loop, so the 50 line keys are unrolled and only keys a
  write changes are validated. The 1000-expression budget is the binding limit:
  a changed line costs about 130 plus 27 per contract id (35 more with
  `manual`), over ~350 for the document, so one write of four full lines is
  denied; `batchLines` in `src/engine/communities/delivery.ts` splits writes to
  fit and `rules-tests/communities.rules.test.ts` pins its cost model. `…/pledgeMails/{pledgerUid}` and
  `characters/{uid}/requestMailQuota/{day}` are the Pledge-mail
  callables' bookkeeping (100 mails a day, a slot per Pledger), read-only to
  clients; a Request's `notify` is written by the post and edit callables. Leave/removal deletes a Member's Requests and
  Pledges in `deleteMemberShares`.
  Cleanup (issue #3812): the daily `sweepCommunityRequests` (a task of `dailyHousekeeping`) (`functions/src/communityRequestsCleanup.ts`,
  verdict in the pure `decideRequestSweep`) deletes Requests expired 7 days ago
  (they stay Expired and extendable meanwhile) and Requests closed 7 days ago with their Pledges (`recursiveDelete`; two
  single-field queries per Community, each candidate re-read before its delete,
  capped per run). The Community admin removes any Request or Pledge through
  `removeCommunityRequestCallable` / `removeCommunityPledgeCallable` (admin
  checked server side; the rules still deny the client), surfaced as the side
  panel's **Remove request** and per-Pledger **Remove**, each behind
  `ConfirmDialog`. Neither the sweep nor the callables are deployed by
  CI: `firebase deploy --only functions`.
  **Fleet Payouts** (issue #4779) mirror Requests: `communities/{id}/fleetPayouts/{id}`
  (boss-owned, `memberUids`, `shareCount`/`paidCount`, 30-day expiry) with one
  `shares/{index}` per pilot (`memberUid` set only when that Character is a current
  Member). Read by Members; shares by the boss or the share's own Member; all writes
  via `createCommunityFleetPayoutCallable` (20 open per Member, 250 shares),
  `setCommunityFleetShareDoneCallable` (boss only) and `removeCommunityFleetPayoutCallable`
  (boss or admin) in `functions/src/communityFleetPayouts*.ts`. Daily
  `sweepCommunityFleetPayouts` deletes them 7 days after expiry; leave/removal deletes a
  Member's own.
- **Corp-shared data: the Corp Tax Book** (issues #4061/#4055, ADR 0023) is
  the fourth kind of Firebase data: a corporation's moon-mining tax record,
  `corps/{corporationId}`, shared by every officer and gated by a
  verified corp role instead of a uid or a Community. The root doc holds the
  settings (start date, trade hub, Ore Form, dated rates, grace, minimum
  Statement, divisions, last sync); beside it are `officers/{uid}` (access
  records), `observed` (Observed Mining Entry rows), `extractions`,
  `payments` (Tax Payments), `dismissals`, `declarations`, `adjustments`,
  `writeOffs`, `rebills`, `statements` (create-only; a Statement never
  changes), `miners` (groupings), `meta/paid` (`paidStatementIds`, only ever
  grown: a paid Statement's days stay closed, D22) and `audit` (immutable log,
  shown as the activity feed). `corpTaxBookTokens/{token}` maps a Statement's
  verify link to its Statement; no client can read it. **Nothing is written by
  a client**: every write is a callable in `functions/src/corpTaxBookStore.ts`
  (pure parsing and role decisions in `corpTaxBook.ts`) that appends an audit
  entry in the same transaction. `verifyCorpOfficerCallable` takes the caller's
  short-lived EVE **access token** (never a refresh token), reads the
  Character's corporation, roles and the CEO from ESI (with
  `X-Compatibility-Date` and an `X-User-Agent`), writes an `officers/{uid}`
  access record that expires after 24h, and keeps no token. Role checks are
  trusted for 10 minutes; dismiss, reverse-dismissal, write-off, rebill and
  "not tax" require a live check (the token again). Rules let an officer read
  the whole book while that record is unexpired for their ownerHash, and let
  any signed-in Character read **their own lines** (`uid`/`uids` equals the
  verified `char:{id}` uid) in any corp's book, including after leaving it; the
  settings doc is `get`-able by any signed-in Character (the terms are on every
  mail). Callables (actions of the `corpTaxBookCall` router, `callableRouter.ts`; not deployed functions of their own, see SYNC-SETUP "Functions are routers"): `verifyCorpOfficerCallable`, `turnOnCorpTaxBookCallable`
  (Director), `deleteCorpTaxBookCallable` (the opener or the CEO; wipes the book), `reclaimCorpTaxBookCallable` (the CEO; revokes other officers'
  access), `syncCorpTaxBookCallable` (monotonic observer upsert, Extractions,
  donations; Accountant+), `editCorpTaxBookCallable` (rates, settings, payments,
  dismissals, groupings, adjustments, write-offs, rebills, Statements,
  declarations), `confirmCorpTaxBookGroupingCallable` /
  `declineCorpTaxBookGroupingCallable` / `listPendingCorpTaxBookGroupingsCallable`
  (a guest answers a hand-made grouping as the added character, never by token;
  #4210), the player-facing `claimCorpTaxBookPaymentCallable` (see below), and
  the no-login verify-link callables `readCorpTaxBookStatementCallable`,
  `stopCorpTaxBookRemindersCallable` and
  `declineCorpTaxBookGroupingByTokenCallable` (decline only). `functions/` cannot import `src/`, so the
  slice of the pure engine the callables enforce is mirrored in
  `functions/src/corpTaxBookEngine.ts`, pinned to `src/engine/corpTaxBook` by
  `functionsMirror.test.ts`. Callable tests run against the emulator
  (`functions/src/corpTaxBookEmulator.test.ts`, part of `npm run test:rules`).
  The officer sync client is `src/features/corp/taxBook/` (issue #4062):
  `syncCorpTaxBook` reads the observer ledger, Extractions, moon notifications
  and journal donations, uploads them, then settles the Statements
  `allocatePayments` reports paid (the server never detects settlement); its
  pure half is `src/engine/corpTaxBook/sync.ts` (gaps, donation resolution,
  settlement plan). `useCorpTaxBook` exposes last-synced/stale/gaps and syncs
  on visit; `useMiningLedgerAccess` says when to ask for the mining scope.
  **Scheduled sync** (issue #4068, ADR 0025): `syncCorpTaxBooks`
  (`onSchedule`, 00:35/06:35/12:35/18:35 UTC) syncs and settles each opted-in corporation's
  book with the token of one opted-in book editor. The grant is
  `corpTaxBookSyncGrants/{corporationId}`: function-only (rules deny every
  client), one doc per corporation holding the holder's narrow-scope refresh
  token encrypted under the Alerts Grant's `ALERTS_TOKEN_KEY` with a
  `corpSyncGrant` purpose in the AAD. What officers read is
  `corps/{corp}/meta/scheduledSync` (holder, active or stopped and why,
  last run). Callables: `saveCorpTaxBookSyncGrantCallable` (the holder, proven by
  the grant's own token) and `revokeCorpTaxBookSyncGrantCallable` (the holder, or
  the CEO with a live role check). A run refreshes and rotates the token,
  re-reads the holder's corporation and roles, then calls `syncBookAs` /
  `editBookAs` (`assignPayment`, `settleStatements` only; never issues or mails).
  It stops the schedule and deletes the token when the holder lost the role, left
  the corp, SSO says `invalid_grant`, ESI refuses the token or the book is off.
  The pure half of the visit's pipeline is mirrored in
  `functions/src/corpTaxBookSyncEngine.ts`, pinned by
  `src/engine/corpTaxBook/syncMirror.test.ts`; emulator tests are
  `functions/src/corpSyncGrantEmulator.test.ts`. The client is
  `AutomaticSyncSection` (Settings) and `features/corp/taxBook/syncGrant.ts`; the
  round trip rides the `corpSync` login intent, like Alerts. Not deployed by CI:
  `firebase deploy --only functions,firestore:rules`.
  **Claiming a donation** (issue #4065): `claimCorpTaxBookPaymentCallable` is
  authorised by the caller's uid, not an officer record. It finds the payment,
  answers "not found" for a missing one and for someone else's alike, refuses
  one already assigned or marked not tax, and sets the payment's `minerId`
  (the Miner the Character is grouped into, else `solo:{characterId}`) plus
  `claimedBy` and `claimedAt`; the audit entry is `claimPayment`, attributed to
  "Player claim". **The personal tab** (`src/features/miningTax/corpBook/`) is
  the member's view of the same book: `useCorpBookView` does a `get` of
  `corps/{corp}` for the Character's corp (and any corp remembered in
  the `corpTaxBookCorps` setting, so a leaver keeps reading), reads only the
  member's own lines through the `uid`/`uids` rules, and
  `src/engine/corpTaxBook/personal.ts` (pure) overlays them on the Tax tab. No
  book or any failed read leaves the tab untouched; a guest has no app login
  and uses the verify page instead. **The verify page** is the public,
  no-login route `/corp-tax-book/verify/:token`
  (`src/features/corpTaxBook/VerifyPage.tsx`): it is in `PUBLIC_ROUTES`
  (`src/app/routerPath.ts`), so it sits outside `RequireCharacter`, registers
  no service worker and skips the update wait, and analytics and Sentry
  record the route pattern, never the token. It calls
  `readCorpTaxBookStatementCallable`, whose `readStatementByToken` resolves
  `corpTaxBookTokens/{token}` and returns that Statement, its terms and **only
  the payments credited to it** (`paymentCredits`, from the mirrored
  `allocatePayments`, so a donation that paid two Statements shows its own part
  on each) and never the Miner's other Statements. A token carries a
  closed-account note when `miners/{id}.closedAt` is set (the `closeAccount`
  edit, issue #4184), and applies day, Miner, moon and Extraction dismissals
  to the allocation, mirrored by `moonOnDay` / `dismissalCredits` in
  `corpTaxBookEngine.ts`.
  **Local development** runs against the Firebase emulators instead of
  production: `VITE_FIREBASE_EMULATORS=1` in `.env.local` (issue #4190)
  points Auth (9099), Firestore (8080) and Functions (5001) at
  `npm run emulators`, with project id `demo-neocom-desk`, and
  `npm run emulators:seed` writes a sample book. It also requires
  `import.meta.env.DEV`, so a production build never connects. Steps:
  `docs/agents/testing-and-ci.md`.
  Not deployed by CI: `firebase deploy --only functions,firestore:rules`.
- **Sync change marker** (issue #5073): `src/sync/syncMarker.ts`. `characters/{uid}.syncVersion`
  is a counter that every pass that pushed bumps (`increment(1)`) once its pushes landed
  (`ctx.onPush` in `collectionSync`/`feedSync`/`settingsSync`, bump in `syncCharacter`). A
  `background` full pass (the sweep) reads that one doc and ends there when it equals what
  this device stored at its last full pass (`syncMarkerKey` in `localBookkeeping.ts`, dropped
  with the pull cursors); 1 read instead of ~16. Foreground passes (boot, sync now, edits)
  never skip, a full pass is forced every `SAFETY_RECONCILE_INTERVAL_MS` (3 h), and any
  failure clears the stored value. A marker the rules refuse or a failed bump costs only the
  shortcut, never the sync. Functions that only delete synced docs (`purgeFeed`,
  `purgeStaleAccounts`) do not bump: an incremental pull never reads absence. Deploy
  `firestore:rules` before the client ships: `firebase deploy --only firestore:rules`.
- **Corp Tax Book section pages** (issue #5247). The Overview (first tab), the
  Miner page and the moon page are one scroll of `BookSection`s
  (`features/corp/moons/sectionParts.tsx`): a count in the title, the newest
  ten rows, "Load older" (`usePaged`), a phone fold. No inner tabs. Everything
  they group comes from the client-side `buildBookView` (ADR 0032's read models
  are not built); the pure grouping (day phases Today's mining / Next
  Statement / earlier, the Overview's 7-day pops window, ore lines per Miner and
  moon, the place line, the merged Payments and Activity ledgers) is
  `src/engine/corpTaxBook/bookSections.ts`.
  The Overview tab is `OverviewTab.tsx` (totals chips, `NeedsYouQueue`, the
  moon schedule); the Miners table opens a row in place with `MinerExpandedRow`
  (a Miner's Statement days and one Open page link); `OreLinesTable` is the ore
  make-up table the Miner and moon pages share. `corpBookFixture.ts` builds a
  whole book for the section pages' stories.
- **Corp Tax Book send queue** (issue #4064, D16). Pure rules:
  `src/engine/corpTaxBook/mailQueue.ts` (pacing, 520 holds, summary, D27
  reminder rule) and `statementMail.ts` (the short Statement mail). Client:
  `src/features/corpTaxBook/`: `mailQueue.ts` (`enqueueStatements`,
  `enqueueReminder`, `retryMail`, the API the Statements tab calls),
  `officerMail.ts` (the one door for any Officer mail, SRP results included: `canSendMail`, `resolveRecipients`, fire-and-forget `queueOfficerMail`; nothing else calls `sendMail` for an officer's notice),
  `mailQueueStore.ts` (Dexie `corpMailQueue`, one row per mail),
  `mailQueueRunner.ts` (`stepQueue` / `runMailQueue` under the
  `neocom:mailQueue` Web Lock), `bookApi.ts` (verify tokens, `recordMail` /
  `recordReminder` through `editCorpTaxBookCallable`), and the UI
  (`MailQueueChip`, `MailQueuePanel`, `MailLimitNotice`,
  `StatementMailPreview`). `MailQueueMount` sits in `Layout` and loads the
  chip and sender only while the queue has rows. The queue is **local**, never
  in Firebase: Dexie `corpMailQueue` (indexed on corporation, batch and sender)
  is the only record of what is waiting, and the sender is whichever tab holds
  the `neocom:mailQueue` Web Lock, one at a time, so two open tabs never send
  twice. Only the audit of each mail (`recordMail` / `recordReminder`) goes to
  the book. The queue sends only while an app tab is open: no server holds an
  ESI token (ADR 0010).
- Firestore rules tests live in `rules-tests/` (`@firebase/rules-unit-testing`,
  `vitest.rules.config.ts`) and run only via `npm run test:rules`, which starts
  the Firestore emulator (needs a JRE; CI's `static` job installs Java 21). They
  are not part of `npm run test:run`.
- `esi/client.COMPATIBILITY_DATE` is a pinned constant (`X-Compatibility-Date`
  header) — bump deliberately, not silently, when adopting a newer ESI
  contract.
- **ESI's error limit is global, so the throttling policy is too** (issue #655,
  and the **Error Budget** glossary entry). 100 non-2xx/3xx responses per 60
  seconds across every route for the whole client: one fan-out of forbidden
  structures 420s the mail, contracts and jobs of every other Character. The
  policy therefore lives at `esi/budget.ts` behind `esiFetch`, never at a call
  site. Two consequences to know: `ESI_FANOUT_CONCURRENCY` caps one call site
  and `ESI_MAX_IN_FLIGHT` caps their sum, so tuning the former no longer tunes
  the app's burst; and a shut circuit refuses **before** sending, with an
  `EsiBudgetError` (`status: 0` — nothing was sent, so ESI said nothing) that
  read-through callers see exactly as they see a 5xx — a caller with nothing
  cached gets `{ cached: null }` rather than a spinner.
  Acquire the gate only at the `esiFetch` leaf: wrapping it around a fan-out
  (rather than around one request) deadlocks against the ceiling.
- Dev server port 5173 is `strictPort: true` — the EVE SSO callback URL must
  match exactly; never let Vite fall back to another port. E2E runs its own
  server on 5199 instead of sharing 5173.
- `playwright.config.ts` blanks `VITE_FIREBASE_*` env for e2e so
  `isSyncConfigured()` is false — otherwise `triggerSync` would hit the real
  Cloud Function and trip the e2e network guard (`e2e/support/testBase.ts`
  aborts any request to a non-baseURL host).
- Adding an ESI scope requires re-login UX: a token with the old scope set
  can't call the new endpoint (403) until the user re-authorizes — see
  `app/GrantNote.tsx` (`GrantBanner`/`GrantNote`) and `isAuthFailure`/`needsReauth` handling.
- `POST /universe/names` rejects the **whole batch** with 404 if even one id
  is unresolvable (undocumented in the OpenAPI spec, reproducible in
  practice). `features/character/typeNames.ts` falls back to per-id
  `GET /universe/types/{id}` (capped at `lib/concurrency.ts`'s `ESI_FANOUT_CONCURRENCY`, shared with `roster.ts`'s live mode — both count requests, so retuning it retunes both) on that 404.

## 7. Adding a new ESI-backed view

1. Add the ESI endpoint wrapper to the matching domain file under `src/esi/endpoints/` (typed request/response, follows existing wrapper shape; pass `endpointId: '<its own registry key>'` on the `esiFetch`/`fetchAllPagesStatus` call so it shows up in the activity log, issue #32).
2. If the endpoint needs a scope, add it on the endpoint's `ESI_REGISTRY` entry in `src/esi/registry.ts` — never hand-edit `src/esi/scopes.ts`, whose `SCOPES` is derived from the registry. Remember this forces a re-login UX for existing users (§4); batch every new scope from one release into a single `registry.ts` edit so a user re-authorises once, not once per shipped view.
3. Add a per-view data module under `src/features/<area>/` that wraps `esi/cache.loadWithCache`/`loadWithCacheStatus` (see §3) — don't hand-roll another read-through loop.
4. If the view needs calculation, add it to `src/engine/` test-first (pure, no fetch/DOM/Dexie).
5. Add the Dexie schema bump in `src/db/index.ts` only if new local storage is needed (additive `db.version(n+1).stores({...})`, never mutate a shipped version).
6. Build the route component in `src/routes/`, composing `components/ui` primitives (`Panel`, `DataAgeBadge` — required on every ESI-backed view, `EmptyState`, `Spinner`).
7. Wire the route into `src/app/App.tsx` — as a `lazy()` over a new loader in `src/app/routeChunks.ts`, whose `PRELOADERS` table is typed to require it — and give it a nav entry — one entry in `NAV_PAGES` (`src/app/navDestinations.ts`, the shared descriptor the desktop rail and the phone tab bar / More sheet read, and whose `listNavDestinations` lists every page and tab for the planned command palette, #2318), or a sub-nav tab if it belongs to an existing page (`features/skills/SkillsSubNav.tsx`, `features/character/OverviewSubNav.tsx`). A sub-nav tab still declares its own scopes in `routeScopes.ts`: tabs group views visually, they don't share a gate. If the route is gated, whichever nav renders it also renders the missing-scope marker.
8. Add strings to `src/i18n/locales/en.json`; colocated unit tests; e2e mock additions in `e2e/support/mockEsi.ts` if the view needs e2e coverage.

## 8. Adding a Notification Event

Issue #1285. The work lands in two places, and the compiler holds you to the second.

1. Add a row to the catalog in `src/features/notifications/events.ts`: id, label key, scope, corp capability and `defaultChannels`. Add the label string at `settings.notifications.event.<id>` in `en.json`. This half is service-worker-safe, and the `NotificationEventId` union is derived from it.
2. Once the id exists, `NOTIFICATION_EVENT_ENTRIES` in `src/features/notifications/eventEntries.ts` fails to typecheck until the event has an **Event Entry**. The entry names every required field:
   - `source`: the `SNAPSHOT_SOURCES` handle of the poll domain it reads.
   - `diff`: an engine diff, written test-first in `src/engine/notificationDiffs/`.
   - `copy`: its live wording in `domainCopy.ts` and `notifications.fired.*` strings.
   - `projection`: either a push renderer or `null`. `engine/projection.ts`'s `PROJECTABLE_EVENT_IDS` decides which, per id.
   - `thresholds`: fields from `eventThresholdFields.ts`, or `null`.
   - `rowHintKey`: a row hint, or `null`.
3. If the event needs data no domain fetches yet, add a domain file under `src/features/notifications/pollDomains/` (a `defineDomain` call naming a new `SNAPSHOT_SOURCES` handle) and list it in `pollDomains/index.ts`. Describe its persisted snapshot's shape with `shapeGuard` and `is` from `snapshotShape.ts`, keyed by the engine type's own fields so the compiler flags a missing one; a field added after snapshots already existed is `is.optional(...)`, so an old baseline stays readable. Add the domain's stale-shape case to `staleShapes.test.ts`.
4. A new fire type must join `AnyNotificationFire` (`eventEntries.ts`), or the entry's `diff` fails to typecheck. Joining it then makes `engine/occurrenceKey.ts`'s exhaustive `OccurrenceFire` switch demand a case.

You don't touch the domain's event list, its per-event gating, its live renderer or Settings' row for the new event. The domain's event list, its per-event gating and its live renderer are derived from the entries. Settings' row gets its threshold controls, hint, height and Scheduled Push badge from the entry too.

Some per-event sites stay by hand, because they are either service-worker-side or event-specific by nature:

- `notificationOptions.ts`'s `SUBJECT_URLS` and routes
- `eveNotification`'s per-type sub-list
- the `projection.ts` `project*` runners, called from their domain

## 9. Adding a tabbed page and URL-backed filters

ADR 0015. Contacts (`src/routes/Contacts.tsx`) is the reference conversion.

**Tabs → paths.**

1. Declare the tabs in `src/app/pageTabs.ts` with `definePageTabs('<path>', [{ id, labelKey }, …])` — the id is the URL segment, the first tab is the default — and add it to `PAGE_TABS` under the page's existing route path. A page whose feature modules also link to its tabs may declare them feature-side and import them here instead (`INDUSTRY_TABS` in `features/industry/industryTabs.ts`), so `features/` never imports `app/`. A route nested under a tabbed page (`/industry/plans/:planId`) stays its own page — `pageTabs.ts` carves registered nested routes out of the tabbed page.
2. Do **not** touch `ROUTE_ELEMENTS`, `ROUTE_REQUIREMENTS`, `pagePathFor` or `routeWarm`: `App.tsx` mounts a registered page at `<path>/*` and wraps it in `TabRoute` (bare path / unknown segment → default tab, replace), analytics reports each tab path, and a page may opt into an index state (`definePageTabs(..., { hiddenFrom })`, Settings only) that keeps the bare path below a breakpoint instead of redirecting, and `Layout` does not fade or remount between tabs.
3. In the page, `const [tab, setTab] = usePageTab(MY_TABS)` replaces the `useState`, and the `Tabs` bar maps `MY_TABS.tabs` (`t(item.labelKey)`). A tab switch pushes history and keeps the query string.
4. Any in-app link to a specific tab uses `tabPath(MY_TABS, id)`.
5. A one-level subtab (`/<page>/<tab>/<subtab>`) needs no extra machinery: give it its own tab id containing a literal `/` (e.g. Contracts' `'search/items'`) — `tabFromPathname` only ever compares one segment against a tab's `id` for equality, so a `/`-bearing id resolves the two-segment path directly. Leave it out of the `Tabs` bar's own `tabs` array if the UI that switches into it is not a second row of tabs — `usePageTab`'s `selectTab` still works for it.
6. A page of its own that must stay mounted with a tab (Ships' Fitting editor, `/ships/fittings/edit`, which carries the library's workspace state across the open) is a tab with `standalone: true`: `TabRoute` passes it through, `tabBarTabs` leaves it out of the bar, and `pageKeyFor`/`focusKeyFor` key it as its own page, so arriving there fades and moves focus as a page change does. A detail page that shares no state with the tabs (Industry's plan page, Ships' Compare) is an ordinary nested route in `ROUTE_REQUIREMENTS` instead — it outranks the `<base>/*` splat and `tabbedPageFor` leaves it out.
7. A page-local, non-tab split that is still worth a distinct path in the same sense (Market Browser's per-item Market Data / Price History split, `itemTab`) does not have to become a path segment at all — a plain scoped query param (`useUrlParam`) is the other half of "sub-path of browser, or scoped param" and is the simpler of the two when the split is only ever relevant with something else already selected.

**Filters, search, sort → query params.**

1. Declare codecs at module scope (`src/lib/urlState.ts`: `textParam`, `boolParam`, `intParam`, `enumParam`, `enumSetParam`, `idListParam`; `characterFilterParam` from `features/character/characterFilterUrlParam.ts` in a `useMemo` keyed on the synced default).
2. Keys that change together (one filter bar) go in one `useUrlParams({ … })` group; a lone toggle can use `useUrlParam(key, codec)`. Scope keys per panel/table (`across.sort`) so two tables on one page do not collide.
3. Bind a `DataTable`'s sort with `const sortProps = useUrlSort(key, DEFAULT_SORT, columnIds)` and spread it onto the table in place of `defaultSort`.
4. URL wins; absent → the default (which may be a stored setting); never write URL values into storage (scope decision "persisted view preferences stay out of the URL"). When the default is a stored setting, use `useRememberedUrlParams(schema, remembered)` (`src/lib/useUrlState.ts`) rather than blending by hand: it owns per-field presence, the blend, and sending each edit only to where it belongs (Courier Search, Market Browser). A remembered _tab_ is `useRememberedPageTab` (`src/lib/usePageTab.ts`, Contracts' Search mode). Its `adoptLinked` option writes a linked value into storage and is the Market Browser's recorded exception only (decision `20260926-201312`).
5. Leave one-shot params (`useHighlightParam`, `useOpenParam` — `?open=<id>` opens a row's modal on open orders, contracts and the calendar, and flashes the row; `?product=`, `?material=`) and modal / inspector state alone.
6. Tests: a reload test (`window.history.replaceState` to the URL, render, assert the view), and one asserting defaults leave the query empty.
