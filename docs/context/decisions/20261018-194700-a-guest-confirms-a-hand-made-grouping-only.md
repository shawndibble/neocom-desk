# Scope decisions — A guest confirms a hand-made grouping only as the added character (issue #4210)

_Recorded 2026-10-18 · issue #4210._

- **A confirm is accepted only from the added character's own signed-in uid, never from a verify token.** A verify token proves the Statement mail reached the main, not that whoever holds it controls the alt an officer added. The server's `confirmGrouping` already derives the character from the caller's uid (minted only after an EVE SSO sign-in as that character), so the verify page cannot confirm by itself: it shows the pending character, and "Sign in as <name> to confirm" runs a core-scope EVE sign-in and returns to the Statement, where the button then confirms as that signed-in character. Rules out a token-only confirm and a client-supplied character id on a confirm.
- **A verify link may decline.** A decline only removes a link and grants nothing, so the main's mail is proof enough: `declineCorpTaxBookGroupingByTokenCallable` takes the token and the pending character id, removes it, and is audited as the verify link. The added character may also decline as itself. Declining deletes a two-character Miner and records the character in `declinedAutoGroup` like an unlink, so no sync re-adds it.
- **The officer sees the answer in `meta/groupingAnswers`.** A declined character is no longer in the group, so its answer cannot live on the Miner; the officer-only meta doc holds `{minerId, answer, at, via}` per character, shown on the Miner page as "confirmed by the player" or "declined" (and whether the link declined). An officer asking again clears the old answer.
- **The personal tab finds its questions with a callable.** The added character is not in the Miner's readable `uids` until it confirms, so Firestore rules cannot show it the grouping; `listPendingCorpTaxBookGroupingsCallable` runs a collection-group query on `pendingConfirmation` as that character and returns only corporation, Miner and main (needs a collection-group index override on `miners.pendingConfirmation`).
