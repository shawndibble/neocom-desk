# Scope decisions — Item Detail reads baked type info from sharded lazy SDE files (issue #3882)

_Recorded 2026-10-15 · issue #3882._

Extends `20260928-144005-feature-sde-files-load-on-demand-not-precached.md`.

- **Every published type's description, dogma attributes and volume are baked into the SDE snapshot, and Item Detail reads them first.** Item Detail used to read them from ESI on open, so offline the whole modal errored for any item not cached from an earlier visit, though its required skills, attribute names, planetary schematic and Used in data are all local. Baked, it opens offline for any published item, including ones never viewed online, once the shards are cached (first use or the background warm). Only the order-book prices still need the network.

- **The data ships as 64 lazy range-bucket files, `public/data/typeInfo/<floor(typeId / 2000)>.json`, not one file and not precached.** All of it is ~11.9 MB raw, ~1.36 MB gzip summed per file (GitHub Pages compresses each file on its own). One file would mean parsing ~12 MB to show one item; precaching it would put it on every install for a panel most sessions rarely open. Opening an item reads one file of at most ~620 KB raw.
  - **Range buckets, not `typeId % n`.** Neighbouring ids are near-identical types (a module's meta variants, a ship's skins) sharing most of their description text, so gzip compresses them together: ~1.36 MB, against ~2.9 MB for the same data scattered across 32 modulo shards. A patch that only adds new types usually rewrites just the top bucket, so every other file keeps its content hash and stays cached.
  - **Fixed count and width (64 × 2000, ids below 128,000; the highest published id today is ~98,000).** Every bucket has a file, `{}` when empty, so the lazy list is a constant and every file gets a `?v=` hash. The build fails on a published id past the last bucket, saying to raise the count; `typeInfoBucket` returns null there and the app goes straight to the ESI fallback. `scripts/lib/typeInfo.mjs` mirrors the width and count in `src/sde/typeInfoShard.ts`; `typeInfoShards.test.ts` checks the committed files against the app's key.
  - Shards follow the earlier decision's rules: out of the precache, versioned by content hash, cached by the service worker on first use or by the connection-gated background warm. The `sde-data` cache's entry cap rises to 150, ~2x the 73 lazy files (9 + 64 shards), so a deploy's stale `?v=` entries never evict a current one.

- **The source is CCP's JSONL export (`types.jsonl` + `typeDogma.jsonl`), not Fuzzwork's CSV dump.** The CSV's `valueFloat` loses precision (Rifter attribute 124: ESI 16777215, CSV 16777200; attribute 5796: 2147483647000 vs 2147480000000), and Item Detail must show what ESI shows. The bake also merges the attributes ESI derives from the type row (4 mass, 38 capacity, 161 volume, 162 radius), so the baked list matches ESI's `dogma_attributes`.

- **A type the shard doesn't carry falls back to the cached ESI read (`loadUniverseTypeOnce`), never raw ESI.** That covers unpublished types (shards hold published types only) and types newer than the build, and the same fallback applies when a shard won't load. A type seen online once still renders offline from the Dexie cache. When neither source has it, the type's own sections show the error state, and the local planetary schematic and Used in still render beside it.
