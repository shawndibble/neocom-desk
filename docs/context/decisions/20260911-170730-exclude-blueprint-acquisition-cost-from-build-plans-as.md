# Scope decisions — Exclude Blueprint Acquisition cost from build plans, as an opt-in setting

_Recorded 2026-09-11._

- **A new synced setting, "Exclude blueprint cost from build plans" (`sync.industryExcludeBlueprintCost`, off by default), suppresses Blueprint Acquisition's row without touching tier resolution.** When on, `IndustryInputs.excludeBlueprintCost` (and its twin, `ResolveMaterialOptions.excludeBlueprintCost`) drops the synthetic Blueprint Acquisition row from `materials`/`materialCost`/`totalCost` at every level of the build tree — the plan's own top-level row (`buildVsBuy.ts`) and every nested sub-build's row (`materialResolution.ts`'s `resolveSubBuild`) — while `acquisitionFor` is still consulted for the resolved ME/TE tier, so quantities scale exactly as they would with the row shown. Rules out disabling `acquisitionFor`/`blueprintAcquisition` entirely to achieve the same effect: that would also revert every sub-build's ME to the plain `assumedMe` heuristic, silently changing material quantities (and therefore cost) for a setting that only promised to remove one line item — the opposite of what a pilot flipping the checkbox expects.
- **Group Rollup and Build Plan Compare already never included Blueprint Acquisition's cost, independent of this setting.** `useComparedBuildResults.ts` calls `computeBuildPlan` without ever passing `acquisitionFor`/`blueprintAcquisition`, so both surfaces have quoted every plan sans blueprint cost since issue #838 shipped, whether or not this setting exists. Rules out wiring the new flag through that hook: there is no row there to suppress, and doing so anyway would suggest — wrongly — that flipping the setting off restores a Blueprint Acquisition cost in rollups/compare that was never there. That gap between the single-plan view and the rollup/compare views is a pre-existing inconsistency, tracked separately, not something this change fixes.
