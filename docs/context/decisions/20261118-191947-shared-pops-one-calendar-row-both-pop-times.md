# Scope decisions — Shared pops: one Calendar row, both Pop Times, finished state, three days kept

_Recorded 2026-11-18._

- **A Calendar event the corp also made for a pop is dropped, and the pop row wins.** An event is that pop when it starts within five minutes of _either_ of the pop's Pop Times and every word of its title (letters and digits, case and punctuation ignored) is in the refinery's or the moon's name. Either time, not only the shown one, so the pilot's own Pop Time choice never brings a duplicate back. A pop the pilot already reads as a corp moon chunk, or one past its retention, is not on the board, so it drops nothing. The cost: the pop row has no RSVP chip. No toggle; an event further than five minutes away (a fleet that forms hours earlier) is a different thing and stays.
- **The row names the refinery alone; the moon lives in the detail.** The row's second line names the other Pop Time ("ready · auto-fractures 11:01 AM") until the pop pops.
- **The pilot picks the Pop Time, per device, in the Calendar's settings** (`calendarSharedPopTime.ts`): As shared (default, the officer's choice), Ready or Auto-fracture. The server publishes both instants on every pop (`readyAt`, `autoFractureAt`, additive; a doc without them reads as its `popAt`). An early-fractured chunk keeps its actual time. The Shared Moon Pop notification stays on the officer's Pop Time: a per-viewer time would mean per-viewer scheduling on the server.
- **"Fully mined" is an officer's Fully Mined flag or a finished linked Survey; both read the same on the row.** The server publishes the flag (`fullyMined`); the client reads the Survey (`loadSurveyCached`, `summarizeSurvey`) for each linked pop on the board rather than mirroring that maths in `functions/`. The detail names who flagged it and when, and shows "Survey: 62% left" while it runs. A popped moon nobody flagged says "Not marked fully mined" in the detail and nothing on the row: ESI never reports remaining ore.
- **"Likely mined out" is a guess, never a clock.** The server marks it when the book's ledger rows for the Extraction total at least 90% of the chunk's ore and that total has not moved for 30 minutes. ESI's mining observers are per-day and cached about an hour, so "quiet" is measured between publishes (`minedChangedAt`, carried from the held doc), not read off a row's time. It labels the row and the detail; it never ends the countdown or the overdue state. It can lag by up to a sync, and by up to the quiet-republish age when nothing else changed.
- **Every pop stays three days past its belt expiry** (`retainUntil`, `expiresAt` unchanged so an older client still drops it at the expiry). Past the expiry it reads Overdue ("belt expired") until it is fully mined, when it reads "Fully mined" instead of Overdue; after the three days it goes whether or not anyone flagged it. The doc holds more pops for longer; ore make-up rides on them, so a book with very many refineries nears Firestore's 1 MiB doc limit sooner.
