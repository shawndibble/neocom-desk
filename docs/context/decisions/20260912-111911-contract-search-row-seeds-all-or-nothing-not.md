# Scope decisions — Contract Search row seeds all-or-nothing, not BPC Sourcing's zero-fill (issue #931)

_Recorded 2026-09-12 · issue #931._

- **The row's seed follows `seedFromContractItem`'s all-or-nothing rule, not `BpcSourcingPanel`'s inline `row.runs === -1 ? null : {...}` conditional.** This is the call issue #931 held back from an agent ("whether the seed's fallback values should exactly copy `BpcSourcingPanel`'s convention or the sibling `bpcRowsFromContractOffers` adapter's own `?? 0` default"). All-or-nothing wins because the two surfaces have different inputs: `bpcRowsFromContractOffers` zero-fills absent ME/TE/runs, so a BPC Sourcing row always has three numbers and needs only the `-1` guard, while a raw snapshot row's three fields are each independently optional. Quoting a copy as unresearched because a field was blank is worse than opening unseeded.
- **A second near-twin function (`seedFromOfferRow`) rather than one shared helper with two adapters.** The snapshot renames ESI's fields as it publishes (`material_efficiency` -> `me`, `time_efficiency` -> `te`), so only `runs` lines up. Two six-line functions in one module, with a test asserting they agree on the same copy, was judged cheaper to read than a generic helper plus two field maps. Revisit if a third shape appears.
- **Seeding is deliberately identical to the detail modal's.** Since #933 one Contract Search item line is reachable both by the row's own context menu and by the modal's contents list; a copy that seeded differently per path would open as two Build Plans. The shared rule in `planSeed.ts` is what holds them together, and `planSeed.test.ts` asserts the agreement directly rather than leaving it to convention.
- **`BpcSourcingPanel`'s own inline conditional is left alone.** Its `-1` branch is now unreachable — the publisher drops a negative `runs` before it reaches any client (`functions/src/publicContracts.ts`), and `bpcRowsFromContractOffers` zero-fills — but folding that panel onto `seedFromOfferRow` would change a surface this issue puts out of scope. Its zero-filled `runs: 0` is rejected whole by `parsePlanSeed`'s `runs >= 1` bound, so both panels already end up unseeded for a BPO; the duplication is cosmetic, not behavioural.
- **Range validation stays on the read side only.** `seedFromOfferRow` writes whatever the snapshot reported; `parsePlanSeed` enforces `me ∈ [0,10]`, `te ∈ [0,20]`, `runs >= 1` when `/industry` reads it back. A malformed copy row therefore emits a seed the reader then rejects as a whole, opening the plan at defaults. Validating twice would duplicate the bounds and risk the two drifting.
