# Scope decisions — Request delivery marking: manual amounts and write batching (issue #3809)

_Recorded 2026-10-15 · issue #3809._

- **A typed delivered amount is stored beside the automatic one, and the shown figure is their larger, never their sum.** A Pledge line carries an optional `manual` number (a rules-bounded field). `delivered` is `min(Pledged quantity, max(contract figure, manual))`, so the automatic recompute cannot erase it, a later-granted Contracts Permission cannot double count goods the Member already typed in, and clearing it (saving 0) falls back to the contract figure. It is always offered (a direct trade or any other hand-over outside a contract must be recordable) and is marked "manual" while it is the figure that shows. Clearing it re-runs the contract sync so the contract figure returns. `delivered` and `manual` may not exceed the Pledged quantity (rules; lowering a Pledge lowers them).
- **What an earlier run recorded is a floor.** ESI forgets contracts after about a month, so recomputing `delivered` from the contracts it still returns could lower an old delivery. The recorded figure and contract ids are merged in (ids unioned, the newest 20 kept), so a re-run never double counts and never loses a delivery.
- **Oldest Pledge first means the oldest Request, then the line index.** A Pledge document is rewritten on every change, so its own age would reorder deliveries; the Request's creation is stable. A contract finished before a Request was posted is never counted toward it.
- **Delivery writes are batched by measured rules cost, not only by four lines.** The Firestore rules' 1000-expression budget is hit by one write of four lines each with 20 contract ids (and by two such lines); `batchLines` keeps a write within four lines and a measured cost budget, and a full line goes alone. This tightens the earlier "at most 4 lines" note, which assumed few contract ids. The rules test pins it.
- **The BPC "not as asked" flag is the Pledger's own view.** Contract contents never reach Firestore, so the requester cannot be shown it. ESI's Character contract-items route has no ME or TE, so runs is the attribute that can differ today.
- **Marking runs when the app is open and when a panel opens, with no setting;** a failed contracts read or save shows one quiet line in the panel and is retried by the next sweep. A Request closed or expired meanwhile refuses the write and the sync says nothing.
- **A contract counts only toward Pledges on a Request of the pilot it went to.** Each slot carries its requester's Character id and allocation is per requester, so a hand-over to one requester is never credited to another's Request.
- **ESI contract items carry no ME or TE, so the ticket's "ME 8, asked 10" example cannot be produced;** only runs is compared. Item reads stop at the first failure (a rate or error limit) and a contract that failed twice this session is skipped.
- **A refused Pledge write is quiet only when the Request is read back as closed or expired;** any other denial (session, rules budget) shows the failed-save note.
