# Scope decisions — A moon owner's grant also reads its Extractions into the Collector's book (issue #6097)

_Recorded 2026-11-12 · issue #6097._

- **A moon owner's scheduled read also reads its Extractions, with the grant it already holds.** `esi-industry.read_corporation_mining.v1` is the scope `/corporation/{id}/mining/extractions/` needs, so no new sign-in. It extends "the ledger read alone decides health" (`20261020-141656`) the way refinery names did (`20261021-084219`): after a good ledger read, best effort, never part of the moon owner's health. It rules out reading the moon owner's notifications (the Extraction started notification's ore), structures, fuel or timers.
- **A 403 on Extractions is remembered for 7 days on the moon owner's record (`extractionsRefusedAt`).** The endpoint needs Station_Manager in game, which a grant holder may lack; asking every run would spend the shared ESI error budget. An unanswered or rate-limited read is not kept, so the next run asks again. The next good read clears it.
- **Stored in the Collector's own `extractions` collection, tagged `sourceCorporationId`.** Absent means the book's own corporation, the same rule as observed rows (`20261020-132606`); additive, so every existing document and reader keeps working (dev and production share the Firebase project). Its rows are placed and stamped by it, and it gets a moon doc, like any Extraction. Like a moon owner's rows it never touches the book's `lastSync`, gaps or audit. An Extraction that says what the book already holds is not written again, by this read or the book's own sync, so a quiet run stays quiet.
- **A moon owner's coming chunk that ESI stops listing is marked cancelled.** The grant cannot read the Extraction cancelled notification, and a chunk that has not arrived only leaves ESI's list by being cancelled. Only on a whole (not truncated) list. A chunk that already arrived is kept as it is. The laser-fired time is not known for a moon owner either, so its window starts at the natural decay time.
- **A refinery known only from an Extraction gets its name looked up** with the same weekly structure lookup as a ledger refinery (`20261021-084219`), when the grant carries the structure scope.
- **A moon owner's refineries are the union of its ledger refineries and its Extraction refineries; "Mined" stays ledger-only.** The Moon owners tab still opens without ledger rows (`20261030-225738`): the view summary now also carries `refineryIds` (the refineries behind `refineryCount`, built from rows it already reads), and the tab unions them with the Extractions it already holds. A summary built before this shows the larger of the two counts until its next rebuild. `refineryCount` itself stays ledger-only, so "no ore yet is priced as Guests" does not move.
- **A corporation with no ledger row and no Extraction says "No mining or extraction seen yet", with its last read's age.** Own corporations too: their line keeps "no owner rate · no payouts" and gains the age.
- **Extractions names each row's corporation once any row is a moon owner's.** A book with only its own Extractions shows no corporation line.
- **What a moon owner sees of the book is unchanged.** `refineryIds` is the moon owner's own data and no page of theirs shows it.
