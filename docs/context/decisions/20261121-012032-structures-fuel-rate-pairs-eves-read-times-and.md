# Scope decisions — Structures fuel rate pairs EVE's read times and remembers the last measured rate (issue #6093)

_Recorded 2026-11-21 · issue #6093. Supersedes the "more than an hour apart" clause of `20261112-060350-structures-page-fuel-plan-reads-fuel-blocks-from.md`._

- **The bay and the expiry are paired by when EVE read them, not when the app fetched them.** Both corp reads keep ESI's `Expires`, and EVE's read is an hour before it (both routes cache for an hour). The app's fetch time is no use: a 304 resets it to now. That is how a refuel slipped through: the old 773-block bay paired with the new 27-day expiry gave 28/day for a structure burning about 120/day.
- **A rate is _measured_ only from reads within 5 minutes of each other.** If the bay is the later read, the pair still gives an _estimate_: a refuel between the two can only make it too high, which over-orders fuel rather than letting a structure run dry. If the bay is the earlier read, the pair gives no rate. A refuel there would understate both the rate and Needed.
- **The last measured rate is remembered per structure, on this device**, and used only when the bay is the earlier read, or when its read time is unknown. It shows as `~N/day`. A structure burns at one rate until its services change, and the two reads keep their hourly offset from one load to the next, so without this fallback that case would show no rate about half the time. The pair's own estimate always wins over the remembered rate, so a service brought online shows up as soon as the reads allow. Nothing is remembered for an unreadable bay or a dry structure.
- **With no rate to fall back on, the row says "Rate updating"** and Needed is unknown, which counts toward the footer's "N structures unknown". The rate is never a guess. Working the rate out from fitted service modules is still out of scope.
