# Scope decisions — Refinery systems learned from miners' own ledgers, kept on the moon owner record (issue #4650)

_Recorded 2026-10-21 · issue #4650._

- **The miner's client learns it; the server keeps it.** Only the miner's client holds both their own Mining Ledger (Dexie; refresh tokens never leave it) and their observed rows in the book. On loading the Moon Mining Tax tab it runs `ownerRefinerySystemsToLearn` (engine `learnRefinerySystems` on moon owner rows with no system) per Character and sends the result through `learnCorpTaxBookRefinerySystemsCallable`, under that Character's own session. Fire and forget: the personal ledger never waits on it. Supersedes "learning … is not wired" in `20261021-025114`.
- **Stored per structure on the moon owner record, `feeders/{feeder}.refinerySystems.{structureId}`, and copied into the view's `refineries/{id}.solarSystemId` in the same transaction** (the label precedent). Accounting officers read the record (`learnedSystemsOf` → `refineryFacts`), the moon owner reads the view, and every view rebuild falls back to the record. No rules change. A system a row carries always wins over a learned one.
- **The server trusts only what it can check.** It keeps a system only for a refinery the caller's own Character has an observed row at, from a moon owner, whose row carries no system; the system id must be a solar system id. The first learned system stays: a later report never moves it, which stops flip-flopping and limits a bad report to one refinery's label. The call always answers `{ ok: true }`, so it says nothing about the book. Audited as `refinerySystemLearned`.
- **Statements keep the label they were issued with.** Spec #4504 says nothing on whether an issued Statement follows a later label edit or a newly learned system, so Statements are unchanged.
