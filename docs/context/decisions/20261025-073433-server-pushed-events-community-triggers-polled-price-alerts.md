# Scope decisions — Server-pushed events: community triggers, polled price alerts and ship losses (issue #5121)

_Recorded 2026-10-25 · issue #5121. ADR 0027 records the model change._

_Amended 2026-10-29: ship losses are no longer server-pushed; see `20261029-000802-ship-losses-are-no-longer-server-pushed`._

- **The contract is per device, per Character, beside `eveTypes`.** Each `registerDevice` character entry gains an optional `serverEvents` (sorted, de-duplicated ids this device enabled for the browser channel, limited to the client's `SERVER_PUSHED_EVENT_IDS`) and an optional `serverInputs`. Stored on the device's registration doc as `serverEventsByCharacter` / `serverInputsByCharacter`; absent keeps what the device stored, as `eveTypes` does. The server stores ids it does not handle, so #5122 (skyhook and incursion nearby) adds its ids on the client and its handling on the server without touching the parser. A device that cannot show a pop-up (master off, browser gate off, no permission) uploads empty lists, never nothing.
- **Inputs travel at registration, not from synced data.** Price targets live in the Quickbar and the hub in `sync.marketHub`, both synced; the ship-lost minimum is in the synced feed-prefs blob. But sync is per account and optional, the synced blob is whole-value last-write-wins, and the server would have to read and parse three different synced shapes per Character. The device already sends the browser half of its choices, which never syncs; sending the four numbers it already reads for its own poll (`readServerInputs`, the same reads as `pollDomains/priceAlerts.ts` and `kills.ts`) is smaller and diffs exactly what the open app diffs. Bounded: 100 alerts, 200-character names.
- **Rollout is safe in either order.** The deployed `registerDevice` parser destructures only the keys it knows, so a new client's upload registers against the old function with the new fields ignored. Functions deploy manually and may trail the web deploy by days: until then nothing is pushed for these events and the open app still fires them. A new function with an old client stores nothing for them. The fingerprint includes the new fields, and the hourly re-registration re-sends them once the function is live.
- **Community events push on the backend's own write.** Two Firestore triggers: `pushCommunityAlert` on `communities/{id}/{collection}/{doc}` (acts on `requests` and `members` only; one trigger instead of two, at the cost of a no-op invocation on other Community writes) and `pushCommunityPledge` on `…/itemRequests/{r}/pledges/{uid}`. Create only: a re-ask refreshes an existing waiting-list doc and the poller does not re-fire it either.
- **A Member the admin let in from the waiting list is not pushed.** The join request already told them and they acted on it (the poller's "already waiting" rule). The admit path marks the Member doc `admittedFrom: 'request'` so the trigger can tell; the founder's own Member doc is skipped by uid. A Character who was waiting and then joins through a pre-approved mail invite is marked the same way. A doc written before this marker existed has no marker and pushes, which can only happen for a join that predates the deploy.
- **A Pledge pushes once, on create.** Under the client's rules: the requester's own open, non-standing Request that asked for the app, never their own Pledge. The key uses the Pledge's `updatedAt` at creation; the poller keys by the `updatedAt` it reads and groups a poll's new Pledges per Community, so a Pledge edited, or joined by others, before the open app polls can still file its own row. Likewise a withdraw and re-Pledge within one poll gap pushes (the poller only refires after seeing the withdrawal), and a re-asked join request keeps the first ask's key while the poller would key the latest. Accepted: at worst a second row in the bell, never a lost alert. No throttle on a Pledger creating and deleting a Pledge over and over: each create pushes to the requester. It needs a Community Member acting against another, and the admin can remove them; revisit with a per-(Request, Pledger) stamp if it happens.
- **Price alerts and ship losses ride the existing 15-minute `dispatchProjections` tick.** No new scheduled export or Cloud Scheduler job; the projection dispatch and this poll run side by side (`allSettled`) and the timeout rises to 540 s. One Fuzzwork call per hub station (lowest sell, as the app's `getHubPrices`), one zKillboard `losses/characterID` read per Character, spaced 1 s, capped at 300 a run and rotated so no Character is starved; a 420/429 stops loss reads for the run, and so does 5 minutes of wall time, since pushes and readings are written only after the reads and the tick's timeout is 9 minutes. A hash-only list (entries, none readable) is a failed read, as the app treats it, never an empty reading. A failed source keeps the last reading. Both send the app's User-Agent, which has no email address. Neither is ESI, so no `X-Compatibility-Date` is involved.
- **Edges mirror the Foreground Poller, per device.** Readings are kept on each device's registration doc (`serverEventBaselines`), dropped for an event the device turned off so turning it back on seeds afresh. Price: `diffPriceAlerts` mirrors `diffPriceAlertTriggered` (crossing, not "still above"; an edited target re-arms; no price never fires; Fuzzwork's outage keeps the reading rather than reading as no price). Ship lost: `diffShipLosses` mirrors `diffShipLost` (unseen ids, oldest first, first read seeds, minimum filter). Root parity tests run both side by side, and the Occurrence Keys and dates.
- **Rendering: raw fire, rendered in the service worker (ADR 0020's approach).** The push carries the fire as JSON plus a plain English floor title and body. The worker renders it with the same copy functions the poller uses (`serverEventCopy.ts`, taking the translate function so `sw.mjs` doesn't load `@/i18n`), names a lost hull and system through the public `/universe/names` it already uses, and keys the feed row with `occurrenceKey` itself, so the key is the poller's by construction. ADR 0010's pre-rendering doesn't fit: nothing is known ahead.
- **A push for an occurrence this device already toasted replaces that pop-up silently.** The worker must show something (WebKit revokes a silent push), so it reuses the poller's tag with `silent: true` instead of buzzing twice. Applies to every push, so an open app racing a Scheduled Push or an EVE notification push benefits too. "Already toasted" is the feed row's `notifiedHereAt` only (not a dismissed or day-old row). The tag is per Character and event, so a silent replay can replace a newer pop-up of the same event: accepted.
- **Price inputs are parsed leniently.** A bad alert, one past the 100 cap, or alerts without a station are dropped server-side rather than failing the whole registration (every Character's Projection rides the same call); the client clamps to the same bounds first.
- **A dead token deletes the registration only if it still holds that token** (a transaction): the tick can spend minutes reading, during which the device may have re-registered a fresh token.
- **Quiet Time applies; a ship loss counts as a loss.** `suppressPush` lets `shipLost` through when "Let attacks through" is on, the setting's own "attack and loss alerts" wording.
- **Settings shows the closed-app badge for these five, with its own tooltip** ("Arrives even with the app closed", no 72-hour promise). It shows from the web deploy, before the functions deploy makes it true; acceptable for the short gap.
