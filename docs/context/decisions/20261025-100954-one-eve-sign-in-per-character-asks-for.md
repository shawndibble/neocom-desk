# Scope decisions — One EVE sign-in per Character asks for every permission its Device-ticked events need (issue #5156)

_Recorded 2026-10-25 · issue #5156._

- **Ticking never signs in.** The Device checkbox stays the only per-event control; Settings → Notifications → Alerts when closed reads the ticks (`alertsNeeds.ts`) and says what each Character is missing, in one line ("2 Characters need a sign-in for: EVE notifications, nearby alerts, and new mail").
- **The walk replaces Turn on, Add nearby and Add mail.** One sign-in per Character that needs anything, asking for the union of what its Device-ticked server-pushed events need (location for the two nearby events, mail for `newMail`), notifications if any EVE-notification type is Device-on, and every scope its grant already holds (a re-authorization replaces the token with exactly what is requested). A Character that holds all it needs is skipped; one with nothing ticked that needs a grant is never asked. Per-Character unions differ, so each walk step carries its own scopes, decided before the first sign-in.
- **The listing is the consent, and amends ADR 0029.** `newMail`, `incursionNearby` and `skyhookRaidableNearby` default to Device-on, so a default would otherwise widen the token without the player choosing. Every walk starts with a screen listing each permission, why, and for which Characters; location and mail carry a checkbox (on by default, because the player ticked the event, or left the default, and is reading the list) and unchecking one leaves it out of this walk only: those alerts then work while the app is open, and the `Left out` line says to untick the event's Device box to stop being asked. We chose a leave-out on the listing over writing preferences on the player's behalf: the walk never changes a tick. A scope a grant already holds is never dropped. The consent for mail is therefore the listing shown and Continue pressed, not a separate per-Character button.
- **No nag state kept.** A permission left out is asked again on the next listing while the event stays ticked; we do not persist a "declined" flag. Unticking the event is the durable way to stop.
- **Rollout.** Unchanged from ADR 0028/0029: a scope is planned only when `registerDevice` has answered `nearbyGrants` / `mailGrants`, and `beginAlertsLogin` re-checks it before building the request. A Character whose device sign-in lacks the scope an event reads is not counted as ticked (the row is locked in the list and the registration drops it).
- **The first-run offer is unchanged**: notifications plus location when the server takes it, never mail, with its copy saying so; the Settings walk then lists mail.
- **Future permissions ship as one grouped release** (order fills and the like), so players re-authorize once rather than once per feature.
- **Client-only.** `saveAlertGrant` already accepts any combination of the three scopes that includes notifications; no functions change.
