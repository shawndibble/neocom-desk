# Scope decisions — Register the corp wallet transactions endpoint and give it a filtered tab (issue #570)

_Recorded 2026-09-07 · issue #570._

- **Registering `/corporations/{corporation_id}/wallets/{division}/transactions` costs no new scope and invalidates no login.** ESI secures it with `esi-wallet.read_corporation_wallets.v1` — the same scope `getCorporationWallets` and `getCorporationWalletJournal` already carry, already in the `corp` group, already claimed by `canReadWallet`. `esi/scopes.ts` derives the consent screen from `ESI_REGISTRY`, so the concern this had to clear was a forced re-grant for every corp user, and the registry answers it outright. This rules out treating "the corp side has no transactions tab" as a product decision: `features/corp/wallet.ts` said in as many words that it was a registry fact, and the fact has changed.
- **`x-required-roles` is `['Accountant', 'Junior_Accountant']`, identical to the journal, so `canReadWallet` is the whole gate.** Read off ESI's own spec rather than inferred from the shared scope — a scope and an in-game role are two separate halves of a corp gate (`engine/corpRoles.ts`), and they do not have to agree. Because they do agree here, the tab needs no new Corp Capability, and it hides rather than locks like the rest of the corp UI (CONTEXT.md round 35).
- **The corp payload is the character payload minus `is_personal`, checked against the spec rather than assumed.** `WalletTransaction` splits into `WalletTransactionCommon` plus that one character-only field, and `transactionTotal`, `walletTransactionsCsvColumns` and the new filter are all typed on the shared half. This rules out a parallel corp type that could silently gain a field ESI does not send — the same trap `CorporationAsset` documents having checked for.
- **The two corp wallet reads paginate differently, and that is ESI's doing.** The journal is X-Pages; the transactions are cursored on `from_id` like the character's, capped at `MAX_TRANSACTION_PAGES`. The cursor walk is now one shared function rather than two copies, because the exclusive-cursor subtlety in it (`from_id` already excludes the lowest id seen, so subtracting 1 skips a transaction) is exactly the kind of thing a second copy gets wrong. Both reads still reach the view as a `TruncatableResult`, so `truncated` means one thing to the panel: "there is older history this list does not have".
- **Free text searches the item name _as drawn_, and the filter is told how to spell it.** A journal line carries its own `description`; a transaction carries only a `type_id`. So `filterWalletTransactions` takes the same `nameFor` the table's item column renders with, and a `type_id` whose name never resolved matches on the `Type #99999` text actually on screen. This rules out giving the filter its own name map, which would let a pending resolve quietly drop rows the eye can see — the one failure a search box must not have.
- **The tab is corporation-only, and a personal wallet keeps exactly two tabs.** The character's fills are Market's Transactions tab, so a third entry on the personal side would either duplicate it or navigate away from the page, and neither is a tab. `?tab=transactions` is still parsed for everyone — the owner is not known at parse time, and `?owner=corporation&tab=transactions` is a link the corp view wants — but it resolves to Balance for a personal wallet rather than rendering a panel with no entry above it.
- **Nothing is fetched until the tab is opened, and not again after that.** One cursor walk per division on a rate-limited corp endpoint is a real cost, so the snapshot key is `null` until the tab is selected, then held alive by a visited-key so a tab toggle does not re-walk it — the same treatment #413 gave the corp journal. A division or corporation change still resets it.
- **"This division has never traded" and "nothing matches your filters" stay separate answers.** With no rows at all the filter bar is not drawn, so the page does not invite the user to adjust a filter that is not the reason the table is empty.
- **The corp panel has a filter bar and Market's character panel still does not.** Left asymmetric on purpose: a corp division's fills are the many-Characters case, where "what did we buy last Tuesday" is worth a control, and the character list is much smaller. Matching the two up is a separate call, and so are the `location_id` and `client_id` columns — both are on the corp rows and both need name resolution neither table does today.
- **The From/To pair moved into `components/ui/DateRangeFields.tsx`.** Two filter bars one tab apart now need the same control, including its `display: contents` inline / real-row-in-the-sheet behaviour, which exists because `useFilterSurface` is a hook and `FilterBar` renders its children itself. A second copy would have been a second thing to get wrong about the mobile sheet.
