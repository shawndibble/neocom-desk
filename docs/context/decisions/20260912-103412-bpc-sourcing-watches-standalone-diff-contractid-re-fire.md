# Scope decisions — BPC Sourcing watches: standalone diff, contractId re-fire key, feed-only delivery (issue #926)

_Recorded 2026-09-12 · issue #926._

- **A BPC Sourcing watch's poll/diff logic is a standalone loop (`features/bpcContracts/watchPoller.ts`, `engine/contracts/bpcWatch.ts`), never a `NotificationEventDef` in `features/notifications/events.ts`.** Every entry in that fixed catalog scopes to one Character's own ESI state; a saved search over the shared Public Contract Offers snapshot has no Character to scope to. `ForegroundNotificationPoller.tsx` calls `runBpcWatchPoll` alongside `runForegroundPoll` on the same interval — cadence only, not the `pollDomains.ts` registry.
- **Re-fire identity is `contractId` alone**, even though `20260908-212747-a-bpc-offer-row-has-no-identity-of.md` established that a BPC offer _row_ has no identity within one contract listing several copies. That decision was about `DataTable`'s reconciliation key; this one is about what a buyer would act on. Several rows sharing one `contractId` are the same real listing repeated per quantity split — notifying once per contract, not once per row, is correct here even though it would be wrong for the table.
- **"Cheaper" means a new all-time low ever observed for the watch** (`BpcWatchState.minPriceSeen`), not merely cheaper than the immediately preceding poll. A watch re-diffs the same rows every 5 minutes; comparing only against the last poll would re-fire every time the market happened to tick back down to a price already seen and rejected.
- **`seenContractIds` is replaced wholesale each poll, not accumulated forever.** A contract that rolls off the snapshot and a different one later reusing a similar id range is not something this diff tries to distinguish — bounding the baseline to "what matched last poll" avoids an ever-growing set for what is, in practice, a fast-churning public listing.
- **Editing a watch's filter clears its baseline** (`updateWatchFilter`): a changed search is a fresh, unobserved one, the same re-arm-on-edit rule `20260909-192510-quickbar-price-alerts-re-arm-key-hub-price.md` gives a Quickbar price alert's target.
- **Delivery is feed-only** — no browser/OS notification path. A watch match carries no OAuth scope or Character to gate a browser notification the way every other Notification Event does; the Notification Feed needs only the master + feed-channel switches, both of which `runBpcWatchPoll` still checks so a pilot with notifications off doesn't accumulate feed rows.
- **The feed row's `eventId` is the literal string `'bpcSearchWatchMatch'`, shared by every watch**, not a per-watch id. This satisfies the acceptance criterion (delivery lands in the Feed) but means the Alerts page's type-grouping collapses matches from different watches into one group, distinguishable only by opening each row's body — the mockup's "grouped by the watch's own name" is not literally implemented. Left as-is: the mockup was explicitly non-binding in the issue, and a fix would mean either minting one synthetic Notification Event id per watch (defeating "not a `NotificationEventDef`") or extending `alertGroups.ts`'s grouping key past `eventId`, both bigger than this ticket's scope.
- **"Edit" is rename-or-replace-the-whole-filter, not an in-place field-by-field edit.** The watch list's row offers three actions: rename, "update to current search" (re-runs `createWatch`'s filter-capture logic and re-arms), and delete. There is no dedicated filter-editing form — re-running the search with the desired criteria and clicking "update to current search" is the intended path.
