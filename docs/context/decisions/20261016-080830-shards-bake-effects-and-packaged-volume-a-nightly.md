# Scope decisions — Shards bake effects and packaged volume; a nightly job rebakes on a new game build (issue #3884)

_Recorded 2026-10-16 · issue #3884._

Supersedes the "Readers of fields the shards lack stay on cached ESI" bullet of `20261016-024237-every-description-and-dogma-attribute-reader-goes-baked.md`.

- **The typeInfo shards now carry dogma effects and packaged volume, so hardpoint kinds and Hauling's volume fallback read baked first too.** `effects` is every effect id, plus `defaultEffect` for the one ESI marks `is_default`. It is required, `[]` when a type has none, because a missing list would read as "takes no hardpoint" and be cached that way. `packagedVolume` is stored only where it differs from `volume`; `loadTypeDetail` hands out `packaged_volume` as that or `volume`, as ESI does. Only notification copy (`name`) still needs ESI. The shards grew from ~1.33 MB to ~1.37 MB gzip, this change plus a newer game build.

- **Packaged volume comes from CCP's `types.jsonl`, not an ESI probe.** It matched ESI's `packaged_volume` on all 682 probed market types with a distinct figure. The build used to probe ESI once per market type (~20,000 calls, cached on disk); it now makes none for this, which a nightly CI rebuild needs.

- **A bake reads one game build from both sources, and records it.** Fuzzwork's CSVs are fetched from the build-numbered dump `/dump/latest/` points at and cached under that name, so a cache can no longer serve an older build's tables. The build fails when that dump and CCP's export are on different builds (`SDE_ALLOW_BUILD_MISMATCH=1` overrides, for local experiments). It writes the build to `scripts/sde-build.json`, outside `public/data` so it is never shipped.

- **`.github/workflows/sde-refresh.yml` rebakes nightly when CCP and Fuzzwork agree on a newer build, and opens a PR that auto-merges once CI is green.** Fuzzwork trails CCP by hours to days, so it waits for both. A red PR, or a bake whose sanity checks fail, waits for a human: a failed run opens or comments on an `sde-refresh` issue. The PR is opened with a fine-grained token (`SDE_REFRESH_TOKEN`), because GitHub starts no CI for a PR opened with `GITHUB_TOKEN`. One PR per build (`sde/build-<n>`): a build that already has one, open or closed, is skipped, so a closed PR stays turned down; a newer build's PR closes an older one still open. If Fuzzwork still lags a CCP build the bake lacks after 3 days, the run fails and files the issue instead of waiting silently. The checkout keeps no credentials; only the push step sees the token, and its commit is authored as the token's owner.
