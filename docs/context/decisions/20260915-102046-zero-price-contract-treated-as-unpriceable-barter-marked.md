# Scope decisions — Zero-price contract treated as unpriceable barter, marked not filtered

_Recorded 2026-09-15 · issue #1080._

- **A zero (or negative) contract price is treated as unpriceable, never as a real price of zero.** A barter contract ("take this blueprint, give me 122 PLEX") has an ISK price of zero, but that zero answers a different question than "what does this cost" — the requested side is discarded upstream with no trace (a settled decision this ticket does not reopen), so the published row's price is the ISK-only remainder, not the item's value. Every surface that reads a price treats `price <= 0` the same "unknowable" way every other bad-data path in this feature already does: excluded from selection, sorted last, never named in a notification.

- **A genuine giveaway is indistinguishable from a barter on this data, and is treated the same, safer way.** Nothing in the snapshot records whether a contract asked for something in return once its requested lines are dropped, so there is no honest way to tell "free" from "barter" apart. Treating both as unpriceable is the direction that cannot silently reseed a Build Plan or ratchet a watch to zero; the cost of the (likely rare) real giveaway is that it also reads as unpriceable rather than free.

- **No new stored field, no flag on the crawl, no re-sync.** The zero is already on every row; the fix is entirely in how existing consumers read it. A crawl-side flag recording that a contract has a requested side is named as a fallback for a barter with a _non-zero_ ISK price (e.g. "pay me 50M and 10 PLEX") — the live sample contained none of those — and is deliberately not built now.

- **Blueprint Acquisition's cheapest-purchasable-tier selection and a BPC Watch's baseline exclude a zero-price offer entirely, the same way they already exclude a multi-type one** (`20260915-093419-multi-type-contract-price-treated-as-unknowable-never.md`). A watch's "new offer" fire, unlike a multi-type row's, never names a zero-price contract either — a multi-type row's price is real, just misattributed, so a caveated "new" fire is still honest; a barter's price has no honest number to state at all, so it is excluded from "new" outright rather than fired with a caveat. It is still recorded into the watch's seen-contract set, so it does not read as perpetually "new."

- **Contract Search marks a zero-price row rather than filtering it out of the results.** A real contract a player might genuinely want is not hidden — its item search stays a complete corpus — but it sorts last, in both the default cheapest-first view and the price column's own sort, and its price cell carries an "Asking for goods" marker pointing at the contract detail, which already renders a barter's requested lines with their own badge. This is the one surface #1076 (the sibling multi-type ticket) explicitly exempted, because a bundle's whole price is a real answer to "what would I pay" there — a barter's zero is not.

- **BPC Sourcing's own price cell is not marked.** Only Contract Search's default sort put a zero-price row at the very top of the page; BPC Sourcing's protections (the cheapest-tier exclusion above, and the ISK/run figure returning null) remove the harm without needing a second visual marker on a surface the ticket did not name as damaged by the raw number showing.

- **Every per-type/per-region "cheapest" aggregate excludes a zero-price row too, not only the row-level sort/selection above.** `bpcPriceSummary`, `cheapestByRegion` (BPC Sourcing's blueprint-type headline and region breakdown) and `contractOfferStats`/`contractOfferPriceSummary` (Contract Search's suggestion list and type-summary chips) all fed their own independent min-reduce over raw prices — a barter row would still win "cheapest" there even after the row-level fixes above, since these are separate code paths, not derived from the sort. Fixed the same way: a zero-price row still counts toward `offerCount`, but `cheapest`/`median` are computed only from priced rows, `null` when none exist. A region or type whose every offer is unpriced is omitted from `cheapestByRegion` entirely (no non-null `cheapest` to report), matching `bpcPriceSummary`'s existing `null`-for-no-real-price convention rather than inventing a `0`.
