# Scope decisions — Courier contracts get a sibling snapshot, not more rows in the offers collection (issue #909)

_Recorded 2026-09-12 · issue #909._

- **Courier rows go to their own `publicCourierContracts` collection, not into `publicContractOffers`.** A courier contract has no `contract_items.csv` rows, so a courier row shares nothing with an offer row beyond contract identity: no `typeId`, `price` or `quantity`, which is what every existing reader of the offers snapshot filters and sorts by. `writeChunkedSnapshot` also replaces one snapshot from one row array, so two row shapes in one collection is not expressible there without a discriminated union and a branch in both readers. The ticket allowed either; this rules out any change to what `publicContractOffers` contains, so `src/engine/contracts/*` and BPC Sourcing are untouched.
- **The courier snapshot is published by `syncPublicContractOffers`, off the same single archive fetch — not a fourth scheduled function.** Issue #907 spent a ticket collapsing a second public-contracts crawl back into one to stay inside the 3 free Cloud Scheduler jobs per billing account that ADR 0013 budgeted against; a new scheduled job here would re-create exactly that. The cost of the extra snapshot is one accumulator held during the existing pass and ~2 writes per run.
- **A courier row is published only when it states both endpoints, a reward and a volume; `collateral` and `days_to_complete` are omitted when blank.** `Number('')` is `0`, not `NaN` — the trap the #906 decision record already names — so converting an absent column unconditionally would publish a delivery to station `0`, a free haul, or an empty hold, none of them distinguishable from a real value and none a job anyone can take or rank. Collateral and deadline are different: a real `0` (a favour run) is information, so those follow the omit-don't-zero rule the offer rows apply to ME/TE/runs rather than being required.
- **The required-column rule is a schema guard, not an expected filter, and it is observable.** ESI's own schema (`GET /contracts/public/{region_id}/`) documents `end_location_id`, `reward` and `collateral` as "for Couriers contract" and populates them on exactly these contracts — which is why the pre-#909 courier test fixture, a retyped item_exchange row, has `end_location_id` blank. But none of those columns is in ESI's `required` set, so a schema change could make the drop rule discard every row and publish a clean empty collection. `syncPublicContractOffers` therefore logs `outstandingCourierContracts` beside `courierRowCount`, both behind one shared gate (`isOutstandingCourierContract`) so that contract type and expiry cannot open a gap between them: any gap at all is a required column gone blank.
- **The contract type is matched as `type === 'courier'`, not as the complement of `SEARCHABLE_CONTRACT_TYPES`.** ESI's `type` enum is `unknown | item_exchange | auction | courier | loan`; neither `loan` nor `unknown` is a haul to take, so the complement would have published both as courier rows.
- **#909 is ingestion only — no client reader, no UI.** Its acceptance criteria stop at the Firestore collection and the unit tests, so the snapshot is written and nothing reads it yet. That is the ticket's shape, not an oversight; a hauling search over it is follow-up work. Rules out adding a Contracts-page tab or engine module here.
