# Scope decisions — Corp Tax Book prompts the Statement run and dots the Moons nav (issue #6208)

_Recorded 2026-11-15 · issue #6208._

- **One run sends every missed period, oldest first.** The Statements tab's run plans `nextRunPeriod`, then the next period on a view that already holds the earlier period's Statements (`planStatementRuns`), so a forgotten month goes out with the next one and the later Statement's carried balance includes the earlier. Each period is issued, then its mail queued, before the next starts: a failure part-way keeps what was issued (and queued), and the next run bills the remaining periods and offers any Statement whose mail never left. A Miner gets one mail per Statement, so two missed months mean two mails; the queue's pace (one every 12–15 s, tab open) is EVE's limit and is unchanged. All of a run's Statements share its issue time, so they fall Overdue together. Under the minimum, a period still rolls into the next one in the same run.
- **The run stays a click, never automatic.** Automatic sync still never issues a Statement or sends mail: mail goes out from an officer's Character in an open tab. "Needs you" carries one card, "Statements ready for {periods}", whenever a closed period has Billable days on no Statement that a run would bill (a period whose every Miner is under the minimum rolls on and gets no card); its title links to the Statements tab, where the run is. It counts as one card however many periods are listed. It is computed from the whole-book view on both the read-model and live paths, so it adds no kind to `NeedsYouItem`.
- **The corp Moons nav entry wears the attention dot, not a count, for a book editor.** It lights while "Needs you" has a card (including the run card) or Automatic sync has stopped: one thing to go and handle, the existing §6c dot (`NavItem`'s `attention`). A count would mix cards and a stop, which are not the same unit. The book is too heavy to load in the shell, so each Moons visit stores what it found per Character and corporation in Dexie and the nav reads that; only an editor's visit stores it, and a viewer's visit clears it. Between visits, the open app rereads the one Automatic sync status doc every 30 minutes (visible Tab Leader only, never minting a token, and only for a Character whose editor visit is on record), so a stop lights the dot without a visit. Overdue, Unmatched and a due run move only on a visit or a reload of the book. A visit that finds no book, or no access to it, clears the dot. Statements issued earlier whose mail never left raise no card: the run offers them whenever it is opened. The phone's More button does not echo it: the Moons page is desktop work.
- **A stopped Automatic sync is also a server-pushed alert, "Automatic sync stopped" (`corpTaxBookSyncStopped`), from the existing scheduled job.** It fits ADR 0027 with no new deployed function: `syncCorpTaxBooks` calls `deliverServerEvent` after `stopGrant` commits, as the vetting router does for `vettingShared`. It goes to the book's editors: officer records with edit rights checked in the last 30 days, plus the holder unless they lost the role or left the corporation (each Character once, 25 at most). It is not raised when the book was turned off on purpose (`book-off`). Like every server event it reaches only devices that opted it in (offered to every Character, default both channels, under World like vetting, since it needs no Corporation Permission and fires with the app closed), it never throws, and the run waits at most 5 s for it. A Collector (moon owner) grant's stop sends none. Functions are not auto-deployed, so it is live only once `syncCorpTaxBooks` is redeployed.
