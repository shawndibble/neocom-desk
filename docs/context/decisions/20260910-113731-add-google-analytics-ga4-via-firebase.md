# Scope decisions — add Google Analytics (GA4) via Firebase

_Recorded 2026-09-10._

- **Google Analytics (GA4) is wired through the existing Firebase project via `firebase/analytics`, dynamically imported and gated on `VITE_FIREBASE_MEASUREMENT_ID` being set (blank in local dev, e2e, and the test runner) plus a runtime `isSupported()` check** — no separate gtag.js snippet. `app/analytics.ts` reads `measurementId` off the same `firebase/app` instance `sync/firebaseApp.ts` already exposes; this is a second, named exception to that file's "sync only" scope (ADR 0001), alongside the existing `publicBpcContracts` one (ADR 0013). Rejected loading `firebase/analytics` unconditionally at module scope — this repo already keeps Firestore on the `lite` build to avoid bloating the main chunk, and the same reasoning applies here.
- **`AnalyticsPageViewTracker` (mounted once, inside `BrowserRouter`, alongside `ReloadPrompt`/`WhatsNewPanel`) logs a `page_view` on every route change, using the matched route _pattern_ (e.g. `/skills/plans/:planId`) rather than the raw pathname.** Two routes carry an id in the path (`/skills/plans/:planId`, `/wallet/loyalty/:corporationId`); logging the raw pathname would make GA4 page paths high-cardinality and could leak an EVE corporation ID into analytics data. Firebase Analytics does not itself listen for `pushState`/history changes (that behavior belongs to gtag.js's Enhanced Measurement, not this SDK), so this manual per-navigation call is the only source of page_view events — no double-counting risk.
