# Scope decisions — Moon owner money: settled otherwise keeps what was owed, only an agreed rate accrues, payouts need the reference (issue #6209)

_Recorded 2026-11-15 · issue #6209._

- **Settled otherwise applies from its effective day only: what accrued before it stays owed, on the pay list and payable.** `feederBalance` no longer zeroes a balance while the mode is on; it shows `none` only once nothing is owed (even or credit). Days in the settled spell still accrue nothing. This supersedes the second bullet of `20261020-172643` ("keeps no balance … never on the pay list"). Turning it on or off mails the moon owner's CEO and payee through the Officer mail queue (`mode-change`); a note edit alone does not, and a same-owner corporation is never mailed.
- **A requested rate never takes effect on its own.** `effectiveOwnerRate` is the agreed rate in effect on the day; before the first agreed rate, that first one is backdated over the earlier days. With no agreed rate at all, covered Billable days accrue nothing and wait as `pending` (the view summary's `pendingValueIsk`); they count once a rate is agreed. This supersedes the Owner rate rule "the Agreed rate if one exists, else the Requested rate" and, for the first agreement only, "every entry applies from its effective-from day and never reaches back". The rate a moon owner names when it joins is a request like any other, so it accrues nothing until agreed; an invite's offered rate is stored as agreed and accrues from joining. Every server read of the effective rate (the view, the moon owner's status call) uses the engine rule. A moon owner with a request still waiting (nothing agreed, or a request after the last agreement asking for another rate) has the status `rate-asked` and counts in "Needs a look".
- **A donation is recorded as a payout on its own only when its reason carries the payout reference (`PAYOUT_REASON_PREFIX`, "Moon mining payout", any case).** The pay dialog writes it. Any other outgoing donation to the moon owner or its payee (an SRP refund, say) is recorded `notAPayout: true, unconfirmed: true`, counts for nothing and is listed for an officer to "Count it" or mark "Not a payout"; either clears `unconfirmed`. An officer's own "I've sent it" still attaches to any donation, and folds into an unconfirmed row (counting it). A row created before this keeps counting as it was. The prefix is an engine constant, not i18n text, because the server matches it.
- **The moon owner can flag a payment it disputes, or withdraw the flag** (`disputeCorpTaxBookFeederPayoutCallable`, a corpTaxBook router action). It writes `disputedAt` on the payment and changes no figure; the accounting side sees "They dispute this payment".
- **A day held while a moon owner's ledger cannot be read is never closed as paid.** While a moon owner is stale, every miner with a row at its refineries is held from its first unread day: the miner's recorded paid-through stops the day before, own-refinery days included, so ore read later for those days is billed instead of being written off as recorded after payment. The hold lifts when the ledger reads again or the moon owner's coverage ends (a disconnect closes it). A miner who never mined at that moon owner is not held.
- **Ore with no saved open price is valued for the moon owner at the unit price the miner's line was billed at, before 0.** Both sides read it from Late notices' lines (by line key; the server only when some row is unpriced), so they show one figure; a live price is never used. This supersedes "else 0 and counted as an unpriced day" in `20261020-175727` for a day a notice listed; a day no notice listed is still unpriced.
- **A view summary built under these rules carries `rulesVersion: 2` (`FEEDER_VIEW_RULES`, mirrored) and the record's `mode`.** The Moon owners tab only stands a summary in for the rows when both match; an older summary is priced from rows until the next rebuild. `schemaVersion` stays 1 so a client from before reads summaries as it did.
