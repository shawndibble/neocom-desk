# Scope decisions — Chunks import each other through an import map

_Recorded 2026-10-23._

- **Chunks import each other by stable names that an import map in `index.html` resolves to the hashed files (`build.chunkImportMap`), so a deploy renames only the chunks whose own code (or preload lists, below) changed.** Before this, a chunk's file name carried its imports' hashes, so a changed leaf renamed every importer, and every importer of those. The entry changes on every deploy (it carries the release), so every chunk that imported it was renamed too. Measured in CI on two builds of one tree with different releases (791 js/css files, 513 lazy):

  | Change since the last build   | Production until now | No map, no Sentry stamp | Map, no Sentry stamp          |
  | ----------------------------- | -------------------- | ----------------------- | ----------------------------- |
  | release only                  | 785 (2.8 MB gzip)    | 336                     | **1** (the entry, 99 KB gzip) |
  | one `src/lib` leaf (`isk.ts`) | 786                  | 360                     | **4** (133 KB gzip)           |
  | one route page                | —                    | 336                     | **2**                         |
  | one lazy `en.json` string     | —                    | 336                     | **2**                         |

- **A chunk is also renamed when its preload lists change (`preloadGraphSignature`, folded in through `augmentChunkHash`).** Vite writes each `import()`'s preload list (`__vite__mapDeps`: the target, everything it statically imports, and their css) after the hash is fixed. With the map alone, one probe broke content addressing: a route page gaining one static import left 6 chunks with their old names and new bytes, `routeChunks` and `Layout` (boot) among them. The precache (`revision: null`) and the `lazy-chunks` route never refetch a name they hold, so a pilot would keep the old list for good. A list that names a stable key the map no longer has 404s, and `#stale-build-boot` turns that into a worker unregister and reload. With the signature the same probe renames those 6 and leaves no chunk with the same name and new bytes. A graph edit renames the chunks whose `import()`s reach it (34 for that probe); a code-only edit renames none of them.

- **The Sentry plugin no longer stamps the release into every chunk (`release.inject: false`).** In the deploy build it prepended `SENTRY_RELEASE={id:<release>}` to every chunk, and the release carries the commit, so production renamed every chunk on every deploy, map or no map (the "Production until now" column). `Sentry.init` already sets `release` (`src/instrument.ts`), and source maps match on the per-chunk debug ids, which stay.

- **Amends** `20261023-095831-only-the-boot-graph-is-precached-route-chunks.md`: its "an ordinary deploy invalidated ~360" is now a handful, so the idle warm re-downloads only what changed. Everything else there stands. `lazy-chunks.json`'s `entry` still names one build: the build fails if the entry chunk stops carrying the release (`entryNamesRelease`). `bootClosure` follows imports through the map and fails the build on an import that resolves to nothing, so the boot graph cannot shrink quietly.

- **Every page carries the map, ahead of the entry loader.** `index.html` and its copy `404.html` (the landing shell is the same page). `deferEntryHtml` now runs on the emitted page: Vite writes the map after every plugin's html hook, before the first module tag it finds, and with those tags already swapped for the loader it found none and put the map ahead of the doctype. The build fails if the map is missing, doubled, after the loader or before the doctype (`importMapProblem`). `importmap.json` is still emitted beside the page, for comparing deploys, and is not precached.

- **Trade-off: the page is ~55 KB bigger (raw), ~19 KB gzip (787 entries).** `index.html` goes from 22 KB raw / 7 KB gzip to 77 KB / 26 KB, and the map sits in `<head>` before the stylesheet link. It is downloaded on every navigation that misses the service worker (first visit, the landing page). If PageSpeed shows a landing-page regression, the next step is an early `<link rel="preload" as="style">` ahead of the map. Not a module-script move: the loader has to follow the map.

- **Out of scope, unchanged.** Module workers get no import map: Vite builds them with `worker.rolldownOptions`, which leaves this off, and their chunks import real file names (checked on the CI build). The service worker is built separately (`configFile: false`) and is one file. Every browser the build targets supports import maps and `import.meta.resolve` (Vite's default target: Chrome 111, Firefox 114, Safari 16.4). An older browser that ran the app before (Safari before 16.4, Firefox before 108) now fails to boot: the entry imports its vendor chunks by stable name. The `vite:preloadError` and stale-build paths are unchanged, and they now fire less: an old tab's map still names files a newer deploy kept.
