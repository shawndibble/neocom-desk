# Scope decisions — Undercut alerts classify the station tier in the Foreground Poller (issue #1423)

_Recorded 2026-09-24 · issue #1423._

- **This supersedes `20260914-135534-often-undercut-flag-samples-on-the-open-orders.md`'s "not in the poller" point, for this one event only.** That decision kept station classification out of `pollDomains.ts` because the cost was an uncached Fuzzwork request per station every 5 minutes for every character with the app open, whether or not anyone was looking at Open Orders. `marketOrderUndercut` pays that cost deliberately, and it is now cheap: `getStationPrices` (`src/market/prices.ts`, factored out of `getHubPrices`) shares the same 15-minute in-memory TTL cache the Open Orders page itself reads through, and the whole fetch is skipped when this event is off for every character (`marketOrderUndercutDomain`'s own domain gate, same shape `spExtractionDomain` uses for its opt-in check). The Often Undercut page-side sampling (#1018) is unaffected — it keeps sampling from the page's own `buildOpenOrderRows` run, unrelated to this poller's own classification.

- **The tri-state problem: an `armed` latch on the stored snapshot, not a frozen `state`.** The obvious shape — compare `prev.state`/`next.state` pairwise — cannot tell `clear → unknown → beaten` (must fire) apart from `beaten → unknown → beaten` (must stay silent): both look identical as a two-snapshot diff once `unknown` is in the middle. The fix is not to freeze `state` itself (an `unknown` poll's classification is still stored as `unknown`, honestly), but to persist a second field, `armed: boolean`, computed once per poll per order and carried in the same stored baseline `diffMarketOrderUndercut` reads:
  - `clear` → stores `armed: true` (a `beaten` reading on a later poll should fire).
  - `beaten` → stores `armed: false` (already reported; a later `beaten` reading alone must not fire again).
  - `unknown` → stores whatever `armed` **was** before this poll (frozen) — a Fuzzwork outage must neither arm nor disarm anything, since it proves nothing about the order either way.

  Firing rule: `next.state === 'beaten'` AND the order was armed _before_ this poll — computed as: no baseline for this character at all → never armed (module-wide first-poll-silent rule); order missing from the previous poll's entries → armed (owner decision 5: a brand-new order already beaten on its first sighting still fires); the order's own price changed since the previous poll (a relist) → armed (owner decision 4); otherwise → the previous poll's own stored `armed` value. Both the domain's `toSnapshot` (deciding what to persist) and the diff (deciding what to fire) share one pure helper for this — `wasArmedBefore` in `engine/notificationDiffs.ts` — so the two computations cannot drift apart.

  This also covers the case the brief's own diff test list left out: an order beaten at price P1, relisted at a new price P2 while still beaten, must alert again (an acceptance criterion), even though `state` never left `'beaten'` — the price-changed branch of `wasArmedBefore` is what fires it, independent of the `state` transition.

  `diffPriceAlertTriggered`, which the ticket brief cited as the shape to mirror, does **not** actually carry anything forward across a null-price poll — `prevEntry.price === null` reads as "not previously crossed" every time, so a `beaten → unknown → beaten`-shaped sequence there would incorrectly fire twice. It was not a working precedent for the tri-state problem, only for the ordinary edge-trigger and the "missing from prev still fires" shape; the `armed` latch above is new to this event.

- **The classifier does not reuse `buildStationTier`'s null handling.** `buildStationTier` (`openOrdersModel.ts`) reads a null best-price as "no rival" (`beatsMe: false`) — correct for its badge, wrong here, where `null` must mean `unknown` (Fuzzwork gave no answer), not `clear` (Fuzzwork answered: no rival). The two are distinguishable in practice because the order being classified is always present at its own station: my own open order guarantees at least one order on my own side there, so a null price on _my own side_ can only mean the fetch failed or was never made — never a genuinely empty book. `engine/market/stationUndercutState.ts`'s `classifyStationUndercut` is a new, small function for this reason, reusing only the strict-comparison direction rule (`buildStationTier`'s "only strictly better counts") and not its null fallback.

- **Occurrence Key extra part is the order's own price** (owner decision 4), giving `[characterId, eventId, orderId, price]`. A relist is a new occurrence; a beaten → clear → beaten cycle at an unchanged price reuses the same key, so the diff still fires (each transition is independently real) but `alreadyDelivered` suppresses the repeat browser toast, and the feed row for that key is overwritten in place rather than duplicated — the same anti-flap shape `corpWalletThreshold`'s `transactionAbove` and every other natural-id key already produce, not a new mechanism.

- **Step 9 (OpenOrdersPanel highlight): reveals the row through local component state, not by writing to the URL filter.** The brief's own fork — clear the active filter vs. show a "not shown by current filter" note — turns out not to be reachable in practice for this event: `OpenOrdersPanel`'s filter is entirely URL-derived (ADR 0015, `useUrlParams`'s "read-only defaults... nothing here writes back to a stored setting"), and a notification's `data.url` is a fresh, complete path built by `notificationUrlForSubject` — clicking it replaces the address bar's query string outright rather than merging into whatever was already there. So the only two things that can ever hide a fresh arrival's row are `collapsedGroups` (component state, empty on mount) and `hideHealthy` (URL, but always at its default on a cold arrival since the notification's URL carries no `orders.*` params at all). Given that, forcing the row's group open is implemented by overriding `folded` for the highlighted row's own group during render — local, not a `setFilter`/`setSearchParams` call — specifically to avoid a same-commit race against `useHighlightParam`'s own `setSearchParams` call in its mount effect (both would otherwise be writing the URL in the same React commit on first render, and `react-router`'s functional `setSearchParams` updater risks one clobbering the other). This is recorded as a judgment call rather than a fully-settled scope decision: a content filter (search text, side, a problem chip, a character filter) _could_ still exclude the row from `groupingRows` entirely if the page were navigated to this same route without going through a notification click while such a filter was already active — that path is not cleared, and the row would simply not render, matching "harmless, no match" rather than "shown regardless."
