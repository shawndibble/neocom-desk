# Scope decisions — Closed-app pollers skip idle grants and back off stale devices (issue #5144)

_Recorded 2026-10-25 · issue #5144._

- **Measured, not estimated.** Each `pollEveNotifications` run logs one `pollEveNotifications finished` line and each `dispatchProjections` server-event tick one `Server event poll finished` line, both counts only (field names are fixed in `functions/src/runStats.ts`: grants listed/refreshed/skipped by reason, `tokenRotationWrites`, devices read, `firestoreReads`/`firestoreWrites` at the call sites the pollers own, ESI calls per endpoint, `durationMs`). Counters are in memory and logged, never written to Firestore.
- **A grant is idle when no live device wants anything its scopes cover.** Notifications: some `eveTypes` on. Mail: the mail scope and `newMail` on. Location: the location scope and an `incursionNearby`/`skyhookRaidableNearby` on. An idle grant gets no token refresh and no ESI call. A grant that has seen no notification type yet is still read once so its toggles can appear (a type is only offered after it has been seen).
- **Going idle never opens a replay.** The first time a grant is found idle it gets one write: `notificationsIdle: true` and the mail mark cleared, as #5143 already did for mail. The first read after it ignores the ETag and pushes nothing older than the earliest wanting registration's `updatedAt`, so enabling a type never replays what passed while none was on. Nearby needs nothing: its state lives on the device registration and is already dropped for a Character that is not located.
- **No candidates, no location read.** The incursion and raidable-skyhook lists are read once per run, before any Character, and shared with the nearby phase. If every list a live device reads is empty, no Character's location is read; each still goes through the phase (with `NO_ORIGIN_SYSTEM`) so stored state is brought up to date exactly as with an empty list today. A list that failed or backed off is not known to be empty, so the locations are read.
- **Stale-device back-off reuses the registration's `updatedAt`.** `registerDevice` already stamps it on every call (the open app re-registers hourly), so no new field. Steps: re-registered within 14 days, polled on every 15-minute run; 14 days to the account inactivity window (`ACCOUNT_INACTIVITY_MS`, 90 days, `purgeStaleAccounts.ts`'s own rule), polled every 4th run (hourly); beyond that, not polled until the app registers it again. 14 days covers a holiday without slowing anyone down; 90 days is when the account's synced data is purged anyway, so there is no second staleness rule. A registration with no `updatedAt` counts as fresh.
- **Back-off decides who triggers a poll, not who is told.** A sleeping device is not the reason a grant is read, but when another device's read finds something it is pushed to as well (an FCM send costs nothing extra). A grant only sleeping devices want is skipped without touching its state; one only dormant devices want is idle. The server-event tick skips sleeping and dormant devices outright, and clears a dormant device's stored readings once, so waking it seeds silently rather than announcing every loss since.
- **One device read per run.** Planning needs the devices before the refresh, so the registrations are read once for all active grants and shared with the nearby phase (`registrationReader.ts`), replacing a read per Character on every 200 plus the phase's own.
- **Known limits.** A stale device's document is still read by the listing queries (a range filter on `updatedAt` would need a composite index); the saving is the token refresh, ESI, zKillboard and Fuzzwork calls. A Character whose every seen type is off for every device, and for which a new default-on type appears, is not offered it until some type is on.
