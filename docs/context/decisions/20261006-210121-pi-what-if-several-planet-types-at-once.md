# Scope decisions — PI what-if: several planet types at once on the Map (issue #2795)

_Recorded 2026-10-06 · issue #2795. Code: `src/features/pi/map/PlanMap.tsx`, `map/mapModel.ts` (`unlockedBy`, `unlockedRecipe`), `biggerChainsModel.ts` (`whatIfKey`, `whatIfPlanetId`, `whatIfChainCandidates`, `estimateOnColoniesWith`, `estimateOnNewPlanetsWith`), `useBiggerChains.ts` (`useWhatIfChains`). Supersedes the "One planet is added, not several" bullet of [20261006-162120](20261006-162120-pi-what-if-add-a-planet-for-bigger.md)._

- **On the Map, every ticked what-if planet type counts, together.** Clicking a planet type the pilot lacks ticks it; clicking it again unticks it; the last one off closes the panel. Hovering a type that is not ticked still previews that type alone. The unlocked products, the best one-planet recipe, the Bigger chains and the planet finder all read the whole ticked set, as one set (a new planet of each type), not every subset of it. Trying every subset multiplies the solver runs by the number of subsets; one run for the set the pilot actually ticked keeps the cost at what one type cost.
- **Every ticked type takes a free planet slot.** With fewer free slots than ticked types the panel says so and prices no Bigger chain, the same as no free slot did for one type. The unlocked products and the one-planet recipe still show: they do not use a slot.
- **A chain counts only when it uses at least one added planet.** It may leave another ticked type out; the figure is still for the whole set's slots. A chain that needs none of them is already on the pilot's own planets and is not listed.
- **Plan is unchanged: one type at a time.** Its "What if I add a planet?" rows still price one type each; only the Map takes a set. Both tabs share one cache, keyed by the sorted types (`lava+plasma`), so a single type's key is the type itself.
- **A new planet's id is negative, one per added type** (`-1`, `-2`, … in sorted-type order). Every route to one reads "not known yet", never zero.
