# Scope decisions — Communities: approve new Members is an admin switch, mailed invites skip it

_Recorded 2026-10-12. Refines "Invite link only in v1" in `20261011-160026-communities-share-blueprint-libraries.md`._

- **"Approve new Members" is a per-Community switch the admin sets on the Invites tab, off by default.** With it on, a Character that joins by the link does not become a Member: it becomes a **Join Request**, and the join page says the admin has to let it in. The link still shows the same preview and still needs no account to read.
- **A Character the admin mailed an invite to goes straight in, once.** The admin already chose that Character by name, so asking again would be noise. The check is the confirmed mail-invite record for that Character in that Community: it must have been sent (not just reserved), come from the Community's current admin, and not have been used to join already. Joining on it marks it used, so a Member who is removed or leaves must be approved again, and an admin who hands the role on takes their mailed invites' approval with them.
- **The caps apply when someone asks, and again when the admin accepts.** A request is refused up front if the Community is full or the Character is already in 10 Communities, so nobody queues for a seat that is not there. Accepting re-checks both, because either may have changed while the request waited. A cap that stops an accept is named to the admin and the request stays.
- **Waiting requests belong to the admin.** Only the admin can read them (a Community rule, like mail invites), only the join and decision callables write them, and they are deleted with the Community. Turning the switch off leaves requests already waiting for the admin to decide; it does not admit them. Declining deletes the request with no message to the Character, who can ask again.
- **Share choices survive the wait.** A Character that picked blueprints on the join page keeps that choice on the device while it waits; the library publishes on the next sweep after it is let in.
- **Where it shows:** the switch, the link and mail invites are the Invites tab (admin only). Waiting requests sit above the Member list on the Members tab, which carries a "· N waiting" count while there are any.
- **Needs a deploy.** The switch and the decision actions are new Cloud Functions callables and the requests rule is new, so a build that reaches the admin before `firebase deploy --only functions,firestore:rules` shows an error on those controls; joins by link keep working as before until the switch is on.
- **A stale request never evicts a Member.** Accepting a request whose Character already has a Member doc (it was sold and the new owner joined, or it joined another way) just drops the request.
