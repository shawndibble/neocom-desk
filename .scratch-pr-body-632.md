## Summary

Editing the form (hub/facility/build system, security follows the system) writes nothing until Save; the preview lists every member plan with a checkbox (checked by default) so any plan can be left alone.

- `BuildGroup` gains an optional `snapshot` (`BuildGroupSnapshot`): the last-applied Retarget values + timestamp, stored in the same synced-setting blob (no Dexie schema change). Inert — never read by any calculation engine.
- Adds a persistent per-plan "Use group target" link (`GroupTargetLink.tsx`, styled like `OwnedStockHint`) beside a plan's own hub/facility/security/build-system controls in `BuildPlanDetail.tsx`. Usable any time, renders nothing once the plan already matches the group's snapshot or the group has none yet.

## Deviation from the brief

Acceptance criterion "a new plan created into a group with an existing snapshot pre-populates from that snapshot" (`newBuildPlan.ts`'s `defaultsFrom`) is **not implemented**. The brief assumed a flow that doesn't exist in this codebase: no UI currently creates a brand-new plan directly into an _already-existing_ group at creation time. The only two ways a plan gets a `buildGroupId` today are Fit Import (which always mints a brand-new group via `crypto.randomUUID()`, so it can never already carry a snapshot) and the existing "Move to group" action on an already-created plan. Building a new "create plan into this group" entry point would be unrequested scope beyond this ticket's actual ask. The persistent quick-fill link (criterion 4, "usable any time") closes the same gap in one extra click: create the plan (today's character-recency defaults), move it into the group, click "Use group target."
