## Settled icon map

Glyph → its one meaning, confirmed consistent app-wide. A new use of a listed
glyph for a different meaning is a finding.

| Glyph                           | Meaning                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Icon.Close` (X)                | Overloaded by design, not drift: close an overlay, clear a field/search, dismiss a notification, remove a non-persisted item, or permanently delete a saved entity — disambiguated by `tone="danger"` for the destructive cases (see Contract already enforced). Treat a plain (non-danger) `Icon.Close` next to a destructive, unconfirmed removal as the one remaining risk shape. |
| `Icon.More` (DotsThreeVertical) | "Open this row's/panel's overflow menu." Single import site in `icons.tsx`, single meaning everywhere.                                                                                                                                                                                                                                                                               |
| `Icon.Done`                     | "Success / confirmed / completed" — used for calendar RSVP acceptance, post-copy confirmation swaps, and build-plan verdict tone. One meaning across all sites checked.                                                                                                                                                                                                              |
| `Icon.Select`                   | "Pick/target this row" (Blueprint Acquisition modal, Assets/CorpAssets pin-to-plan). Distinct from `Icon.Done` despite sharing the `Check` Phosphor glyph — different call sites, no overlap.                                                                                                                                                                                        |

## Contract already enforced

Patterns guarded by a lint rule or a test, so no run re-sweeps them. The
built-in lint rule is covered in RUBRIC.md axis B. Add a line here whenever a
filed ticket lands its guard.

- **`tone="danger"` on a destructive `Icon.Close`.** Settled via #1998 (closed): an icon-only `Close` `IconButton` that removes an entry from a user-owned list or deletes a saved item carries `tone="danger"`; a neutral X stays for dismiss/clear-field/close/unlink. Verified across ~10 sites (`BuildPlanList` plan/group delete, `MyFittingsPanel`, `DamageProfilePicker`, `PlanList`, `Characters.tsx` character/group, `EntryList.tsx`, `PlanEditor.tsx`, `BoosterList.tsx`) — all compliant except the one gap filed as #2100 (`FittingCompare.tsx`'s error-slot branch, missed by #1998's fix scope). No test guards this app-wide yet; #2100 adds one scoped to `FittingCompare`. A future run should check whether a broader lint/test (e.g. asserting every `Icon.Close` `IconButton` wired to a delete-type handler carries `tone="danger"`) is worth adding once #2100 lands.
- **No raw Tailwind palette colors, no off-scale `rounded-*`, no stray shadows.** All three token checks (axis F) came back clean or fully explained by an existing shared pattern — nothing to file, nothing new to guard.

## Justified exceptions

Matrix holes and deviations confirmed deliberate, so no run re-flags them.

- **Character "Remove" vs. entity "Delete."** `characters.removeButtonLabel`/`removeConfirm` say "Remove {{name}}," while Build Plans, My Fittings, Skill Plans, Skill Compare and Mining Tax payees all say "Delete" for equally irreversible, confirmed actions. Looks like the rubric's canonical "one action, two verbs" case, but it's deliberate: multiple scope decisions (`20260925-113019-log-out-and-remove-character-unregister-this-devices.md`, `20260926-212411-removing-a-character-deletes-its-production-log-rows.md`) and `CONTEXT.md` (search "removing a Character") establish "removing a Character" as its own settled glossary term, distinct from a plain CRUD delete — a removed character is re-addable and its synced data can restore, unlike a deleted Build Plan or fitting. Do not re-file this.

## Standing kill-tests

See RUBRIC.md "Standing kill-tests". Add here only heuristics learned from a
run that are not yet worth promoting there.

- **A shared `removeSlot`/`onDelete`-style handler wired to two render branches in the same file is worth diffing branch-by-branch**, not just component-by-component — a prior consistency fix (#1998) can land on the common-case branch and miss an early-return/error branch calling the identical handler. This is how #2100 was found.
- **Read this ledger from `origin/main`, not the local working tree.** The rubric's "survey `origin/main`" instruction applies to the skill's own `LEDGER.md`/`RUBRIC.md` too — a stale main checkout can carry a stale, pre-first-sweep copy of this very file even after several runs have already curated it on `origin/main`. Diff `git diff origin/main -- .claude/skills/ui-consistency/LEDGER.md` (with `MSYS_NO_PATHCONV=1` on Windows git-bash, since a bare `git show origin/main:<path>` mis-parses a colon immediately followed by a dot) before trusting what a plain file read shows.
- **A route-file-only grep for a row's visible "more actions" twin can false-positive as a hole.** `Assets.tsx`/`CorpAssets.tsx` render every item row through a shared `assetBrowserRows.tsx` helper, so the twin (`RowMoreActions`) lives in that file, not the route. Grep the actual row-rendering component, not just the route that imports it, before filing a D finding.
- **A surface with a very recent scope decision may have already been deliberately given a different remedy for the same-looking gap.** Check `docs/context/decisions/` dates before filing, not just for "is this allowed" but "was this exact spot just chosen on purpose to work differently." `PlanVerdictHero.tsx`, `ActiveJobsPanel.tsx` and `MaterialsTable.tsx` all got a visible "More actions" button from #1498 (2026-09-24) as the chosen fix for discoverability — a plausible-looking "add `MarketItemLink` here too" finding on the same rows should say so explicitly and treat it as an addition needing its own justification, not an oversight.
